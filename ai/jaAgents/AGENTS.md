# Codex Agent 工作协议

## 🔴 本文件的修改授权（用户 2026-09-10 设立）

**未经用户明确授意，不得修改本文件（`AGENTS.md`），也不得修改 `CLAUDE.md`。**

- 「授意」= 用户在当前对话里明确说了要改这份协议（"在 agents 文档里加一条…"、"把这条规则改成…"）。
  从别处推断出来的都不算：顺手发现规则写得不好、其他文档改了想同步过来、自己觉得某条已过时——一律**先说出来问，不要动手**。
- 改完必须在报告里贴出改动原文（增 / 删 / 改哪一节），与代码改动同等待遇。
- **`CLAUDE.md` 与本文件是一对**：一份改了什么，另一份要等义跟改，只在「两个 agent 的机制不同」处分方言。

> 为什么：这份文件是每次对话的开场规则，改错一句会静默影响之后所有会话。正本在 `ai/jaAgents/`，随仓库入库；根目录这份是给 agent 读的副本（gitignored）。两份改哪份都行，`shelf sync` / `push` 会把改动同步给另一份。

## 规则来源与优先级

- 本文件是 Codex 在本项目中的工作协议，由根目录 `CLAUDE.md` 等义改写而来，规则一致，只有取用技能的方式按各自 agent 的机制不同。
- 通用技能登记在本文件「Skill 系统」节；本项目专属技能登记在 `ai/JASKILL.md`；项目特有的强制前置动作在 `ai/PROJECT.md`「开工红线」。三份都要在开工前读。
- 系统、开发者和用户在当前对话中的明确指令优先于本地文件；其余情况下严格执行本文件与上述三份。

## 上下文准备

每次对话开始时：

1. 读 `ai/PROJECT.md`（含「开工红线」，本项目的强制前置动作）和 `ai/TODO.md`
2. **完整读取 `ai/JASKILL.md`**：本项目专属技能的登记、用法摘要与项目口径都在这里，开场整份读，用来在合适的场景触发技能（用户 2026-10-16 定）。Codex 的技能列表只给名字、描述和位置，也不展开 `@` 导入，所以这一步要自己打开文件
3. 需要确认本地实际装了哪些技能时，列一次 `.agents/skills/` 与登记表核对
4. 遇到对应场景时，**按登记表打开对应技能的 `SKILL.md` 并执行**，不要重新发明已有规范
5. **不要读 `ai/sessions/`**：那是手动会话存档，只在用户点名某个档时才读。开场不扫这个目录、不列有哪些档、不问要不要恢复

## Skill 系统

### 真源与落点

技能本体只有一份，在 **`ai/jaSkills/`**，随仓库入库；`.agents/skills`、`.claude/skills` 各是指向它的整目录链接（Codex / Claude Code 分别从这里发现技能）。链接与根目录协议副本都 gitignored，新检出、新 worktree 里默认没有——**开工第一步先补齐**（重复执行安全）：装了 shelf 就跑 `shelf init`，按账本还原链接、根目录协议副本和缺的货；没装 shelf 或没网，跑 AI 工作流模板带的保底脚本（.NET 项目是 `AI/scripts/`）：

```bash
shelf init                                   # 装了 shelf：按账本还原
bash ai/scripts/sync-worktree.sh             # 没装 shelf：补技能链接 + 协议副本，两个 agent 都补
bash ai/scripts/sync-worktree.sh --dry-run   # 只报告不动手
```

旧版脚本或手动 `ln -s` 在 Windows 的 Git Bash 里会把链接建成目录副本（PA-060，脚本已修）：PowerShell `(Get-Item .agents\skills).LinkType` 为空就是副本——先 `diff -r .agents/skills ai/jaSkills` 确认副本没有独有改动，删掉再跑保底脚本。`Junction`、`SymbolicLink` 都是有效链接；删链接只用 `cmd /c rmdir <链接路径>`（不带 `/s`），递归删除会删到正本。

**要改技能就改 `ai/jaSkills/`**——技能目录是链接，从哪边改都是同一份；改完 `shelf push ai/jaSkills/<名>` 同步到货架。

### 调用方式（Codex 侧）

Codex 没有技能调用工具，「触发某个技能」就是**完整读取 `.agents/skills/<技能名>/SKILL.md`**（等价于 `ai/jaSkills/<技能名>/SKILL.md`）并按其指令执行。技能正文按 Claude 的机制写，读到这几类写法自己翻译：

| 写法 | Codex 侧怎么办 |
|---|---|
| `` !`命令` `` | 不会自动执行，遇到就自己跑一遍那条命令，把输出当作它要注入的上下文 |
| `${CLAUDE_SKILL_DIR}` | 没有这个变量，按 `.agents/skills/<技能名>/` 代入 |
| `allowed-tools` | Claude 侧的预批准清单，Codex 侧忽略，按自身权限模式执行 |
| `$ARGUMENTS` | 调用时用户给的参数，自己代入 |

### Skill 对话规范

在技能上下文中回复时，**在回复开头标注技能名**，像这个技能的「人」在说话，例如 `**INTJ** 好，我看了一下，你现在还有...`、`**VC** 当前分支状态如下...`。格式：`**技能名（全大写）**` + 空格 + 正文。

## 文档维护规则

### 职责分工（哪份文档装什么）

- **PROJECT.md**：项目现状——结构、功能摘要、数据库摘要等技术事实（表结构正文的位置由 PROJECT 写明），以及 Brain Dump 想法区
- **TODO.md**：任务的唯一来源，**只记没做完的事**；做完就从 TODO 删掉（实现细节进功能文档，过程留在 commit）
- **features/**：一个功能一份的实施文档，装实现细节、Subtask 进度、边界情况与测试记录
- **sessions/**：会话存档目录，一个会话一份，文件名 = 会话标题（手上这件事 / 关键决策 / 下一步 / 别踩的坑），由 `intj` 维护，入库（用户 2026-10-10 设立）。长期为真的东西归 PROJECT.md，待办归 TODO.md，存档只留续接所需的最小上下文。**全程手动**：用户说存才存、点名才读、说删或问过才删

**活文档只写现状**：实现变了就改写对应段落，不追加带日期的过程段；用户的决定记进项目的决定清单（编号、写明谁何时定），过程与证据留在 commit 和审核目录。

怎么写、什么时机写、谁来写的细则归对应的技能（两边各写一套会各自漂移）；Codex 侧没有自动加载，要用哪条规则就**去读那个技能的 `SKILL.md` 全文**：

| 文档 | 归谁管 | 到哪查规则 |
|---|---|---|
| `ai/TODO.md` · `ai/PROJECT.md` | `intj` | Brain Dump 流、写入时机、写什么不写什么 |
| `ai/features/*.md` | `intj` + `feature` **共管** | `feature` 管细节（目标、链路、Subtask、测试）；`intj` 管 PROJECT 里的摘要与索引、TODO 同步 |
| `ai/sessions/` | `intj` | 两条铁律（手动存、点名读）与存档模板 |

### Agent 记忆只装「用户要求隐藏」的规则（2026-09-29 用户设立）

Agent 的持久记忆（Claude 侧是 auto-memory：`~/.claude/projects/<项目>/memory/`，`MEMORY.md` 索引 + 各条主题文件；
Codex 侧若启用了跨会话记忆，同一口径）**只存一类东西：
用户明确说过要隐藏、不能写进项目的规则**——我们自己记住、不入库的那部分。

- 其余一切（项目事实、踩坑与排查手法、上游契约、流程规则、用户对工作方式的要求）**一律写进项目**：
  按上面的职责分工落到 PROJECT.md / TODO.md / features/ / 对应 skill / 相关 README，不进记忆。
  协议级的规则经用户授意才改本文件，否则写进 `ai/PROJECT.md`。
- 写记忆前先自问：用户说过这条要藏起来吗？没说过就不写记忆，写进项目；判不准就问用户。
- 记忆里已有的条目，项目里已经有等价记录的就删掉记忆那份；记忆与项目矛盾时以项目为准，并删掉记忆。

> 为什么：记忆不进 git、没有 diff、换设备或换 agent 就没了，而且会和项目文档各自漂移；
> 项目文档才是所有 session 与协作者共同的真源。记忆要保持干净。

## 命名规则

新建文件、文件夹或文档前，**先扫描当前项目已有的命名模式**并遵循它，不凭习惯套用其他项目的规则。看这几个维度：文件夹大小写（全小写 / PascalCase / kebab-case）、文档（`.md`）命名风格、代码文件命名（camelCase / snake_case / kebab-case）、是否有 `codeStyle.md`、`.editorconfig` 等明确规范文件。

同一类目内存在多种风格时，挑**多数派**或**最近新增**的那种；不确定时先问用户。发现历史遗留不一致的，顺手改正，并在报告里说明（用户 2026-10-17 定）。

## 语言规则

默认使用**中文**与用户沟通。必要时（代码术语、英文原文引用等）可穿插其他语言。

## 会话标题

**每当这个会话开始做一件新的、和当前标题对不上的事，就主动把会话标题改掉**（用户 2026-09-10 设立），不等用户开口。判据：用户扫一眼标题列表，能不能说出这个会话现在在干什么。

- **触发**：接到新任务 · 任务性质转向（从「调查 X」变成「修 Y」）· 原标题已经名不副实
- **不触发**：同一件事的正常推进（写完代码去跑测试、开完 PR 等 CI）
- **写「在做什么」，不写「做完了什么」**：短名词短语并带上对象。`技能真源统一到 ai/jaSkills` 好过 `更新文档`；`Data Hub 404 排查` 好过 `修 bug`
- **手法（Codex 侧）**：改名是客户端动作（`/rename` 等），agent 的工具里没有改名工具，所以动作是**把标题算好、提醒用户按一下**：`【建议改名】<短名词短语> —— 打 /rename 回车即可`。不要写成「已更新标题」——没有权限做的事写了就是假交付。非交互场景（`codex exec`）在该轮输出第一行写 `【本轮任务】<短名词短语>`。以后接上能改名的工具（MCP / plugin 包一层 app-server 的 `thread/name/set`）就改回「直接改，不提醒」

## Log 规范

写、改、检查任何 log 语句时**先读 `.agents/skills/logman/SKILL.md`**，按它的规范来（标签格式、功能域、运行时环境标签、分级与 Pro 屏蔽、检查清单都在 `ai/jaSkills/logman/`）。协议里不写格式细节——不同项目的日志形态不一样，写死会把别的项目的习惯带过来。

## 代码风格

**动手写第一行代码之前，先找项目里的风格与格式配置，按它生成代码。** 至少看：格式化器配置（`.prettierrc*` / `prettier.config.*`、`.editorconfig`）、Lint 配置（`eslint.config.*` / `.eslintrc*`、`biome.json`）、风格文档（`codeStyle.md`、`CONTRIBUTING.md` 之类）。

**这些配置是用户手工设定的标准，优先级高于「代码库现状」**（用户 2026-08-11 明确：配置是他手动设的，代码是 agent 写的，该向配置看齐）。现存代码不符合配置，说明的是代码欠格式化，不是配置写错了——不要反过来推断「多数文件是 2 空格所以应该用 2 空格」，也不要去改配置迁就现状。

配置与现状冲突时：按配置写新代码；要不要顺手格式化存量，问用户。项目里没有任何这类文件，才按通用习惯来，且不强行套用其它项目的规则。

## 报告规范

**每一轮任务结束都给详细报告**（不再以 Full Access 为前提，用户 2026-10-16 定）。报告义务不扩大用户请求的任务范围，也不自动授权破坏性操作、外部发布或其他需要单独授权的动作。

> 🔴 **这条最常被忘（用户 2026-09-10 点名强调）。** 最典型的漏法不是「完全没报告」，而是**改完东西只用文字交代，没把改动的代码 / 文档原文贴出来**——活干得越多、报告写得越长，越容易省掉贴码只留叙述。
>
> **发出每一轮回复前，先自查这三条**：
> 1. 这一轮**动过的每个文件**，报告里是不是都有一节？（含只改了一两行的、含删除、含 `.md` 文档）
> 2. 每一处改动是不是都有**实际代码块**？（表格 / 要点 / 摘要**不算**，删除要贴被删的原文）
> 3. 每个代码块前后是不是各有一句话——前说「这段干什么」，后说「为什么这么做 / 原来会怎样、现在会怎样」？
>
> 三条里有一条答不上，**这轮报告就还没写完**，不要发。「怕报告太长」不是省略的理由——该省的是叙述，不是代码。

1. 自主完成全部工作，中途不停下等确认（破坏性操作除外）
2. 报告覆盖：做了什么、为什么这么做、遇到的问题与处理、验证结果
3. **改了文件的回合，详细报告用 `annotated-report` 技能做成可批注的页面**（用户 2026-10-16 定，方便批注验收）。Codex 用该技能的 `build-report.mjs` 生成页面：能用 Sites（ChatGPT / Codex 的站点托管，公开测试）就发布成站点、访问范围只选用户本人，会话里给链接和结论；用不了时生成到 `tmp/reports/`（不入库）给文件路径；纯问答、没改文件的回合直接在会话里答
4. **代码修改逐文件展示实际代码**（写在报告页里）：
    - **行文节奏：一句话 → 一段代码 → 一句话 → 一段代码**（用户 2026-09-09 设立），不许「一大段叙述 + 末尾一个代码块」。判据：读者不看仓库、只读这份报告，能不能说出每一处改动改了哪一行、为什么
    - **贴重点代码，不倾倒全文**：每个文件挑真正承载这次改动的那几行，用 `-` / `+` 标出前后差别，上下文超过三五行用省略号收掉；改动多到贴不完时，按「这次的结论靠哪几行成立」排序先贴，其余列清单
    - **术语顺手翻成人话**（2026-10-06 用户设立）：不说「壳」，说「响应体外面那层 `{success, data, errorCode}`」；壳 / 归类 / 透传 / 预签名这类写代码时的速记，对读报告的人就是密码
    - 每个改动文件一节：文件路径 + 这个文件为什么要动；一两行的小改动也贴；新文件或新函数贴核心代码全文；样式改动贴关键 CSS 规则
    - 删除 / 移除也是代码改动，贴出被删的原文；移动代码贴「从哪删、加到哪」两侧
5. **每条 command 都说明为什么执行**（shell、git、构建等）；批量同类命令可合并说明一次
6. **文档修改（`.md` 等）同样展示**：改了哪个文档的哪一节，贴出新增 / 修改的关键段落原文（直接改不用事前确认，事后必须展示）
7. **暂存区只放本轮自己的改动，提交只管自己那份，默认不推送**（用户 2026-08-11 设立，2026-10-16 加暂存规则）：每轮结束只把本轮自己改的文件逐个 `git add` 进暂存区、不提交，用户看暂存区就是这一轮的 diff；上一轮留在暂存区的改动，本轮开工时先提交（说明写清是上一轮的内容）再开始。用户要求本轮就提交、推送或合并时照做。

    | 动作 | 默认 |
    |---|---|
    | commit **本会话自己改的**文件 | ✅ 按上面的节奏 |
    | commit **别的会话 / 用户**改的文件 | ❌ 禁止 |
    | `git push` | ❌ 禁止，除非本会话用户明确授权自动推送 |

    - 暂存的做法见下方「并行工作区保护」（任何模式都适用）
    - **同文件混杂时**（自己和别人的改动落在同一个文件里，git 拆不开）：可以整文件提交，但 commit message 里**必须说明**哪些是本会话做的、哪些是搭车进来的、为什么拆不开
    - 「可以推送」的授权**只在当轮有效**，不跨会话继承
    - 判不准某个文件是不是自己改的，就问，不要猜

    > 为什么：多个会话会并行改同一个仓库。把别人的工作卷进自己的 commit，commit message 就与内容对不上，要回退时也拆不开；未经许可 push 会把别人**尚未完成**的中间状态推上远端。本项目踩过：一次 `git add -A` 卷入了他人的改动。

8. **在 worktree 里工作时：合并只走 rebase，不切分支**（用户 2026-08-20 设立，2026-09-10 改合并行；集成分支 2026-10-16 起是 `main`）：

    | 动作 | worktree 中的默认 |
    |---|---|
    | 在本 worktree 自己的分支上 commit | ✅ 自主执行 |
    | push 本 worktree 自己的分支 | ✅ 自主执行（推的是自己的分支，不碰共享分支） |
    | 创建 PR（base: main） | ✅ 自主执行 |
    | **`gh pr merge --rebase`** | ✅ 自主执行，**前提是下面三条校验全过**；CI 绿即可合，不必等人审。单分支 PR 一律 rebase，环境分支之间同步（如 dev → staging）才用 `--merge`（用户 2026-10-17 定） |
    | **`gh pr merge --squash` / `--admin` / `--auto`** | ❌ **禁止**：squash 把一条分支上几件事压成一个提交，日后 `blame` 只剩一句概述；`--admin` 绕过检查；`--auto` 让合并发生在没人看着的时刻 |
    | **`--delete-branch`** | ❌ 别加：它会在本地切 base 分支——主检出占着 `main` 时报假失败（PR 其实合了），没占着时把**本 worktree 骑到 `main` 上**。合完手动 `git push origin --delete <branch>` |
    | checkout / switch 到别的分支 | ❌ **禁止** |
    | 把工作区分支 reset 到别处 | ❌ **禁止** |

    - **合并前三条校验，缺一不合**：① CI 跑在**当前 head** 上——按 sha 直查 `check-runs`，`gh pr checks` 会把旧 head 的绿报成通过；② 不落后 `main`——落后就先 `git rebase origin/main`、`--force-with-lease` 推，再等**新 head** 的 CI（文本不冲突 ≠ 能编译）；③ `main` 自己是绿的——红了先修 `main`
    - 合完核对 `state=MERGED`，再看一眼 `git worktree list`——自己那行不该变成 `[main]`
    - 需要知道上游进展时用 `git fetch` 拿信息，不 reset、不 checkout；主检出（非 worktree）的分支状态一律不碰——那可能是别的会话的工作台

    > 为什么：worktree 存在的意义就是「我这条线的改动不影响别人」，切分支会改动共享检出的状态、打断并行会话。**合并本身不禁**——`main` 只能经 PR + 校验进入，三条校验就是那道门；禁的是绕门（`--admin`）、不看着门（`--auto`）和把历史压扁（`--squash`）。

## 并行工作区保护

- 任何时候都只提交本任务自己的文件：逐个 `git add` 自己改的路径，不用 `git add .` 或 `git add -A`
- 发现本地主检出、其他分支或同文件存在并行任务内容时，保留原状，不 reset、不覆盖
- 需要 rebase 或强制更新自己的功能分支时，只能用 `--force-with-lease`，不得强推共享分支
- 合并前按上面第 8 条的三条校验走，合并后核对 `state=MERGED` 与 `git worktree list`
