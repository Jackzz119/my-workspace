# /feature — 功能驱动开发流程

**触发策略：询问后触发** — 检测到相关场景时，先提示用户确认是否触发，等用户同意后再执行。

用法：`/feature <功能名>`

功能名对应 `ai/features/<功能名>.md`。如果文档不存在，流程会先帮你创建它。

`ai/features/` 是每个项目都有的固定目录：本技能在 frontmatter 的 `metadata.shelf-scaffold` 里声明了它，`shelf init` / `shelf sync` 会在项目里建出来（空目录放 `.gitkeep`），不等第一份功能文档才建。

## 🔴 菜单功能走 menu 目录（2026-08-12 立）

**如果这个功能对应一个菜单项**（= 侧栏里能点到的一屏），它的文档**不在** `ai/features/` 根下，
而在**菜单功能目录**里，且必须走登记流程：

1. **开工前**：读该目录的 `INDEX.md`（功能目录 + entry 契约 + 登记点清单），
   再读这个功能自己的 `<KEY>.md`。文档不存在就按目录里的模板新建，并在目录表登记一行。
2. **动代码时**：按 `INDEX.md` 的「新增一屏的登记点」逐项过；文件放置按 `STRUCTURE.md`
   （一屏一文件夹、`_components/` 私有、路由组只分组不改 URL）。
3. **收工后**：回写 `<KEY>.md` 的「现状 / 待办」，并把状态列同步回目录表。
4. **删除功能**：按 `INDEX.md` 的「彻底删除」四处一起删——entry、权限键、页面文件夹、
   功能文档 + 目录表那一行。缺一处就是悬空引用。

> 本项目的菜单功能目录 = `ai/features/menu/`（入口 `INDEX.md`）。
> 若项目没有这个目录，本节不适用，按下面的通用流程走。

**不要**把菜单功能单独登记进 `ai/PROJECT.md` 的文档索引——那张索引只登记文档族的入口，
功能级登记全在菜单目录表里，否则功能一多索引就失控。

---

> **命名**：新建功能文档时，文件名跟随 `ai/features/` 里已有文档的命名模式（协议「命名规则」）；`/feature` 后的功能名按已有文档匹配，不区分大小写。

## 与 intj 的分工（feature 文档共管）

`ai/features/*.md` 由 **intj 和本 skill 共同管理**，但各管一层：

| | 谁负责 | 管什么 |
|---|---|---|
| Feature 文档的**细节** | **本 skill** | 功能目标、调用链路、模块设计、Subtask 拆分与进度、边界情况、测试记录 |
| Feature 文档**存不存在、要不要建** | 本 skill（Step 1） | 不存在就先建，菜单功能按 `INDEX.md` 登记 |
| `PROJECT.md` 里的**摘要与索引** | `intj` | 只写一句摘要 + 文档路径引用，**不搬运细节** |
| `TODO.md` 的增删 | `intj`（本 skill 在 Step 4d / 6 同步） | 高层任务描述，不写数据结构 |

一句话：**细节归这里，摘要与待办归 intj。** 同一件事不要两边都写全文——
Feature 文档已有的细节，PROJECT.md 只引用不复制。

## 流程步骤

执行此 skill 时按以下顺序推进。Step 2、3 定方向，要用户点头；Step 4 起按批准的计划连续执行，每轮结束给详细报告（按协议的报告规范）供用户验收；要用户在实际环境里测的，停下等反馈。

### Step 1 — 读取 / 创建功能文档

> 菜单功能先看上面那节：文档在 `ai/features/menu/<KEY>.md`，且要读 `INDEX.md` 的登记点清单。

1. 尝试读取 `ai/features/<功能名>.md`
   - 存在 → 展示文档的**当前状态摘要**（章节列表 + 未完成 TODO 数量）
   - 没有 → 再找同名文件夹 `ai/features/<功能名>/`（文档多于一份的功能放文件夹，主文档通常与文件夹同名）；都没有才告知用户，准备在对话中收集信息后创建

### Step 2 — 需求对齐

与用户聊清楚以下内容（已有文档的可跳过已记录部分）：
- 功能目标是什么？
- 涉及哪些系统/模块？
- 完整调用链路是什么？
- 有哪些边界情况需要考虑？
- 有没有可参考的已有实现或项目？

对话结束后，将收集到的内容**更新写入** `ai/features/<功能名>.md`，保持文档始终是最新状态。

### Step 3 — 拆分 Subtask

根据功能文档，将实现拆分为**有序的 Subtask 列表**，写入文档的 `## 实现计划` 章节：

```markdown
## 实现计划

进度：0 / N subtasks 完成（0%）

- [ ] ST-1: <任务标题>
  - 影响文件：`路径/文件.cs`, `路径/文件2.cs`
  - 说明：做什么、为什么这么做
- [ ] ST-2: ...
```

展示给用户确认顺序和范围，等用户批准后进入 Step 4。

### Step 4 — 逐 Subtask 执行（循环）

对每个 Subtask，执行以下小循环：

**4a. 开工前**
- 列出本 subtask 的影响文件，先 Read 每一个
- 一两句说清改动方案（改哪里、改成什么、为什么）；超出 Step 3 批准的范围、或要在产品行为上做取舍时，先问再动

**4b. 执行改动**
- 按方案修改代码
- 改动的代码贴进本轮报告（按协议的报告规范）

**4c. 测试提示**
- 列出本 subtask 应测试的点（由用户在项目的实际运行环境里操作）
- 等用户反馈测试结果

**4d. 完成记录**
- 将 `ai/features/<功能名>.md` 中该 subtask 标记为 `[x]`
- 更新进度计数：`进度：K / N subtasks 完成（XX%）`
- 同步 `ai/TODO.md` 对应条目：改写它的进度描述；整条做完就从 TODO 删掉

### Step 5 — 最终测试 & 边界分析

所有 subtask 完成后：

1. **链路测试清单**：列出完整端到端流程的测试步骤
2. **边界问题分析**：列出可能的边界情况（空值、网络失败、多次触发、极端帧率等）
3. 针对发现的问题，视严重程度决定是否补充 Subtask 修复

最终将测试结论更新到 `ai/features/<功能名>.md` 的 `## 测试记录` 章节。

### Step 6 — 收尾

- 将 `ai/features/<功能名>.md` 中进度更新为 `100%`，标注完成日期
- 从 `ai/TODO.md` 删掉对应条目（实现与测试结论已在功能文档里）
- 可选：更新 `ai/PROJECT.md` 中对应模块说明（较大功能模块才需要）

## 功能文档的维护规则

功能文档是活文档：读的人要的是「现在是什么样」，不是「怎么走到这一步」。每次新建或修改都守这几条：

1. **开头一句话说范围**：标题下第一行说清这份文档管什么、其余内容去哪看（界面去设计系统、后端去后端文档、待办去 TODO）。不写「某日校准」「在役」这类状态行——状态看 git 历史和 TODO。
2. **只写现状**：实现变了就改写对应章节。带日期的过程段（「10-06 改成…」「后来发现…」）要么删，要么改写成现状的一句话；要留的原因跟着现状写，不讲经过。
3. **用户的决定只引用编号**：决定正文只在项目的决定清单里（清单在哪记在 `PROJECT.md`），功能文档写「（D-7）」并链过去，不复述——复述的那份会在决定修改时悄悄过期。
4. **测试记录每条一行**：日期 · 场景 · 结果 · 证据在哪；被新记录取代的删掉。
5. **命名跟随项目**：见上面「命名」。

## 文档章节模板

创建新功能文档时，使用以下模板结构：

```markdown
# <功能名>

<一句话：这份文档管什么；界面、后端、待办分别去哪看>

---

## 一、功能目标

## 二、调用链路

## 三、模块设计

## 四、时间线 / 参数

## 五、待实现 / 已知问题

## 实现计划

进度：0 / 0 subtasks 完成（0%）

## 测试记录
```

## 注意事项

- 每次对话中断后，用户可以用 `/feature <名字>` 重新进入，直接从文档的当前进度继续
- 如果用户说"继续"，默认从下一个未完成的 Subtask 开始
- 文档是唯一的进度追踪源——代码可能还没改，但文档的计划一旦写定就不轻易变动（除非用户要求调整方向）
