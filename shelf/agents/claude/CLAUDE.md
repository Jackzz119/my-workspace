## 🔴 本文件的修改授权（用户 2026-09-10 设立）

**未经用户明确授意，不得修改本文件（`CLAUDE.md`），也不得修改 `AGENTS.md`。**

- 「授意」= 用户在当前对话里明确说了要改这份协议（"在 claude 文档里加一条…"、"把这条规则改成…"）。从别处推断出来的都不算（顺手发现规则写得不好、其他文档改了想同步过来、自己觉得某条已过时）：一律先说出来问，不动手。

> 为什么：这份文件是每次对话的开场规则，改错一句会静默影响之后所有会话。正本在 `ai/jaAgents/`（入库），根目录这份是给 agent 读的副本（被 git 忽略），由 `protocol-mirror.sh` 用正本覆盖，所以要改就改正本。副本被改过时两份都不动，先给用户看 diff，确认后才 `shelf push … --take-mirror`（细则见 `shelf-ops`）。

## 文档维护规则

- **`ai/PROJECT.md`**：项目现状——结构、功能摘要、数据库摘要等技术事实（表结构正文的位置由 PROJECT 写明），以及 Brain Dump 想法区。
- **`ai/TODO.md`**：任务的唯一来源，只记没做完的事；做完就从 TODO 删掉（实现细节进功能文档，过程留在 commit）。
- **`ai/features/`**：一个功能一份的实施文档，装实现细节、Subtask 进度、边界情况与测试记录。
- **`ai/sessions/`**：手动存的档，入库（用户 2026-10-10 设立，2026-11-13 分成两个子目录）：`savepoint/` 会话存档、`handoff/` 交接档。全程手动——用户说存才存、点名才读、说删或问过才删。长期为真的东西归 PROJECT，待办归 TODO。
- **活文档只写现状**：实现变了就改写对应段落，不追加带日期的过程段；用户的决定记进项目的决定清单（编号、写明谁何时定），过程与证据留在 commit 和审核目录。
- **怎么写、什么时机写、谁来写，归对应的技能**（两边各写一套会各自漂移）：TODO、PROJECT、`ai/sessions/` 归 `intj`；`ai/features/*.md` 由 `feature` 管细节（目标、链路、Subtask、测试），`intj` 管 PROJECT 里的摘要与索引、TODO 同步。

### agent 记忆只装「用户要求隐藏」的规则（用户 2026-09-29 设立）

Claude 的 auto-memory（`~/.claude/projects/<项目>/memory/`：`MEMORY.md` 索引 + 各条主题文件）只存一类东西：用户明确说过要隐藏、不能写进项目的规则。

- 其余一切（项目事实、踩坑与排查手法、上游契约、流程规则、用户对工作方式的要求）一律写进项目：按上面的分工落到 PROJECT / TODO / features / 对应技能 / 相关 README。协议级的规则经用户授意才改本文件，否则写进 `ai/PROJECT.md`。
- 写记忆前先自问：用户说过这条要藏起来吗？没说过就不写记忆，写进项目；判不准就问用户。
- 记忆里已有的条目，项目里有等价记录的就删掉记忆那份；记忆与项目矛盾时以项目为准，并删掉记忆。

> 为什么：记忆不进 git、没有 diff、换设备或换 agent 就没了，还会和项目文档各自漂移；项目文档才是所有会话与协作者共同的真源。

## 会话标题

会话开始做一件新的、和当前标题对不上的事时，主动把标题改掉，不等用户开口（用户 2026-09-10 设立）。判据：用户扫一眼标题列表，能不能说出这个会话现在在干什么。

- 触发：接到新任务 · 任务性质转向（从「调查 X」变成「修 Y」）· 原标题已经名不副实。同一件事的正常推进（写完代码去跑测试、开完 PR 等 CI）不改。
- 写「在做什么」，不写「做完了什么」：短名词短语并带上对象。`技能真源统一到 ai/jaSkills` 好过 `更新文档`；`Data Hub 404 排查` 好过 `修 bug`。
- 最前面加模型和 effort（用户 2026-10-25 定）：`[Opus 5.5·max] Data Hub 404 排查`；中途换了模型或 effort，标题跟着改。
- side chat 要标出来（用户 2026-10-27 定）：方括号里在 effort 后面加 `·sidechat`，如 `[Opus 5.5·max·sidechat] Data Hub 404 排查`。判据：`get_session("self")` 带 `parentSessionId`，且 `detached` 不是 true。用户开的 side chat（Cmd+; / `/btw`）、从别的会话分叉出来的、别的会话用 `start_session` 开的都算；用户把它移到顶层（Detach to top level）后去掉。side chat 开出来时标题照抄父会话，第一轮就按本条改成自己的。
- 手法：用会话改名工具改（改本会话时 `session_id` 传 `"self"`；模型和 effort 用同组的 `get_session` 查，查不到 effort 就只写模型），改完不用特意汇报。

## Log 规范

写、改、检查任何 log 语句时自动触发 `logman`，按它的规范来。协议里不写格式细节：不同项目的日志形态不一样，写死会把别的项目的习惯带过来。

## 代码风格

动手写第一行代码之前，先找项目里的风格与格式配置，按它生成代码。至少看：格式化器配置（`.prettierrc*` / `prettier.config.*`、`.editorconfig`）、Lint 配置（`eslint.config.*` / `.eslintrc*`、`biome.json`）、风格文档（`codeStyle.md`、`CONTRIBUTING.md` 之类）。

**这些配置是用户手工设定的标准，优先级高于「代码库现状」**（用户 2026-08-11 明确：配置是他手动设的，代码是 agent 写的，该向配置看齐）。现存代码不符合配置，说明的是代码欠格式化，不是配置写错了：不要反过来推断「多数文件是 2 空格所以应该用 2 空格」，也不要去改配置迁就现状。

配置与现状冲突时：按配置写新代码；要不要顺手格式化存量，问用户。项目里没有任何这类文件，才按通用习惯来，且不强行套用其它项目的规则。

## 长任务与额度（用户 2026-11-22 设立）

**任何任务都不因额度缩水**（用户 2026-11-24 设立）：不管用户有没有说「这是长任务」，都不得因为额度不够、快撞额度、想赶在撞额度前做完，或任何别的原因，就缩减性能（换低一档的模型、调低 effort）、减少步骤、少派 agent。宁可做好撞额度的准备：照下面「每段做完就落盘」「快到额度时」「恢复后」做，撞了就停在那里，额度恢复了从下一步接着做。

用户说「这是长任务」（或「可能撞额度」「撞额度就挂起，恢复了接着做」）时，**开工前就按会被额度打断来安排**，额度恢复后自己接着做，不等用户再说「继续」。

- **开工前**：把任务拆成几段，每段做完都能单独落地。在任务自己的说明文档开头写一行「进度」：做到哪、下一步做什么、恢复时要先拉起什么。说明文档按上面「文档维护规则」放；**不写会话存档**，存档只在用户开口时写。
- **每段做完就落盘**：本段的改动提交（或至少暂存），进度行跟着更新，随时被打断也不丢活。超过 2 分钟的命令放后台跑。
- **快到额度时**：先把进度行补到别人照着就能接上。再用宿主的定时唤醒（Claude Code 里是 `ScheduleWakeup`、`CronCreate` 或计划任务）约一次额度恢复后的唤醒，提示词写「读进度行，从下一步接着做」。用量能查就查（会话用量工具），查不到就每段做完估一次。
- **恢复后**：先读进度行，再把挂起时被宿主停掉的东西重新拉起来（开发服务器、后台任务、浏览器标签页），然后从下一步接着做，已经落盘的段不重做。
- **报告里写一句**：中途被打断过几次、各从哪里接上。

> 为什么：额度用完时会话会被挂起，宿主还会停掉开发服务器这类后台进程。没留进度的长任务恢复后要从头摸索，用户还得守着说「继续」。

## 报告规范

**每一轮任务结束都给详细报告**（用户 2026-10-16 定）。报告义务不扩大用户请求的任务范围，也不自动授权破坏性操作、外部发布或其他需要单独授权的动作。

1. 自主完成全部工作，中途不停下等确认（破坏性操作除外）。
2. 报告覆盖：做了什么、为什么这么做、遇到的问题与处理、验证结果。
3. 每轮的回复都用 `annotated-report` 做成可批注的页面、发布成 artifact，会话里只给链接和结论，方便用户批注验收；没改文件的回合也出页（用户 2026-10-16、10-25 定）。用户要求时才直接在会话里答。
4. 代码修改逐文件展示实际代码（写在报告页里）：
    - 每个改动文件一节：文件路径 + 这个文件为什么要动。一两行的小改动也贴；新文件或新函数贴核心代码全文；样式改动贴关键 CSS 规则；删除 / 移除贴被删的原文，移动代码贴「从哪删、加到哪」两侧。
    - 行文节奏是一句话 → 一段代码 → 一句话 → 一段代码（用户 2026-09-09 设立），不要「一大段叙述 + 末尾一个代码块」。判据：读者不看仓库、只读这份报告，能不能说出每一处改动改了哪一行、为什么。
    - 贴重点代码，不倾倒全文：每个文件挑真正承载这次改动的那几行，用 `-` / `+` 标出前后差别，上下文超过三五行用省略号收掉；改动多到贴不完时，按「这次的结论靠哪几行成立」排序先贴，其余列清单。
    - 术语顺手翻成人话（用户 2026-10-06 设立）：不说「壳」，说「响应体外面那层 `{success, data, errorCode}`」；壳 / 归类 / 透传 / 预签名这类写代码时的速记，对读报告的人就是密码。
5. 每条 command 都说明为什么执行（shell、git、构建等）；批量同类命令可合并说明一次。
6. 文档修改（`.md` 等）同样展示：改了哪个文档的哪一节，贴出新增 / 修改的关键段落原文（直接改不用事前确认，事后必须展示）。

> 发出每一轮回复前自查三条（用户 2026-09-10 点名：最典型的漏法是只用文字交代、没把代码贴出来）：
>
> 1. 这一轮动过的每个文件，报告里是不是都有一节？（含只改了一两行的、含删除、含 `.md` 文档）
> 2. 每一处改动是不是都有实际代码块？（表格 / 要点 / 摘要不算，删除要贴被删的原文）
> 3. 每个代码块前后是不是各有一句话——前说「这段干什么」，后说「为什么这么做 / 原来会怎样、现在会怎样」？
>
> 有一条答不上，这轮报告就还没写完。该省的是叙述，不是代码。

**side chat 不出详细报告**（用户 2026-11-01 定）：本会话是 side chat 时（判据见「会话标题」），用户来问多半是对主会话有疑问、或者看不懂主会话的报告。这时不按本节出页，直接在会话里按问的问题快速回答：先用人话答、举个简单的例子，最后写你想补充的（总结、推荐做法、查到的问题都行）。side chat 里真改了文件，回答末尾列出改了哪些文件、各用一句话说改了什么。

## 提交、推送与合并

**每轮做完就提交并推送；在 worktree 里接着开 PR，三条校验过了就合并；提交只管自己那份**（用户 2026-08-11 设立，2026-11-15 定为每轮都推）。这样用户批注报告的同时就能在线上测试和 review。「集成分支」以 `ai/PROJECT.md` 的分支规则为准（各项目不同，如 `dev` 或 `main`）；项目开工红线对推送、合并另有限制的（如某条分支只能经 PR 进入），按红线走。

只提交本会话自己改的文件：

- 逐个 `git add` 自己改的路径，不用 `git add .` 或 `git add -A`；别的会话或用户改的文件禁止提交。判不准某个文件是不是自己改的，就问，不要猜。
- 自己和别人的改动落在同一个文件里、git 拆不开时，可以整文件提交，但 commit message 里必须说明哪些是本会话做的、哪些是搭车进来的、为什么拆不开。
- 发现主检出、其他分支或同一个文件里有并行任务的内容时，保留原状，不 reset、不覆盖。
- 用户说了「先不要推送」：不推也不合，停在本地提交，并在报告里写明停在哪一步。说了「先不要合并」：照常推，不合。「先不要推送」从用户说起，管到用户说可以推为止；不跨会话继承。

> 为什么：多个会话会并行改同一个仓库。把别人的工作卷进自己的 commit，commit message 就与内容对不上，要回退时也拆不开，推上去还会把别人尚未完成的中间状态带上远端。本项目踩过：一次 `git add -A` 卷入了他人的改动。

在 worktree 里，合并只走 rebase，不切分支（用户 2026-08-20 设立，2026-09-10 改了合并这一条）：

- 自主执行，不用问：在本 worktree 自己的分支上 commit、`git push` 这条分支（推的是自己的分支，不碰共享分支）、`gh pr create --base <集成分支>`、`gh pr merge --rebase`。合并的前提是下面三条校验全过；CI 绿即可合，不必等人审。
- 合并方式：单分支 PR 一律 rebase；只有环境分支之间同步（如 dev → staging）才用 `--merge`（用户 2026-10-17 定）。禁止 `--squash`（把一条分支上几件事压成一个提交，日后 `blame` 只剩一句概述）、`--admin`（绕过检查）、`--auto`（合并发生在没人看着的时刻）。例外：平台生成的 `agent/*` 分支按 `ai/PROJECT.md`「分支与合并硬规则」用 squash。
- 不加 `--delete-branch`：它会在本地切 base 分支——主检出占着集成分支时报假失败（PR 其实合了），没占着时把本 worktree 骑到集成分支上。合完手动 `git push origin --delete <branch>`。
- 禁止 `git checkout` / `git switch` 到别的分支，禁止把工作区分支 `reset` 到别处；需要知道上游进展时用 `git fetch` 拿信息。主检出（非 worktree）不切分支、不 reset、不在里面提交——那是别的会话的工作台，唯一例外是下面的快进脚本。
- 需要 rebase 或强制更新自己的功能分支时，只能用 `--force-with-lease`，不得强推共享分支。

合并前三条校验，缺一不合（三条里「没有 CI 时怎么办」那几句是用户 2026-11-15 定的）：

1. **CI 跑在当前 head 上**：按 sha 直查 `check-runs`（`gh pr checks` 会把旧 head 的绿报成通过）。这次 PR / 推送没触发 CI 的，不用等。
2. **不落后集成分支**：落后就先 `git rebase origin/<集成分支>`、`--force-with-lease` 推，再等新 head 的 CI（文本不冲突 ≠ 能编译）。这一条有没有 CI 都要查。
3. **集成分支自己是绿的**：它最新提交带 CI 状态且是红的，先查清修好再合（那是目标分支的问题，改动叠上去只会掩盖它）；没有 CI 状态就不查。

合完：核对 `state=MERGED`；看一眼 `git worktree list`，自己那行不该变成集成分支；再跑 `bash ai/scripts/sync-main-checkout.sh` 把主检出快进到最新（用户 2026-11-15 定）。桌面版的 worktree 会话从主检出读技能、设置与钩子（CLI 只在 worktree 没有技能目录时回落到主检出），主检出落后就读到旧版。这个脚本只在主检出干净、在集成分支上、能快进时动手，否则只报告。

> 为什么：worktree 存在的意义就是「我这条线的改动不影响别人」，切分支会改动共享检出的状态、打断并行会话。合并本身不禁——集成分支只能经 PR + 校验进入，三条校验就是那道门；禁的是绕门（`--admin`）、不看着门（`--auto`）和把历史压扁（`--squash`）。
