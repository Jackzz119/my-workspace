# Codex Agent 工作协议

## 🔴 本文件的修改授权（2026-09-10 用户设立）

**未经用户明确授意，不得修改本文件（`AGENTS.md`），也不得修改 `CLAUDE.md`。**

- “授意” = 用户在当前对话里明确说了要改这份协议（“在 agents 文档里加一条…”、“把这条规则改成…”）。
  从别处推断出来的都不算：任务里顺手发现规则写得不好、其他文档改了想同步过来、
  自己觉得某条已过时——一律**先说出来问，不要动手**。
- 改完必须在报告里贴出改动原文（增/删/改哪一节），与代码改动同等待遇。
- **`CLAUDE.md` 与本文件是一对**：本文件改了什么，`CLAUDE.md` 要等义跟改，只允许在
  「两个 agent 的机制不同」这一点上分方言。反之亦然。

> 为什么：这份文件是每次对话的开场规则，改错一句会静默影响之后所有 session，
> 而它 gitignored，改动不进 git 历史、没有 diff 可查、也没有 PR 可以回退。

## 规则来源与优先级

- 本文件是 Codex 在本项目中的工作协议，由根目录 `CLAUDE.md` 等义改写而来，两者规则完全一致，
  只有取用技能的方式按各自 agent 的机制不同。
- 通用技能登记在本文件「Skill 系统」节；**本项目专属技能登记在 `ai/JASKILL.md`**；
  项目特有的强制前置动作在 `ai/PROJECT.md`「开工红线」。三份都要在开工前读。
- 系统、开发者和用户在当前对话中的明确指令优先于本地文件；其余情况下严格执行本文件与上述三份。

## 上下文准备

每次对话开始时：

1. 读取 `ai/PROJECT.md` 和 `ai/TODO.md`，将项目现状和任务列表纳入上下文。
   `ai/PROJECT.md` 的「开工红线」一节是本项目的强制前置动作，必须读到
2. 通用技能登记在本文件「Skill 系统」节；**完整读取 `ai/JASKILL.md`** 拿本项目专属技能。
   Codex 没有自动注入机制，这一步必须自己动手打开文件，不能假定它已在上下文里
3. 需要确认本地实际装了哪些技能时，列一次 `.agents/skills/` 目录与登记表核对
4. 遇到对应场景时，**必须按登记表打开对应技能的 `SKILL.md` 并执行**，不要重新发明已有规范
5. **不要读 `ai/sessions/`**：那是手动会话存档，只在用户点名某个档时才读。开场不扫这个目录、不列有哪些档、不问要不要恢复——用户不提就当它不存在

## Skill 系统

### 真源与落点

技能本体只有一份，在 **`ai/jaSkills/`**，随仓库入库。两个 agent 的技能目录**各是一条指向它的整目录 symlink**（不是按件链接）：

```text
ai/jaSkills/<skill>/          ← 唯一真源，改这里
├── SKILL.md                 必需：入口指令 + frontmatter，控制在 500 行以内
├── reference.md             可选：详细规范，需要时才加载
└── references/ · rules/     可选：分篇资料

.agents/skills  →  ../ai/jaSkills     Codex 从这里发现技能
.claude/skills  →  ../ai/jaSkills     Claude Code 从这里发现技能
```

`.claude/` `.agents/` 和根目录 `CLAUDE.md` `AGENTS.md` 都在 `.gitignore` 里，**链接和协议都进不了仓库**，
新检出、新 worktree 里默认不存在。Claude Code / Codex 桌面版建的 worktree 会按仓库根 `.worktreeinclude`
把两份协议复制过来，但技能链接谁都不带；Multica、Codex CLI `--worktree`、手动 `git worktree add` 则什么都不带。

**worktree 开工第一步，先跑保底脚本**（归 `custom-skill` 管，重复执行安全）：

```bash
bash ai/jaSkills/custom-skill/scripts/sync-worktree.sh            # 补技能链接 + 协议文档，两个 agent 都补
bash ai/jaSkills/custom-skill/scripts/sync-worktree.sh --dry-run  # 只报告不动手
```

它做三件事：技能目录不存在就建整目录链接，已是非空真目录就按件追加（同名才替换）；根目录没有协议文档就从
主检出复制一份，已有就把主检出的内容追加在原文下面（再跑只更新那一块）；`ai/jaSkills/` 不在则报错停下，
把错误原文反馈给用户。

**要改技能就改 `ai/jaSkills/`**——技能目录是链接，从哪边改都是同一份；改完 `shelf push ai/jaSkills/<名>` 同步到货架。

### 调用方式（Codex 侧）

Codex 没有技能调用工具，“触发某个技能”就是**完整读取 `.agents/skills/<技能名>/SKILL.md`**
（等价于 `ai/jaSkills/<技能名>/SKILL.md`）并按其指令执行。技能正文是按 Claude 的机制写的，
读到这三类写法要自己翻译：

| 写法 | Codex 侧怎么办 |
|---|---|
| `` !`命令` `` | 不会自动执行，遇到就自己跑一遍那条命令，把输出当作它要注入的上下文 |
| `${CLAUDE_SKILL_DIR}` | 没有这个变量，按 `.agents/skills/<技能名>/` 代入 |
| `allowed-tools` | Claude 侧的预批准清单，Codex 侧忽略，按自身权限模式执行 |
| `$ARGUMENTS` | 调用时用户给的参数，自己代入 |

### Skill 对话规范

在 skill 上下文中回复时，**在回复开头标注 skill 名称**，像这个 skill 的“人”在说话：

```text
**INTJ** 好，我看了一下，你现在还有...
**VC** 当前分支状态如下...
**LOGMAN** 这行 log 格式有问题...
```

格式：`**SKILL名称（全大写）**` + 空格 + 正文。

## 文档维护规则

### 职责分工（哪份文档装什么）

- **PROJECT.md**：记录项目结构、已完成功能的详细描述、数据库表结构等技术细节，以及 Brain Dump 想法区
- **TODO.md**：持续跟踪所有待办和已完成条目，是任务的唯一来源
- **features/**：一个功能一份的实施文档，装实现细节、Subtask 进度、边界情况与测试记录
- **sessions/**：会话存档目录，一个会话一份，文件名 = 会话标题（手上这件事 / 关键决策 / 下一步 / 别踩的坑），由 `intj` 维护，不入库。长期为真的东西一律归 PROJECT.md，待办一律归 TODO.md，存档只留续接所需的最小上下文。**全程手动**：用户说存才存、点名才读、说删或问过才删

**本文件只定义“哪份文档装什么”。怎么写、什么时机写、谁来写，归对应的 skill：**

| 文档 | 归谁管 | 到哪查规则 |
|---|---|---|
| `ai/TODO.md` · `ai/PROJECT.md` | `intj` | Brain Dump 流、写入时机、写什么不写什么、执行顺序 |
| `ai/features/*.md` | `intj` + `feature` **共管** | `feature` 管**细节**（目标、链路、Subtask、测试）；`intj` 管 PROJECT.md 里的**摘要与索引**、TODO 同步 |
| `ai/sessions/` | `intj` | 两条铁律（手动存、点名读）与存档模板 |

Codex 侧没有自动加载，要用哪条规则就**去读那个 skill 的 `SKILL.md` 全文**。本文件不再抄一份——
抄了就会有两套流程各自漂移。

## 命名规则

新建文件、文件夹或文档前，**先扫描当前项目已有的命名模式**，遵循它，不要凭习惯套用其他项目的规则。

需观察的维度：

- 文件夹大小写（全小写 / PascalCase / kebab-case）
- 文档（`.md`）命名风格（全大写 / 全小写 / 混合）
- 代码文件命名（camelCase / snake_case / kebab-case）
- 是否有 `codeStyle.md`、`.editorconfig` 等明确规范文件

如果同一类目内存在多种风格，挑**多数派**或**最近新增**的那种；不确定时先问用户。发现历史遗留不一致的，不擅自扩大修改范围；若确有必要，先说明再处理。

## 语言规则

默认使用**中文**与用户沟通。必要时（如代码术语、英文原文引用等）可穿插其他语言。

## 会话标题

**每当这个 session 开始做一件新的、和当前标题对不上的事，就主动把会话标题改掉**（2026-09-10 用户设立），
不等用户开口。判据：用户扫一眼标题列表，能不能说出这个 session 现在在干什么。

- **触发**：接到新任务 · 任务性质转向（从“调查 X”变成“修 Y”）· 原标题已经名不副实
- **不触发**：同一件事的正常推进（写完代码去跑测试、开完 PR 等 CI）——标题不必跟着每一步动
- **写“在做什么”，不写“做完了什么”**：短名词短语并带上对象。
  `技能真源统一到 ai/jaSkills` 好过 `更新文档`；`Data Hub 404 排查` 好过 `修 bug`
- **手法**：Codex **有**会话改名机制，但它是 client 侧动作，agent 的工具清单里没有改名工具
  （实测 codex-cli 0.154.0：`/rename` 斜杠命令 · `codex agents` 里的 rename 键位 ·
  底层 app-server 的 `thread/name/set` / `ClientRequest::ThreadSetName`；而 model 能调的
  handler 只有 apply_patch / plan / view_image / request_user_input 那一组，没有改名的）。
  所以这条规则在 Codex 侧的动作是**把标题算好、提醒用户按一下**：

  > 【建议改名】`技能真源统一到 ai/jaSkills` —— 打 `/rename` 回车即可（它也能从对话自动生成建议）

  不要写成「已更新标题」——你没有权限做这件事，写了就是假交付。
- **非交互场景**（`codex exec`）没有斜杠命令，退而在该轮输出第一行写
  `【本轮任务】<短名词短语>`，让用户翻记录时同样能一眼定位。
- **想让 agent 自己改**：通过 MCP 或 plugin 暴露一个包 `thread/name/set` 的工具，
  接上之后本条规则改回「直接改，不提醒」。

## Log 规范

**归 `logman`。** 标签格式、功能域标签怎么选、运行时环境标签、分级与 Pro 屏蔽策略、写 log 检查清单，
都在 `ai/jaSkills/logman/`（SKILL.md + reference.md）。

写、改、检查任何 log 语句时**先读 `.agents/skills/logman/SKILL.md`**，按它的规范来。
本文件不重复格式细节——不同项目的日志形态不一样（有的分级、有的不分），
写死在协议里会把别的项目的习惯带过来。

## 代码风格

**动手写第一行代码之前，先找项目里的风格与格式配置，按它生成代码。** 至少要看：

- 格式化器配置：`.prettierrc*`、`prettier.config.*`、`.editorconfig`
- Lint 配置：`eslint.config.*`、`.eslintrc*`、`biome.json`
- 风格文档：`codeStyle.md`、`CONTRIBUTING.md` 等

**这些配置是用户手工设定的标准，优先级高于“代码库现状”。**
现存代码不符合配置，说明的是代码欠格式化，不是配置写错了。不要反过来推断“多数文件是 2 空格所以应该用 2 空格”，也不要改配置迁就现状。

配置与现状冲突时：按配置写新代码；要不要顺手格式化存量，问用户。项目里没有任何这类文件，才按通用习惯来，且不强行套用其他项目的规则。

## 代码修改规则

**未经用户明确说“帮我改”之前，不直接修改代码。**

分析阶段应：

1. 说明要改哪里、为什么这么改
2. 展示改动的代码片段
3. 等用户确认后再动手

用户已经明确要求修改时，不重复索要确认；按授权范围直接完成并验证。

## Full Access 模式报告规范

Codex 界面处于 **Full Access** 模式时，**每一轮任务结束都必须给详细报告**，无需用户额外声明或每次重申。

> Full Access 在本项目中同时触发本节的报告义务，但不扩大用户请求的任务范围，也不自动授权破坏性操作、外部发布或其他需要单独授权的动作。

> 🔴 **这条最常被忘（2026-09-10 用户点名强调）。**
> 最典型的漏法不是“完全没报告”，而是**改完东西只用文字交代，没把改动的代码或文档原文贴出来**——
> 尤其是活干得多、报告写长了的时候，越容易省掉贴码只留叙述。
>
> **发出每一轮回复前，先自查这三条**：
> 1. 这一轮**动过的每个文件**，报告里是不是都有一节？（含只改了一两行的、含删除、含 `.md` 文档）
> 2. 每一处改动是不是都有**实际代码块**？（表格、要点、摘要**不算**，删除要贴被删的原文）
> 3. 每个代码块前后是不是各有一句话——前说“这段干什么”，后说“为什么这么做 / 原来会怎样、现在会怎样”？
>
> 三条里有一条答不上，**这轮报告就还没写完**，不要发。
> “怕报告太长”不是省略的理由——该省的是叙述，不是代码。

1. 自主完成全部工作，中途不停下等确认（破坏性操作除外）
2. 报告必须覆盖：做了什么、为什么这么做、遇到的问题与处理、验证结果
3. **代码修改必须逐文件展示实际代码**，不能只写文字描述：
    - 🔴 **行文节奏：一句话 → 一段代码 → 一句话 → 一段代码。**（2026-09-09 用户设立）
      每段代码前一句话说“这段是干什么的”，后一句话说“为什么这么做 / 原来会怎样、现在会怎样”。
      **不许出现“一大段叙述 + 末尾一个代码块”，更不许只叙述不贴码。**
      判据：读者不看仓库、只读这份报告，能不能说出每一处改动改了哪一行、为什么。
    - 🔴 **贴的是“重点代码”，不是全文倾倒**：每个文件挑真正承载这次改动的那几行，
      用 `-` / `+` 标出前后差别；上下文超过三五行就用省略号收掉。
      改动多到贴不完时，按“这次的结论靠哪几行成立”排序，先贴那几行，其余列清单。
    - 🔴 **报告直接写在 session 里，不另外生成 markdown 文件**（2026-09-09 用户设立）。
      只有长到 session 里读不动时才落盘，且要说明为什么落盘。
      “怕报告太长”不是省略代码的理由——省的应该是叙述，不是代码。
    - 每个改动文件一节：文件路径 + 这个文件为什么要动
    - 关键改动贴**改动前 → 改动后**的代码对照（新文件或新函数贴核心代码全文），每处配一句“为什么这么改”
    - 一两行的小改动也要贴出那几行；样式改动贴关键 CSS 规则
    - **删除或移除也是代码改动，必须贴出被删的原文**；移动代码同理，贴出“从哪删、加到哪”两侧
    - **禁止用表格、要点或摘要替代代码块**：表格可作索引，但每处改动仍必须有对应的实际代码块
4. **执行的每条 command 都要说明为什么执行**：批量同类命令可合并说明一次
5. **文档修改也要展示改动内容**：列出文档与章节，贴出新增或修改的关键段落原文
6. **提交只管自己那份，且默认不推送**：

    | 动作 | Full Access 模式下的默认 |
    |---|---|
    | commit **本 session 自己改的**文件 | ✅ 自主执行 |
    | commit **别的 session / 用户**改的文件 | ❌ 禁止 |
    | `git push` | ❌ 禁止，除非本 session 用户明确授权自动推送 |

    - 同文件混杂时可以整文件提交，但 commit message 必须说明哪些是搭车内容以及为什么拆不开
    - 推送授权只在当轮有效，不跨 session 继承
    - 判不准某个文件是不是自己改的，就问，不要猜

7. **在 worktree 里工作时：合并只走 rebase，不切分支**（2026-09-10 合并行按 `ai/PROJECT.md`「分支与合并硬规则」改）：

    | 动作 | worktree 中的默认 |
    |---|---|
    | 在本 worktree 自己的分支上 commit | ✅ 自主执行 |
    | push 本 worktree 自己的分支 | ✅ 自主执行 |
    | 创建 PR（base: dev） | ✅ 自主执行 |
    | **`gh pr merge --rebase`** | ✅ 自主执行，**前提是下面三条校验全过**。CI 绿即可合，不必等人审 |
    | **`gh pr merge --squash` / `--admin` / `--auto`** | ❌ **禁止**。squash 把一条分支上几件事压成一个提交，日后 `blame` 只剩一句概述；`--admin` 绕过检查；`--auto` 让合并发生在没人看着的时刻 |
    | **`--delete-branch`** | ❌ 别加。它会在本地切 base 分支：主检出占着 `dev` 时报假失败（PR 其实合了），没占着时把**本 worktree 骑到 `dev` 上**。合完手动 `git push origin --delete <branch>` |
    | checkout / switch 到别的分支 | ❌ 禁止 |
    | 把工作区分支 reset 到别处 | ❌ 禁止 |

    - **合并前三条校验，缺一不合**：
      ① CI 跑在**当前 head** 上——按 sha 直查 `check-runs`，`gh pr checks` 会把旧 head 的绿报成通过；
      ② 不落后 `dev`——落后就先 `git rebase origin/dev`、`--force-with-lease` 推，再等**新 head** 的 CI（文本不冲突 ≠ 能编译）；
      ③ `dev` 自己是绿的——红了先修 `dev`。
    - 合完核对 `state=MERGED`，再看一眼 `git worktree list`——自己那行不该变成 `[dev]`
    - 需要知道上游进展时用 `git fetch` 获取信息，不 reset、不 checkout
    - 主检出（非 worktree）的分支状态不碰，那可能是别的 session 的工作台

    > 为什么：worktree 存在的意义就是“我这条线的改动不影响别人”。切换分支会改动共享检出的状态，
    > 把隔离作废，正好打断并行 session 正在做的事。**合并本身不再禁**——`dev` 受保护、只能经 PR + CI 进入，
    > 三条校验就是那道门；禁的是绕门（`--admin`）、不看着门（`--auto`）、和把历史压扁（`--squash`）。

## 并行工作区保护

- 任何时候都只提交本任务自己的文件；不用 `git add .` 或 `git add -A`
- 发现本地主检出、其他分支或同文件存在并行任务内容时，保留原状，不 reset、不覆盖
- 需要 rebase 或强制更新自己的功能分支时，只能用 `--force-with-lease`，不得强推共享分支
- 合并前按上表的三条校验走（当前 head 的 CI、不落后 `dev`、`dev` 自身绿），合并后核对 `state=MERGED` 与 `git worktree list`
