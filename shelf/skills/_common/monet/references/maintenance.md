# 常驻设计文档与清理

## 信息归属

| 载体 | 维护内容 |
| --- | --- |
| 项目 `design-system.md` | 全局风格、已采用设计目录、常驻子文档链接、实际素材来源、关键边界 |
| 领域 Markdown | 角色、建筑/场景、物件、效果等项目实际存在的类别；图片、描述、交互/动画、当前状态和素材/实现链接 |
| `uiux` 常驻 Markdown | 已敲定 UI/UX 全图、主题/组件、状态、输入与导航流程及选定展示；注明实现状态，UI Tailor 主维护，Monet 总审 |
| README | 目录、怎样阅读/更新/检查，不再复制当前风格 |
| concept | 当期的整体构想、深化稿、脑暴与未来设想；当期被否决的方向只留一句理由，旧期方向移档 |
| 设计系统根下的 `codex-visual/` | 当期调研、候选、比稿、待确认原型；确认后只把最终规范和展示晋升到对应定稿文档，定案的比稿移档或删除 |
| 项目美术档案目录（位置登记在 design-system） | 上一期的旧概念、旧稿、旧素材与历史 UI 稿；按期分文件夹，只留一期，不作开发参考源 |
| session | 本轮做了什么、回归结果、排障与进度；默认不新建 report 文件 |

目录与领域文件名沿用项目约定。只给实际存在的类别建常驻文档，不预建空的角色/建筑/CG 页面。项目文件放项目的 `ai` 文档区；项目数据不写入任何 skill 的 SKILL、references、decisions 或配置。

## 采用设计最小展示

名字/用途与状态 → 实际图片或动态示例 → 风格和关键特征 → 用户如何交互或它如何动画 → 原素材/编辑源/运行时/实现的已核实链接。无动作的设计可写静态；只有计划时说明未实现。用运行图验证采用状态，生成稿只能作为设计参考。

首次定位素材库后，将发现的位置写进 design-system 的来源表，后续改路径时同步引用；不要假设素材总在某个文件夹。tokens 指颜色/间距/材质等设计变量：有真实源则链接它，只有确有维护需求才拆独立文档，不默认创建空的 tokens.md。

## 每次更新与阶段清理

1. 同步当前设计和受影响子文档，确保根文档能沿链接找到全部采用项；当前文档之间互链，不复制两份规则。
2. 验证图片/动画可显示、素材/实现位置存在、状态描述符合现状；静态截图不能证明动态行为。
3. 整理不再生效的附属文档：将独有且仍有用的结论并入常驻文档或研究，将否决理由留 concept。已无独有价值的旧报告、重复说明、临时截图/迁移脚本按任务授权清除。
4. 同一期内不按文件年龄删资料；仍被当前设计、生产工具或有价值研究引用的素材先处理依赖。只读任务只提出清理清单与待更新内容。
5. 输出回归结果到 session。必要测试夹具/原始检查数据可留专用工具目录，避免每轮在设计系统堆一份报告。

## 换期与档案（用户定规）

设计系统只放最新一期，是概念与 UI 在内所有美术开发的参考源。「期」是用户认可的一次整体方向更换（产品定位、画风或角色体系换代），不是一次普通改版。

1. **新一期定下时盘点设计系统**：当期采用的内容改写为当前规范；上一期的概念、调研、比稿、历史 UI 稿移到档案目录；两期以前的资料尽量删除。移动或删除前先更新仍引用它们的代码注释、脚本与文档。
2. **档案按期分文件夹**，每期一份索引 README，写明期名、时间段、内容，以及下一次换期时整期删除。开发和审核不从档案取规范。
3. **仍在运行的上一期素材**等新设计替换后再移档或删除；替换前在来源表标明「上一期，替换中」。
4. **原始生成批次不进设计系统**：草稿、未选图和工具日志留在本地或临时目录；定稿图（可压缩为高质量位图）、提示词与制作注记整理后入库。
5. 仍然有效的旧规则（用户定规、制作铁律、验收门槛）先并入当期常驻文档，再移档，不随档案一起失效。

## 可选跨设备展示

Markdown 是唯一人工维护的设计来源。需要网页时用同一生成过程读取当前文档与资源，更新同一个展示文件；导航和图片在小屏可读、路径适合发布。沿已获授权的发布渠道更新原入口，核验实际地址，报告发布范围。不要自行公开私人截图，也不因讨论这种能力就自动发布。
