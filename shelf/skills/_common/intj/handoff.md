# intj · 交接档（handoff）

> 按需读取：写交接档、派发、执行或归档时打开。两条铁律与执行规则在 `SKILL.md`「会话存档与交接」常驻；列档、读档、删档的通用流程在 `savepoint.md`，这里是交接档自己的格式与流程。

交接档是会话存档的一种：把一件**用户定了要做、但本期 / 本会话不做**的活，写给另一个 agent——它新开会话、只读这一份就能开工。
写交接档、派发、归档的一方下称**派发方**；收到交接去做的 agent 下称**执行方**。

## 一、什么时候写，和别的文档怎么分

- **只在用户开口时写**：用户说「交接」「写交接」「交给别的 agent」「派给别人做」「handoff」，或说要安排别的 agent 做。用户没开口，就不提交接这件事（铁律一）。
- 只说「交接」、分不清是交给别的 agent 还是自己换会话续接 → 问一句。换会话续接写存档（`savepoint.md`）。
- 用户说一批活都要交接时，一包一份，外加一份索引。

| | 交接档 | 存档 | 功能文档 | TODO |
|---|---|---|---|---|
| 给谁看 | 另一个 agent，新开会话（本机会话或云端 run） | 换个会话接着做同一件事的人 | 以后所有碰这个功能的人 | 所有人 |
| 装什么 | 一件还没做的活：设计、证据、已定与未定的事、改动范围、验收，写详细 | 还没落盘的会话状态，≤ 40 行 | 功能现状与实现细节 | 没做完的事，一条一行 |
| 何时写 | 用户说要交接时 | 用户说「存档」时 | 开发过程中 | 出现待办时 |
| 何时删 | 合入后归档，问过用户（第五节） | 那件事做完、问过用户 | 不删，随实现改写 | 做完即删 |

- 交接档写的是**将要做**的设计，所以写的是计划；功能文档与 PROJECT 只写做完的现状（SKILL.md「写入时机」）。做完以后，长期为真的结论改写进功能文档 / 规范，交接档删掉。
- 写之前先把能落盘的落掉：用户定了的事进决定清单拿 `ADR-N`，要用户拍板的进待拍板拿 `D-N`（SKILL.md「决定与待拍板」），TODO 里加一行指向交接档（一批可以合成一行指向索引）。交接档引编号，不替代这几份。
- 派发状态只记一处：走派单系统（如 Multica）时跟在 issue 上，索引不另记；没有派单系统时记在索引。TODO 和交接档里都不写。

## 二、放在哪、叫什么

```text
ai/sessions/
├── savepoint/                   ← 会话存档（见 savepoint.md）
└── handoff/
    ├── 00-索引.md               ← 交接索引 + 给派单的人（lead）的交接 + 状态，只列还没归档的
    ├── <一眼看懂的主题>.md       ← 一包一份
    └── img/<文档名去掉 .md>/     ← 这份交接档用到的图（压缩后的）
```

- 主题写清做什么和对象，例如 `亮色输入框描边.md`、`注单查找与筛选分区.md`、`loading与错误边界.md`；不写 `UI修复3.md` 这种看不出内容的名字（目录已经说明是交接档，文件名不再加「交接-」前缀）。
- 文件名的处理同存档：空格转连字符，去掉 `/ \ : * ? " < > |`，中文照常保留。
- 一包只写一份。几包改同一批文件、必须按顺序做的，在索引里排成先后两个 stage，或者合成一包分节写。
- 交接档要入库。派给云端 run 之前，交接档和它的图要已经在执行方检出得到的分支上（通常是合进集成分支）——云端工作区从远端分支建，只在本地或别的分支上的档，执行方读不到。
  在 worktree 里写的，同样随本分支的 PR 合进去。

## 三、交接档的格式

七节，顺序固定。写的标准只有一条：**执行方不看原会话、不读任何不入库的文件，也能独立做完**。
会话里说过的、报告里写过的、评审补出来的，凡是做这件事用得上的都写进来，不遗漏。交接档不受存档 40 行的限制，要写详细。

```markdown
# 交接：<做什么 + 对象>  (写于 YYYY-MM-DD)

## 1. 交接块

- **怎么用这份档**：这是一份交接档，读这一份就能开工。先读完本块与执行规则；第 4 节的待调研 / 待拍板先做或先问；
  再按第 3 节设计、第 5 节范围、第 6 节验收去做；完成报告单列「与交接相比改了什么、为什么」。派发状态看 `00-索引.md`。
- **来源**：<运行目录或会话 / 报告 §N>；用户原话（<日期>，<哪一轮批注或对话>）：「……」
- **要做的事**：<一两句>
- **已定的事**：<一句结论>（ADR-N）；……
- **不在范围内**：<不做的事> —— <去向：另一份交接档 / TODO / 不做>
- **开工前的调研方向**：<先核实什么、查哪方面的当前最佳实践、对照哪份规范；第 4 节逐条展开>
- **执行规则**：<SKILL.md「会话存档与交接」里执行规则的原文，一字不改>

## 2. 背景与问题

## 3. 详细设计

### 3.1 推荐方案

### 3.2 被否的方案

### 3.3 评审补出的坑

## 4. 待调研 / 待拍板

| # | 问题 | 已知 | 建议 | 不定时的默认 |
|---|---|---|---|---|

## 5. 改动范围

## 6. 验收

## 7. 参考
```

各节写到什么程度：

1. **交接块**：执行方只读这一节，也知道怎么用这份档、做什么、不做什么、哪些不能自己改、开工前先查什么。
   - 来源写到能定位：运行目录、报告的哪一节、用户原话的日期与出处。原话照录（只摘和这件事有关的句子），不转述。
   - 已定的事每条一句结论 + `ADR-N`；只是确认现状、没进决定清单的，写明谁何时确认。
   - 不在范围内的事逐条写，并写去向——执行方顺带做掉范围外的改动，是交接最常见的走样。
   - 开工前的调研方向写成几条可执行的「先查什么」：哪段代码要先核实还在、哪类做法要查当前的官方建议或主流实现、要对照哪份规范的哪一节。
   - 执行规则原文照抄。用户派发时明说了「完全照做 / 复刻」的，在规则下面加一行写明是哪天、怎么说的。
2. **背景与问题**：现状什么样、为什么要改。证据给到能复核：截图、量测（数值 + 怎么量、在什么环境）、
   代码位置（`path:line`，再写一句那行是什么，行号漂了也找得到）、规范出处（文件 + §N）。
3. **详细设计**：
   - 推荐方案按改动逐处写：位置 → 改成什么 → 为什么。界面改动写到组件、状态、文案词条与尺寸，数据改动写到字段与迁移。
   - 被否的方案每个一行：方案 + 否掉的理由，免得执行方把走过的路再走一遍。
   - 评审补出的坑（互评、比稿、复核里查出的问题，与规范原文不符的说法）单列，写清怎么避开。
4. **待调研 / 待拍板**：写交接档时还剩的未知项一条不落。每条写问题、已知（查到哪一步）、建议、**不定时的默认**（没人回答时执行方先按什么做）。
   要用户拍板的写上 `D-N`；执行方自己调研就能定的，标「执行方调研」。
5. **改动范围**：要动的文件与组件、要加或改的词条（各语言）、要同步改的规范与它的分册、要跟着改的验收脚本或测试。
   列不全的写明「至少这些，执行方核实」。
6. **验收**：执行方照着就能自己验。
   - 量测：命令或步骤 + 阈值（如「1024 宽不折行」「对比度 ≥ 3:1」），以及在什么环境量。
   - 任务测试：场景 → 期望结果，按这件事挑边界（空数据、超长文案、无权限、两种语言、亮 / 暗主题等）。
   - 门禁：项目要求的检查（build / typecheck / lint / test 等）写成「包 × 检查」的小表，标明哪些必须过。
7. **参考**：入库的文件写仓库路径，外部资料写 URL，图按下一段的规则附上。

### 图与资源链接

做这件事要看的图、页面、资料都要附上，执行方不用回头找：

- **图**：压缩后放 `ai/sessions/handoff/img/<文档名去掉 .md>/`，正文用相对路径引用（如 `img/亮色输入框描边/01-对比度.jpg`）。
  长边 ≤ 1600 px、单张尽量 ≤ 300 KB；能出 WebP 用 WebP，不能就用 JPEG（质量 80 左右，macOS 自带的
  `sips -Z 1600 -s format jpeg -s formatOptions 80 <原图> --out <目标>` 就行）。压完打开看一眼，小字还要能读。
- **原件**：图或资料的原件不入库时（会话临时目录、未跟踪的截图、本机下载的附件），在引用处写原件的本机绝对路径，并注明「本机临时位置，可能已被清理」——压缩件才是执行方靠得住的那份。已经入库的图直接引用仓库路径，不复制。
- **外部参考**：给 URL（规范、官方文档、对标产品页面），并写一句从里面要看什么。需要登录才能看的，写明要什么权限。

### 写完自检

任一条答不上，就还没写完：

- [ ] 只读这份档和它引用的入库文件、URL，能不能做完？有没有「上面说的」「那个方案」这类离开会话就看不懂的指代？
- [ ] 引用的文件都入库了吗（`git ls-files --error-unmatch <路径>`）？图都在 `img/` 里，或本来就入库？不入库的原件写了绝对路径和「可能被清理」？
- [ ] 已定的事都带 `ADR-N`？不在范围内的事都写了去向？
- [ ] 每条待拍板都有不定时的默认？交接块里写了开工前的调研方向？
- [ ] 验收能照着执行：命令、步骤、阈值都在？
- [ ] 交接块里有「怎么用这份档」与执行规则原文？
- [ ] 索引登记了一行，TODO 有一行指过去？

## 四、索引与派发方案（`00-索引.md`）

索引只列还没归档的交接档。开头写派发方案，再一张表：

```markdown
# 交接：00 索引与派发方案  (写于 YYYY-MM-DD)

> 交接档的索引，规则见 intj 技能的 handoff.md。只列还没归档的；归档后整行删掉，过程留 git。
> 状态：待派 → 已派（填 issue 号）→ 进行中 → 已合入（填 PR）→ 归档。

## 派发方案

- <谁做哪几份、为什么：熟悉的模块、要用的技能>
- <stage：哪几份可以同时开，哪几份要等谁合入再派、为什么（文件重叠、依赖）>
- <开工前要用户拍板的：D-N + 一句话 + 不定时的默认>

## 交接清单

| 交接档 | 一句话 | 状态 | 派给 / issue | stage | 能否并行 | 文件重叠 | 开工前要拍板 | PR |
|---|---|---|---|---|---|---|---|---|
| [<主题>](<主题>.md) | … | 待派 | — | 1 | 能 | 与 <另一份> 都改 `<路径>` | D-N | — |
```

- **文件重叠要实查**：每两份交接档比一遍第 5 节的文件清单，有交集的写出交集；有交集的不放进同一个 stage 并行，除非派给同一个执行方按顺序做。
- **开工前要拍板**只列挡住开工的问题；不挡开工、有默认的留在交接档第 4 节。
- **索引是写给派单的人（lead）的交接**：人选、批次、并行与合单是建议，由 lead 按自己团队的情况定；不抄他已经熟悉的派单协议，只写他做决定需要的事实（文件重叠、依赖、开工前要拍板的、用户指定的期次标签与项目分类）。提醒他同一 scope 的包合成一张单，别开太多小单子耗算力。
- 派发说明（如 issue 描述）写一句目标 + 交接档的仓库路径，验收写「见交接档 §6」，不复述正文；执行方只读自己那一份交接档就能开工；用户说了「完全照做 / 复刻」的，写进派发说明。
  派发说明点名了这份档，执行方读它就是「点名才读」。

## 五、状态流转与归档

`待派 → 已派 → 进行中 → 已合入 → 归档`。走派单系统时这些状态就是 issue 的状态，索引不另记；没有派单系统时记在索引，由派发方更新：

| 状态 | 什么时候改 | 同时填 |
|---|---|---|
| 待派 | 交接档写完、在索引登记时 | — |
| 已派 | 派出去时（建了 issue 或开了会话） | 「派给 / issue」：执行方 + issue 号（如 Multica issue）或会话名 |
| 进行中 | 执行方开工后 | — |
| 已合入 | PR 合进集成分支后 | PR 号 |
| 归档 | 结论落盘、用户同意删之后（见下） | 整行删掉 |

执行方不改索引：几份交接并行时都改同一张表，PR 之间会互相冲突。执行方要回报的（开工、PR 号、与交接相比的变化）写在自己的报告里。

**归档**（派发方在 PR 合入后做；执行方的 PR 里已经做了的就跳过）：

1. 交接档里长期为真的结论改写进功能文档或规范的现状段落；用户新定的事进决定清单（`ADR-N`）；执行中冒出的待办进 TODO。
2. 问一句「交接档 xxx 已合入，归档删掉？」，用户同意再删（同 `savepoint.md` 删档：用户已经说了删、或授权你自己判断的，直接删，删完在报告里说明）。
   删的是交接档、它的 `img/` 目录、索引那一行，以及 TODO 里指向它的那一行；整批都归档了，索引也删掉。
3. 过程（交接原文、执行报告、与交接相比的变化）留在 git 历史与 PR 里，不另存。

## 六、收到交接后怎么开工（执行方）

1. **先读交接块**：怎么用这份档、要做什么、已定的事、不在范围内的事、开工前的调研方向、执行规则；再看派发说明里用户有没有明说「完全照做 / 复刻」。
2. **先清第 4 节**：调研项先调研，结论写进报告；拍板项能问就先问用户。派发说明写了按默认走、或问了没人答的，按「不定时的默认」做，报告里写明哪几条按了默认。
3. **按执行规则做**：没有明说照做，交接档的方案就是起点：先核实背景与证据还成立（代码可能已经变了），按调研方向查当前的最佳实践，可以改方案；标「已定」的要改，先问用户。
   明说照做的照做，做不到或不得不偏的地方照样报告。
4. **范围守在第 5 节与「不在范围内」**：范围外的发现写进报告或 TODO，不顺手做。
5. **按第 6 节验收**，把量测数值和门禁结果写进报告。
6. **完成报告单列「与交接相比的变化」**，没有变化也写「无」：

```markdown
## 与交接相比的变化

| 交接档里的做法 | 实际做法 | 为什么 | 依据 |
|---|---|---|---|
| <交接档 §3.1 的哪一处> | <改成了什么> | <理由> | <调研出处 / 量测 / 规范 §N / 用户原话> |

- 已定的事：<未改 / 问过用户后改了哪条，附用户原话>
- 第 4 节：<D-N 用户怎么答的 / 哪几条按默认做了 / 调研结论>
```
