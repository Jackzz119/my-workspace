## 合作者同步

### 指针是什么

`ai/SYNC.md` 里每个跟踪分支一个指针：**「ai/ 文档已经和这个 commit 对齐」**。
它不是「我们最后一次提交在哪」——我方自己的 commit 本来就由我方会话顺手更新文档；指针要守住的是
合作者的提交：指针之后的合作者 commit，都还没被读过、没被总结、没进文档。

跟踪的分支 = 主检出用来集成的分支（通常是 `main` 和/或 `dev`，以仓库实际为准）。
比较一律对 `origin/<分支>`，不对本地分支——本地主检出可能落后，而且主检出的分支状态不归 intj 管。

### `ai/SYNC.md` 模板

```markdown
# 协作同步指针

> 由 intj 维护。指针 = ai/ 文档已对齐到的 commit；之后的合作者 commit 都要读、总结、落进文档。
> 流程见 intj 技能 reference.md「合作者同步」。我方文档范围只有 ai/** 与根目录 CLAUDE.md / AGENTS.md。

## 我方身份

判定一个 commit 是不是我方的：作者邮箱命中下表算我方；作者是 bot / AI 署名（如 `noreply@anthropic.com`）时看提交者邮箱。

| 谁 | 匹配的邮箱 |
|---|---|
| <用户名> | <邮箱1>、<邮箱2> |

## 合作者

| 谁 | 邮箱 | 备注 |
|---|---|---|
| <名字> | <邮箱> | <负责什么、在哪个分支上工作> |

## 指针

```text
pointer.<分支> = <完整 40 位 sha>
```

<一句话：指针对齐时的状态，例如「<日期> 读完 <名字> 的 N 个 commit，文档已对齐」>

## 同步记录

| 日期 | 分支 | 范围 | 合作者 commit | 摘要 | 改了哪些 ai/ 文档 |
|---|---|---|---|---|---|
```

- 指针行必须是 `pointer.<分支> = <sha>` 这一格式，独占一行——SKILL.md 的状态速览用 grep 读它。
- 同步记录一次一行，只追加；超过 30 行时把最早的归档进 git 历史（删掉即可，git 里查得到）。

### 首次建立（`/intj collab init`）

1. **认身份**：`git log --all --format='%an <%ae> | %cn <%ce>' | sort | uniq -c`，把作者分成「我方」「合作者」「bot」。
   bot 署名的看提交者。拿不准的问用户，不猜。
2. **定分支**：`git fetch origin`，看 `origin/main`、`origin/dev` 谁是集成线（谁新、部署跟谁、PR 合进谁）。
3. **找基线**：最后一次「我方 ai/ 文档仍反映全部历史」的 commit——通常是合作者第一个 commit 的父提交
   （`git log --reverse --format=%H --author=<合作者邮箱> origin/<分支> | head -1` 再取 `^`）。
   基线之后若有合作者自己改过 `ai/` 的 commit，照样纳入本轮去读，不因为「他们改过文档」就跳过。
4. 写 `ai/SYNC.md`，指针先写基线，然后立刻跑一次完整同步。

### 一次同步（`/intj collab`）

**1. 取数**

```bash
git fetch origin                                              # 只更新远端引用，不碰工作区
git log --no-merges --format='%H %ae %ce %ad | %s' --date=short <pointer>..origin/<分支>
```

按「我方身份」分组。合并 commit 不单独读（`--no-merges`），但要注意合并引进来的合作者 commit 已在列表里。

**2. 只有我方 commit**：指针推到 `origin/<分支>` 的头，同步记录写「仅我方 N 个」，报告一句话。结束。

**3. 本地底子检查**（要改 ai/ 文档前）

```bash
git diff --name-only HEAD origin/<分支> -- ai/
```

非空 = 远端有本地没有的 ai/ 改动。停下问用户能不能把本地快进——否则文档改在旧底子上必冲突。
用户同意后只做 `git merge --ff-only origin/<分支>`（快进失败就停下交给 `vc`，不 merge、不 rebase、不 stash）；
快进前确认本地未提交的改动和这批远端改动不碰同一个文件。
空 = 本地落后的只是代码，可以直接改文档。

**改完文档再 fetch 一次**：读和改的过程中合作者可能又推了，新 commit 照同样流程读完再推进指针，不把没读过的 commit 算进去。

**4. 读改动**

- 先 `git show --stat` 每个合作者 commit，按主题归堆（后端 / 某功能 / 修复 / 部署 / 测试…）。
- 量小（≤5 个 commit 或 ≤500 行）自己读；量大按主题分给只读子代理并行读，每个子代理交回：
  ① 改了什么（用户看得到的效果 + 关键文件路径）② 我方 ai/ 文档里因此过期的说法（文件:行号 + 原文 + 应改成什么）
  ③ 合作者是否已经改过 ai/ 里相关文档、改全没有。
- 读的是 diff 本身，不是 commit message 的自述——message 说「修了 X」要在 diff 里看到。

**5. 总结给用户**（先说，后改）

按主题，每条一句「原来 → 现在」，然后单列三类：

| 单列 | 为什么 |
|---|---|
| 动了 `ai/` 或协议副本的 commit | 这是我方上下文，等于别人改了我们的规矩，必须让用户看见 |
| 与已有用户决定冲突的改动（例如改了某个已定的默认值） | 不能悄悄让文档跟着别人走；问用户以哪个为准 |
| 与我方进行中的工作撞车的改动（同一批文件） | 提醒后续合并要小心 |

**6. 对齐 ai/ 文档**

按 SKILL.md「文档更新规范」：功能细节进 `ai/features/`，PROJECT.md 写现状摘要并更新「最后更新」，
TODO.md 里被合作者做掉的直接删掉（做完即删；是谁、哪个 commit 记进 `ai/SYNC.md` 的同步记录），作废的删掉并在同步记录里写一句原因，新出现的待验收加进去。
冲突项不改，留在报告里等用户定。

**7. 推进指针**

文档改完才推：`pointer.<分支>` 改成本轮读到的 `origin/<分支>` 头，同步记录追加一行。
用户说「先不改文档」→ 指针不推，同步记录写「已读未落」，下次从原指针重读（读过的可以只看 stat 快速过）。

**8. 提交**：`ai/SYNC.md` 与文档改动按项目的提交规则交给 `vc`，不在这里自己 commit。

### 边界情况

- **合作者 force-push 改写了历史**，指针 sha 不在 `origin/<分支>` 上（`git merge-base --is-ancestor <pointer> origin/<分支>` 失败）：
  不要硬算范围。用 `git log origin/<分支> --since=<指针日期>` 找候选，拿给用户确认新基线。
- **合作者只在自己的分支上干活、还没合进集成线**：不跟踪（指针只看集成线）。用户问起再临时看 `origin/<她的分支>`。
- **跟踪的分支被弃用**（例如集成线从 dev 换成 main）：在 SYNC.md 删掉那条指针，同步记录里写一句。
- **合作者是 AI 署名但由合作者账号提交**：按提交者判，算合作者。
