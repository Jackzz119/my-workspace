# intj · 文档更新细则

> 按需读取：要改 PROJECT / TODO / 功能文档 / 决定清单 / 待拍板，或跑文档体检、压体积时打开。更新流程（判断、顺序）与新想法的去向在 `SKILL.md`。

目录：决定与待拍板 · 写入时机 · 写什么、不写什么 · 上下文瘦身 · 文档体检

## 决定与待拍板：给 PROJECT 和 TODO 减负（用户 2026-11-03 立）

PROJECT 与 TODO 每个会话开场都要读。「为什么这样定」「还没定的争论」写进去，它们会一直长胖，读的人也分不清哪句是现状、
哪句是理由、哪句还没定。所以分两份**按需读**的文档出去：

- **待拍板（`ai/PENDING-DECISIONS.md`）**：还没定、要用户拍板的问题。每条一行或一小节——编号（`D-N`；要分类就加前缀，
  编号只增、不复用）、未决问题、处理边界与落点（不定的话先按什么做、影响哪份文档）。不写讨论过程。
- **决定清单（`ai/DECISIONS.md`）**：用户拍板了、会影响以后怎么做的结论，尤其是推翻旧做法的。**按拍板日期倒序排，
  最新的决定在最上面**；编号（`ADR-N`）按记录先后分配，只增、永不改、不重排，所以列表里的编号不一定连续；
  事后补录的旧决定照样取下一个编号，标「补录」并写原拍板日期，按原日期排进对应位置。每条写日期、状态、推翻了什么、
  裁定人与原话出处（哪一轮批注或对话）、决定、原来是什么样、为什么改、代价与什么情况下改回去。
  被推翻的旧条目保留原文，开头标注被哪条推翻，或在末尾加「已再动」一小节。

流转：

1. 冒出要用户定的事 → 进待拍板。TODO 里不展开讨论，要挂就写「等 D-N」
2. 用户拍板 → 决定清单写一条（注明关掉了哪个 D-N）→ 从待拍板删掉那一条 → 要做的事进 TODO
3. 做完 → 现状改写进 PROJECT / feature 文档，理由只写「（ADR-N）」，不复述
4. 用户在批注或对话里直接定了、没经过待拍板的，同样记进决定清单；只是确认现状、不改方向的，
   在对应条目上补一句「谁何时确认」，不另开一条

几条纪律：

- **引用不复述**：PROJECT、TODO、feature 文档提到决定只写编号与一句结论；理由、原话、代价只在决定清单里有一份——
  复述的那份会在决定改动时悄悄过期。
- **开场不整读**：两份都不进开场必读；按编号查（搜 `ADR-N` / `D-N`），讨论未决问题时才读待拍板。
- **骨架由模板植入**：AI 工作流模板（`shelf init` / `sync`）会植入两份带格式说明的骨架，往里填即可；
  没接模板的老项目，第一次出现要记的决定或待拍板时再建，开头一段写清只装什么，不预建空文件。
- **待拍板只留未决的**：定了就删（结论去了决定清单）。决定清单的条目不删——它是「这条路走过」的判据；
  条目多了按下面「上下文瘦身」给它加摘要与目录。

## 写入时机（什么时候才准写 PROJECT.md）

- **技术实现细节（数据库结构、配置、模块说明等）只在实际执行完成后才写进文档**；
  还没做的改动只写在 `ai/TODO.md`。把计划当成果写进 PROJECT.md，下一个人会照着它写代码。
  交给别的 agent 做的计划写成交接档（见 SKILL.md「会话存档与交接」）：它标明了是待做的设计，做完归档时结论才改写进功能文档。
- `ai/TODO.md` **只写高层描述**，不写数据结构细节。
- 数据库结构写进项目指定的唯一正文（PROJECT.md 写明在哪；没指定才写在 PROJECT.md），PROJECT.md 别处只留摘要与指针。
- 功能模块与数据库的描述**保持与线上实际状态一致**——写「现在是什么样」，不是「打算做成什么样」。

## 写什么、不写什么

| 写入 TODO.md | 写入 PROJECT.md | 写入 Feature 文档 |
|---|---|---|
| 高层任务描述 | 架构模块、接口说明、完成功能摘要 | 实现细节、数据结构、Subtask 进度 |
| Bug 记录 | 标签池、规范说明 | 边界情况、实现取舍（用户的决定只引用决定清单编号） |
| Epic/Milestone | 最后更新日期 | |

**不重复写**：Feature 文档有的细节，PROJECT.md 只引用不搬运。

**开工红线**（PROJECT.md 里每会话必读的强制清单，有的话）只写强制前置动作和指向唯一正文的链接，细则写进对应正文。

**活文档只写现状**：这几份文档每个会话都会被读，写进去的每一句都在花之后所有会话的上下文。
实现变了就改写原段落，不在末尾追加「某日：做了什么」；做完的事不留在 TODO；过程与证据留在 commit 与审核目录。

## 上下文瘦身（2026-09-30 立）

常驻文档是每个 agent run 的固定上下文成本，完成的历史不留在活文档里（TODO 做完即删，见上）。长文档还要能选读：

- **40KB+ 的文档要有「摘要与目录」头**：开头 ≤15 行——一段现状 + 每节一行「什么时候读」，
  让读者选读而不是整吞；追加内容后顺手更新摘要。
- **大到无法整读（约 100KB+）的按节分册**：本体改成索引（节号 → 文件 + 一句话），节编号不重排，
  全仓「§N」引用必须仍可寻址；新增节的人在同一个 commit 里建分册 + 补索引行。
- **按压缩后排版**（用户 2026-11-24 定）：上下文压缩后，宿主只重新读入最近改过的几份文件，超过上限的只剩路径、没有内容
  （Claude Code 2026-11 的口径是单份 5,000 token，中文约 12KB；数字以宿主当前文档为准）。所以任务中途反复要用的文档（功能文档、进度、交接档）
  把现状、下一步和要守的规则写在开头，超过上限的开头有目录或摘要、能按节重读（40KB+ 的按上面写完整的「摘要与目录」）；
  全程要守的规则归根协议或技能前部，不放在长文档的中段。
- **TODO 压回预算**：做完的删掉；项目有归档文件（如 `ai/TODO-ARCHIVE.md`）时，做完但还有参考价值的条目、压缩时删去的细节原文移进去（按原分区归组，写明何时、为何移入），活 TODO 里进行中的条目只留「现状 + 剩什么 + 链接」，开头放摘要与目录。
- **PROJECT 压回预算**：决定的理由与原话移进决定清单、未决的移进待拍板，PROJECT 只留「（ADR-N）」+ 一句结论；实现细节移进对应功能文档；开工红线这类规则原样保留。
- **留余量，一进一出**：压缩时压到预算的九成以下。卡着预算线收工的文档，下一次加一行就又超了。往设了预算的文档里加内容之前先看余量（`check-docs.mjs --budgets`，只查体积、不扫链接）：加完会超的，在同一次改动里先删掉等量的内容（做完的条目、过时的状态、别处已有唯一正文的段落），再加新的。
- **开工时报「常驻文档超预算」**（项目把预算检查接进了会话开场或开工脚本时会出现）：这一轮要写那份文档的人负责把它压回九成以下；只读它的任务不用处理，也不要为此另起一轮改写。

## 文档体检（`/intj check`）

命令在 `SKILL.md`「文档体检」。它只读 git 跟踪的 Markdown，查三样：链接与 `#锚点`（按 GitHub 的规则，含中文标题）、反引号里写的仓库路径、活文档的体积预算。活文档有失败或超预算时退出码为 1。

- **项目设置**在 `ai/check-docs.json`：不读的目录、冻结原件（调研、档案、审核证据，报出来但不用改）、生成或忽略的路径、有意接受的引用、体积预算。没有这份文件时所有文档都算活文档、不设预算。
- **预算给每会话都读的文档**（协议、PROJECT、TODO、技能登记表）和反复长胖过的文档。超预算说明它在回胀：改写成现状，不调高数字。只想看各份文档用了预算的多少，加 `--budgets`（不扫链接，够快，可以接进项目的开工脚本）。
- 移动或改名文档后，同一次改完它的入向链接，再跑一遍到 0 失败。
