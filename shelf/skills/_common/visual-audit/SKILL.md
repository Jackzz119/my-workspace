# VISUAL-AUDIT — 视觉体验审核

用 `**VISUAL-AUDIT**` 开场。以专业视觉设计师、概念设计师和产品体验评审的标准，看一款产品「用起来、看起来到不到位」，并把结论做进产品里。
适用于游戏、网页、桌面与移动应用；单个界面的小修、单张图的评审不升级成整轮审核。

## 和别的技能怎么分

本技能管**一整轮评审的流程、证据与记录**，设计判断和产出仍按各自的技能做：

| 事 | 归谁 |
| --- | --- |
| 整体风格、材质、角色与场景的判断，视觉完成件的审核 | 主美技能（如 `monet`） |
| 概念模型、术语一词一义、信息架构、任务流程、状态与失败恢复、动效的设计与验证 | UI/UX 技能（如 `ui-tailor`） |
| 把出图、审图、比稿交给外部模型 | 出图工具技能（如 `codex-visual`），按它的额度与归档规则 |
| 给用户看的报告页与批注 | 批注报告技能（如 `annotated-report`） |
| 文档、结构、协议、性能、上下文成本 | 工程审核技能（如 `project-audit`）；体验上的卡顿（打开慢、掉帧）两边都看，这里量「用户看到的」，那边量「为什么慢」 |

这些技能在就照它们做，不在就按本技能写的最低要求自己完成，并在报告里说明是同一个 agent 做的。

## 调用与边界

- 支持：完整一轮、只调研、只走查出审核点、只比稿某个设计点、继续、复查上一轮、处理报告批注。用户说了轮数就按轮数，每轮单独一个运行目录。
- **用户的使用反馈是真源**：原话原样记进本轮日志，拆条编号进审核点文档，收口时逐条验收；不改写、不替用户「总结成更合理的说法」。反馈和现行设计决定冲突时，以用户最新的话为准，并把被取代的决定登记出来。
- 授权只覆盖用户说过的范围。「重新设计」「能做的直接实现」是实施授权；删功能、改数据、改协议文件、对外发布仍各自要授权。产品的铁律与冻结项（设计系统里写明的）不因审核结论自动失效。
- **三种走法**，第 0 步定下、写进日志：**直接实现**（用户授权了直接实现，改动面小）；**先看稿**（改动面大、会上生产，或用户说要先看稿；拿不准就走这条）——比稿的各方向做成能点的稿给用户亲手体验，定了再实装；**只交付建议**（没有实施授权）——交工作包与决定项，实施由用户排期另派。
- 审核用隔离的样板或本地数据，不连真实账号；浏览器自动化把离开被测站点的请求全部拦掉。
- 修改本技能本体前先给用户看改动；用户已明确要求迭代技能的那一轮可以直接改，改动写进报告。

## 运行目录

技能本体留在技能目录；审核产生的一切放项目 ai 区的 **`visual-audit/`**（记为 `AUDIT_DIR`）。已有同职能目录就复用，不另建一套。

| 文件 | 内容与加载时机 |
| --- | --- |
| `INDEX.md` | 入口：现在在哪一轮、怎么续接、边界、历史轮次表；继续时先读 |
| `STEPS.md` | 跨轮蓝图：标准子步骤、子代理配置（哪个领域用哪个模型）、跨轮经验、可复用工具；开工实例化，收尾写回 |
| `FINDINGS.md` | 审核点的稳定编号与最新状态（一行一条），跨轮追踪；待办进项目的任务唯一来源，这里只引用 |
| `scripts/` | 项目自己的截图场景表与审核脚本（引擎在技能目录 `scripts/capture.mjs`） |
| `runs/<run-id>/00-log.md` | 本轮日志：用户原话、真源需求拆条、子步骤表、续接、进度、收口验收、复盘、验收期 |
| `runs/<run-id>/01-points.md` | 审核点：用户反馈拆条、走查与调研发现、每点的判定 |
| `runs/<run-id>/02-pitch.md` | 比稿：题目、方向、出稿人、互评与评分、结论、要用户定的事 |
| `runs/<run-id>/03-verify.md` | 实施与验收：改了什么、前后数值对照、复审发现、未完成项 |
| `runs/<run-id>/99-report.md` | 总报告源稿，交批注报告技能出页 |
| `runs/<run-id>/evidence/` | 调研文件、截图矩阵与 `manifest.json`（计时、尺寸、对比度） |

**数值入库，图组不入库**：整套截图体积大、能按提交重拍，只把 `manifest.json` 和报告里用到的精选图入库；比稿的原型、图和说明按项目设计系统的规矩放比稿区，不放审核目录。记录格式见 [references/records.md](references/records.md)。

## 一轮怎么走

七步，前一步的产物是后一步的输入。每步的子步骤从 `STEPS.md` 蓝图实例化进本轮日志，做完一项记一项。

### 0 · 准备

1. 建运行目录与 `00-log.md`：用户原话原样贴进去，拆成真源需求；反馈拆条编号（F-01…）。
2. **定性的评价先翻成可检查的属性**：「不够 X 的级别」「没有质感」「不高级」这类话，拆成几条能在截图与实测里检查的属性（例如「游戏化」= 质感、层次、视觉冲击、交互反馈的丰富度），写在拆条旁边；第一次交付（审核点或比稿 brief）里写明「我把这句话读成了……」请用户确认。读偏一句话，整轮的方向都跟着偏；用户纠正了就改拆条，后面的题目重定。
3. 读项目入口文档、设计系统（整体风格、铁律、UI/UX 入口、决定清单里相关的条目）、上一轮审核的蓝图与发现。只读本轮范围涉及的模块，不整库通读。把硬约束与已定决定列出来（带编号、摘原文），后面的复核、brief 与评审都以它为准。
4. 定范围：目标平台与输入方式、作为基准的外观 / 主题、要覆盖的视口、不在范围的东西（写明原因）。**问清哪些稳定、哪些以后会换**（场景与背景、镜头、主体的位置与朝向、色调、内容量）：会换的只能当风格参考，不能当布局与取色的依据；拿不准的按「会换」处理，在第一次交付里确认。
5. 定档位与走法：**完整档**含比稿；额度（主线程与外部出图工具，有无付费兜底）或授权不够时走**轻量档**——不比稿，只交付发现、建议、工作包与决定项，把「要不要比稿、比哪几题」列成决定项。走法见「调用与边界」。

### 1 · 现状采证

先看，再判断。用技能目录的 [scripts/capture.mjs](scripts/capture.mjs) 加项目的场景表，拍出**界面 × 状态 × 外观 × 视口**的截图矩阵，并量三样数值：

- **打开计时**：从按下到出现、到停稳、途中最长一帧（用户说「慢」就用它定量）。每项量 5 次报中位数与范围（`--repeat 5`），**单独跑**：一次的值在机器忙时能偏出 10–25 ms，足以把「没变」读成「变差」。
- **尺寸与材质**：面板占视口的比例、字号、圆角、投影、模糊。
- **对比度**：文字压在真实背景上的像素对比，不用 token 推算。

同一张场景表加 `--viewport`、`--set` 就是视口 × 外观 × 时段的矩阵；各组的数值用 [scripts/collect.mjs](scripts/collect.mjs) 并成一个入库的文件。场景表写法见脚本头部注释；非网页产品用引擎自带的截图与性能工具替代，记录同样三类数值。拍完自己把关键图看一遍——人物、背景、状态都对了才算数（少等几秒，画面里的角色或大图可能还没画出来）。

改了量法（怎么算「停稳」、算不算某一帧、量几次）就在审核点里单列一节写明新旧差别：两轮的数不能直接比，同一份代码用新旧量法各是多少要有交代。

有外部审图工具时，采证之后先让它对关键截图**冷读一遍现状**（只给产品、用户原话、硬约束），它的发现和主线程的走查并列进审核点。

### 2 · 调研

两层：**通用规则**与**目标产品的定制调研**。

- 通用规则从 [references/rules.md](references/rules.md) 起步（可用性、心理、反馈时序、层级排版、弹层模式、视觉流、情感化、游戏感、阴影材质、按界面类型的专项），本轮涉及的关键条目重新打开原文核一次。
- 定制调研每轮都做，不复用上一轮的结论当现状：**横向**比同类产品此刻的界面与口碑，**纵向**比本产品上一轮的调研与改动；再按本轮反馈集中的界面类型做专项（聊天、播放器、设置、HUD……）。
- 并行派调研子代理，一条线一个文件，全部打开原文核验、只凭摘要的标 UNVERIFIED、评论只转述。写法与 brief 模板见 [references/research.md](references/research.md)。
- 调研之间**结论相反的地方就是比稿题目**，不由主线程拍脑袋选边。

### 3 · 审核点

把三个来源汇成一张表：F（用户反馈）、W（走查：截图与数值，加上命名是否一词一义、入口好不好找、反馈与失败恢复、焦点与键盘、规范与实现的偏差）、R（调研对照）。每点一个稳定编号，写位置、现状与证据、对照的规则、判定。走查时把每个「点一下之后，变化出现在哪」按规则库的 L 节（视觉流与触发处展开）过一遍：起点、落点、方向、时长。

**先复核再判定**：走查、调研与外部模型冷读的每条结论，先回到代码、规范原文、已定决定与真实数据分布核一遍——样板数据的长度与分布可能和真实数据不同，截图里的列宽、留白、截断先查定宽依据再判；核不上的不进表。

- **直接改**：规则与证据都清楚，没有多个合理做法。
- **存疑 → 比稿**：有两个以上说得通的方向，或调研结论相反。
- **记录**：走查或调研的结论与已定决定冲突（写决定编号，不进比稿；确实值得重议的转决定项；用户反馈与决定冲突的照「调用与边界」以用户最新的话为准）、新功能、超出本轮授权、纯属视觉偏好、要用户定的事。

用户反馈的每一条都必须落到至少一个审核点上。

### 4 · 比稿

存疑的点归并成少数几个题目（一个题目回答一组相关的问题），每个题目 2–3 个有实质差别的方向，一个方向一个子代理。要点（完整规程见 [references/pitch.md](references/pitch.md)）：

- **按领域派模型**：界面与交互、概念与材质、角色与场景……各用那方面最强的模型与最高的 effort。对应关系由用户定，记在蓝图的「子代理配置」里；没定就跟主线程同一个模型，并在报告里写明。
- **每轮都用新的子代理**：同一个子代理不会有新视角；新一轮的方向也要换，不重跑上一轮的题目。
- **稿必须能看**：可运行的原型或实景图，各方向比较时用同一张背景、同一个视口、同一份内容；文字线框不算稿。出稿人自己截图、自己看、改到愿意拿出来比。
- **不绑在会换的东西上**：brief 的硬约束写明第 0 步列出的会换项只当风格参考，并逐项列「必须保持原样」的既有样式与样板数据；评审把「换一张背景 / 换一个机位还成立吗」当必答题；交稿逐格核对生图走样（错字、改了数据或既有样式），走样不计分。
- **外部模型当第二意见**：每份稿交给出图工具技能审一次，出稿人按意见改一轮；全部交稿后再让它把各方向放在一起比一次。它的额度是另一本账，撞到上限就欠着、恢复后补跑。
- **评审**：每题派一位没出过稿的评审人，除了按共同标准打分，还要去代码与决定清单里做**事实核查**（稿里的东西是不是真数据、和哪条已有决定冲突）、核可行性、把用户原话里的量列成数值对照表；方向少、想看出稿人互相借鉴时改用互评（每人只评别人的稿）。
- **归纳**：主线程自己看每一张图，出对照表（得分、共识、分歧），给推荐或混合方案；要用户定的事逐条给推荐和不回答时的默认。分数接近时不按最高分选，找出那一个真正的分歧来定。混合方案实施出来的第一版要当成稿再审一遍。

归纳之后按第 0 步定的走法：

- **直接实现**：按推荐实施，决定清单随报告给用户批注；批注改了决定就按批注再改。
- **先看稿**：这一步的交付物是每个方向（含推荐的混合方案）一份**能点的稿**——可交互原型，用真实长度的内容、能切关键状态——随批注报告页一起发布给用户亲手体验：每份稿一个能打开操作的页面或内嵌框，带批注层，截图只作辅助。**定稿之前不动产品代码、不推生产**；用户批注定了方向再进第 5 步，没定的题按批注再出一版稿。稿怎么放进报告见 [references/pitch.md](references/pitch.md) §8。
- **只交付建议**：停在这里，交工作包与决定项（格式见 [references/records.md](references/records.md) §8），实施由用户排期另派。

### 5 · 实施

- 先公共后分区：外壳、材质与 token 这类所有界面共用的先改、先验、先提交，再分给互斥的文件并行改。分区只依赖公共部分的几个名字（变量名、容器名）而不依赖它的数值时，把名字在任务里约定好，公共与分区可以同时开工。
- 版式与材质两题都要落地时**先版式后材质**：两边会动同一批样式文件，材质又要在定下来的版式上看效果；版式那一批验过、提交了再派材质。派实现子代理时写明各自负责和不能碰的文件；几个人都可能动的共享文件（回归脚本、样板页、入口页面）只许做小范围的精确替换、不许整文件重写；子代理不做版本控制操作，各自用自己的端口起开发服务、用完停掉。
- 改动守项目的代码规范、设计系统与铁律；被新决定取代的旧决定在决定清单里登记，文档跟着改写（只写现状）。
- 要新美术素材的地方按项目的出图规矩走（先占位、登记要图），不在实现里临时造。

### 6 · 验收

- **同一套矩阵重拍**，和改前并排；计时、尺寸、对比度逐项对照，没达标的写在数字旁边。
- 用户反馈逐条回看：这一条现在是什么样，图在哪。
- **独立复审**：派没参与设计的新子代理，只给它改后的图和评判标准，让它找问题；修完再审，直到一轮没有新的可改项。
- 项目自己的检查（类型、lint、构建、已有的界面回归脚本）照跑，区分原有失败与新回归。说一条失败「原本就有」之前，在改动前的提交上复跑一次（临时检出一份），值对得上才算数，不凭实现者一句话。
- **用户原话里的量要用数值核**：「不够大」「太慢」「太小」这类话，拿改前改后的面积、毫秒、字号比一遍；方案在比稿里得分再高，量上没回应就是没解决。
- 没条件验的（真机、真实账号、其它浏览器）列成待验，不写成通过。

### 7 · 收口

对照真源需求逐条验收，没达成的回到那一步；审核点状态写回 `FINDINGS.md`，待办进任务来源，决定进决定清单，设计系统的常驻文档按改后的现状更新。总报告交批注报告技能出页发布。最后复盘：哪一步发现了问题、哪里重复低效、漏了什么，把有证据的改进写回蓝图。

报告发出后用户的批注是本轮的**验收期**，不另开一轮：逐条处理——问题要答、决定要记、改动要做、本期不做的转交接档或待办。用户批准的设计结论由设计技能写进设计系统的定稿区，审核里不提前改定稿。用户说「本期收尾、交给下一个 agent」时，按宿主的交接规程（如会话存档）写交接档：用户原话、已定的事、被否的方案与原因、下一轮的题目与硬约束、可复用的工具与坑；本轮运行目录是它的证据来源，交接档链过去、不复制（格式见 [references/records.md](references/records.md) §9）。

## 多轮

用户要多轮时，每轮都是完整的七步：第 N+1 轮从第 N 轮**改完之后的现状**出发重新采证，调研补新的角度，比稿换新的子代理与新的方向（上一轮没比过的界面、上一轮落选方向里值得再看的部分、复审留下的问题）。上一轮的结论只作纵向对比的基线，不当成这一轮的完成。

新一轮的题目从四处来：上一轮复审留下的问题、外部模型与上一轮结论不一致的地方、上一轮没达标的数值、这一轮对现状的冷读（主线程自己的走查 + 外部模型）。新一轮开工先把上一轮的工具过一遍——量法有没有失真、底图干不干净、场景表还指不指得到元素——上一轮的数字是用它们量出来的。用户的反馈每轮都原样再记一遍，并写上「上一轮之后现在是什么样」（重新量的，不是抄上一轮的结论）。

## 额度与断点

整轮是长任务，额度用尽时会话直接停。续接所需的一切随做随存：

- 每个子步骤完成或受阻，立刻更新本轮日志的「续接」与「进度」；子代理的结论落到文件才算数，派出前把它的产出路径写进断点。
- 派子代理、跑比稿、做实测前查一次用量；任一窗口到 90%，或撑不到下一个可交付单元，先写断点再停。
- 最高档的子代理同时跑很耗额度，一次派满可能在半小时内把一个用量窗口打穿、所有稿都停在半路：分批派，只有出稿用最高档，互评、复审、实现、调研用常规或高一档。被截断的子代理额度恢复后从它自己的断点续跑，不重派。
- 外部模型（出图 / 审图工具）的额度与有无付费兜底开审时就查，不够就把审图与比稿排到重置之后、先做别的步骤，排期写进「续接」；每批出稿子代理派出前再查一次。撞到它自己的用量上限时，这一步欠着、记进断点，恢复后补跑并把结果如实并进结论（和已有结论不一致也照写）；不跳过，也不换别的办法冒充。
- 用户授权过自动续跑的，用宿主的定时机制排在额度重置之后几分钟，提示写「继续 visual-audit 运行 <run-id>：先读 INDEX.md 与 00-log.md 的续接节」；没有定时机制就把续接指令交给用户。定时机制多半只在宿主应用开着、电脑醒着时触发：会话因额度停下后电脑一睡，它就顺延到用户下次打开——能申请「保持唤醒」就申请，并把这个限制如实告诉用户，不要把「设了定时」说成「会自动续上」。
- **主线程自己也很贵**（上下文越长，每一步越贵）：它只做归纳、决定、看图与核对；读长文件、写代码、跑整套矩阵都交出去；等子代理时不轮询。
- 续跑先核对分支、未提交的改动、运行目录里的产物与断点记录是否一致，再从断点继续，不重做已完成的子步骤。

## 让审核本身跑得快

- **并行**：调研线、出稿人、互评、实现分区都并行；主线程只做归纳、决定与核对。
- **主线程省上下文**：调研与稿件都落文件，主线程只读结论节与主图；整份证据按需查。大段源码交给子代理读。
- **脚本复用**：截图矩阵、计时、尺寸、对比度都由同一个引擎出，改前改后用同一张场景表；新需要的测量加进引擎而不是写一次性脚本。
- **先确认证据是对的再用**：第一批图拍完先抽看；场景表里的变量、等待时间错了，后面所有判断都跟着错。比稿用的干净底图也由引擎出：场景表里放一个把界面全藏掉的场景（凡不是画面本身及其祖先的元素都隐藏，而不是列一串要藏的类名——列漏一个，底图里就带着旧界面），发出去之前打开看。
- 每轮收尾把耗时最长的环节和踩到的坑记进蓝图，下一轮先看。

## 经验摘录

症状 → 结论 → 细节在哪。

- 方向连着几轮被用户说「还是不对」→ 多半把一句定性评价读偏了：翻成可检查的属性，第一次交付就请用户确认 → 第 0 步第 2 项
- 方案在当前背景上好看，换个场景、外观或机位就散 → 布局与取色绑在了会换的东西上：第 0 步问清稳定项，brief 写进硬约束，评审必答「换了还成立吗」→ 第 0 步第 4 项、[pitch.md](references/pitch.md) §3、§6
- 改版没看稿就上了生产、用户要返工 → 改动面大或会上生产的走「先看稿」：能点的稿进批注页，定了再实装 → 第 4 步、pitch.md §8
- 审图说某列太窄、某处留白太多 → 先查定宽依据与已定决定，样板数据的分布可能和真实数据不同 → 第 3 步「先复核再判定」
- 生图把既有样式或样板数据改了 → brief 逐项列「必须保持原样」，交稿逐格核对，走样不计分 → pitch.md §3、§4

## 固定目录

frontmatter 的 `metadata.shelf-scaffold` 声明了两个目录，`shelf init` / `shelf sync` 会在项目 ai 区建出来（空目录放 `.gitkeep`）：

| 目录 | 放什么 | 第一次什么时候写 |
| --- | --- | --- |
| `visual-audit/runs/` | 每轮一个 `<日期-序号>/` 运行目录 | 第一次审核开工时 |
| `visual-audit/scripts/` | 项目的截图场景表与审核专用脚本 | 第一次采证时 |

`INDEX.md`、`STEPS.md`、`FINDINGS.md` 第一次审核时才写，不预建空文件。
