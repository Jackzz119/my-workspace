# VISUAL-AUDIT — 视觉体验审核

用 `**VISUAL-AUDIT**` 开场。以专业视觉设计师、概念设计师和产品体验评审的标准，看一款产品「用起来、看起来到不到位」，并把结论做进产品里。
适用于游戏、网页、桌面与移动应用；单个界面的小修、单张图的评审不升级成整轮审核。

## 专区与调用

审核分五个专区：点哪个深审哪个，也可以几个一起或完整一轮（用户 2026-11-23 定）。专区管「审哪个方面」，下面的七步管「怎么走」，两者正交：步骤、证据与标准各专区共用一份，专区文件只写它自己的那部分。

| 专区 | 代号 | 审什么 | 主要证据 | 开审前读 |
| --- | --- | --- | --- | --- |
| 界面与体验 | `ui` | 信息层级与布局、可用性、弹层与呈现模式、术语与文案、状态与失败恢复 | 截图矩阵；尺寸、对比度 | [references/zone-ui.md](references/zone-ui.md) |
| 整体风格与概念 | `style` | 概念与美术方向、材质阴影与质感、情感与气质、界面和画面是不是一家 | 截图矩阵；材质数值；换背景、换外观的图 | [references/zone-style.md](references/zone-style.md) |
| 特效与粒子 | `fx` | 命中、完成、庆祝的强度与节奏，粒子、闪光、混合与层级 | 逐帧胶片 | [references/zone-fx.md](references/zone-fx.md) |
| 动效与交互手感 | `motion` | 动画与转场、按下反馈、可打断、视觉流、拖拽与连点 | 打开计时；逐帧胶片 | [references/zone-motion.md](references/zone-motion.md) |
| 渲染性能 | `perf` | 实时渲染掉不掉帧、打开慢不慢、长任务与内存 | 真实试玩的采样与 trace | [references/zone-perf.md](references/zone-perf.md) |

```text
/visual-audit                完整一轮：五个专区都审
/visual-audit motion         只深审一个专区
/visual-audit ui style       几个专区一起，按完整一轮的顺序
/visual-audit fx 只走查       专区 × 阶段：做到出审核点为止
```

自然语言一样管用：「跑一轮视觉审核」「只审动效」「审查粒子效果」「看看渲染性能」「继续上一轮」「处理报告批注」。Codex 侧没有参数提示：点名本技能后加同样的词，或直接用自然语言。

- **没点专区就是完整一轮**：五个专区都在范围内，七步只走一遍（不是每个专区各走一遍）——截图矩阵拍一套共用，第 3 步走查按 `ui → style → fx → motion → perf` 的顺序过完五个再进第 4 步；走试玩这条线的，各维度照 playtest.md §4 在维度内比完、改完、提交了再下一个，`style` 不是维度，和 `ui` 一起走查。说法对不上哪个专区时先问一句，不猜。
- **点了专区就只审它**：七步照走、标准不降，每步只做这些专区的部分，做完就收口交付，不顺手跑别的专区。碰到别的专区的问题只记一句；没跑的专区在报告里标「未覆盖」。
- 支持：完整一轮、只调研、只走查出审核点、只比稿某个设计点、继续、复查上一轮、处理报告批注，都可以再限定专区。用户说了轮数就按轮数，每轮单独一个运行目录。

## 和别的技能怎么分

本技能管**一整轮评审的流程、证据与记录**，设计判断和产出仍按各自的技能做：

| 事 | 归谁 |
| --- | --- |
| 整体风格、材质、角色与场景的判断，视觉完成件的审核 | 主美技能（如 `monet`） |
| 概念模型、术语一词一义、信息架构、任务流程、状态与失败恢复、动效的设计与验证 | UI/UX 技能（如 `ui-tailor`） |
| 把出图、审图、比稿交给外部模型 | 出图工具技能（如 `codex-visual`），按它的额度与归档规则 |
| 给用户看的报告页与批注 | 批注报告技能（如 `annotated-report`） |
| 文档、结构、协议、性能、上下文成本 | 工程审核技能（如 `project-audit`）；体验上的卡顿（打开慢、掉帧）两边都看，这里量「用户看到的」，那边量「为什么慢」 |
| 只读代码、给动画改造计划 | 动画代码审计技能（如 `improve-animations`）；`motion` 专区看用户看到、摸到的 |

这些技能在就照它们做，不在就按本技能写的最低要求自己完成，并在报告里说明是同一个 agent 做的。

## 边界

- **用户的使用反馈是真源**：原话原样记进本轮日志，拆条编号进审核点文档，收口时逐条验收；不改写、不替用户「总结成更合理的说法」。反馈和现行设计决定冲突时，以用户最新的话为准，并把被取代的决定登记出来。
- 授权只覆盖用户说过的范围。「重新设计」「能做的直接实现」是实施授权；删功能、改数据、改协议文件、对外发布仍各自要授权。产品的铁律与冻结项（设计系统里写明的）不因审核结论自动失效。
- **三种走法**，第 0 步定下、写进日志：**直接实现**（用户授权了直接实现，改动面小）；**先看稿**（改动面大、会上生产，或用户说要先看稿；拿不准就走这条）——比稿的各方向做成能点的稿给用户亲手体验，定了再实装；**只交付建议**（没有实施授权）——交工作包与决定项，实施由用户排期另派。
- 审核用隔离的样板或本地数据，不连真实账号；浏览器自动化把离开被测站点的请求全部拦掉。
- 修改本技能本体前先给用户看改动；用户已明确要求迭代技能的那一轮可以直接改，改动写进报告。

## 目录

技能本体留在技能目录；审核产生的一切放项目 ai 区的 **`visual-audit/`**（记为 `AUDIT_DIR`）。已有同职能目录就复用，不另建一套。

- `INDEX.md`：入口，继续时先读；`STEPS.md`：跨轮蓝图，开工实例化，收尾写回；`FINDINGS.md`：审核点的稳定编号与最新状态，跨轮追踪——待办进项目的任务唯一来源，这里只引用。三份第一次审核时才写，不预建空文件。
- `scripts/`：项目自己的截图场景表、审核脚本与试玩适配；引擎在技能目录 `scripts/`（截图 `capture.mjs`、试玩 `play.mjs`）。
- `runs/<run-id>/`：每轮一个，内有 `00-log.md`、`01-points.md`、`02-pitch.md`、`03-verify.md`、`99-report.md` 与 `evidence/`。

**数值入库，图组不入库**：整套截图体积大、能按提交重拍，只把 `manifest.json` 和报告里用到的精选图入库；比稿的原型、图和说明按项目设计系统的规矩放比稿区，不放审核目录。每份文件写什么、`run-id` 怎么编、证据去留，见 [references/records.md](references/records.md)：建运行目录、写审核点、收口时读对应的节。

**固定目录**：`visual-audit/runs/`（第一次审核开工时开始写）与 `visual-audit/scripts/`（第一次采证时开始写）由 frontmatter 的 `metadata.shelf-scaffold` 声明，`shelf init` / `shelf sync` 会在项目 ai 区建出来，空目录放 `.gitkeep`。

## 一轮怎么走

七步，前一步的产物是后一步的输入。每步的子步骤从 `STEPS.md` 蓝图实例化进本轮日志，做完一项记一项。**每一步开工前先读它的细则**：[references/round.md](references/round.md) 的同号节（开工时连 §9 一起读），加本轮专区的专区文件；各文件的格式在 records.md 的对应节。

- **0 · 准备**：建运行目录与日志，反馈原样记下、拆条编号；**定性的评价先翻成可检查的属性**，第一次交付就请用户确认；列硬约束与已定决定；**问清哪些稳定、哪些以后会换**；定专区、档位与走法。
- **1 · 现状采证**：先看，再判断。用 [scripts/capture.mjs](scripts/capture.mjs) 加项目的场景表拍截图矩阵（界面 × 状态 × 外观 × 视口），量打开计时、尺寸与材质、对比度；有外部审图工具时采证之后先让它冷读一遍现状。
- **2 · 调研**：**通用规则**从 [references/rules.md](references/rules.md) 起步，**目标产品的定制调研**每轮都做、不复用上一轮的结论当现状；并行派调研子代理，派之前读 [references/research.md](references/research.md)。结论相反的地方就是比稿题目，不由主线程拍脑袋选边。
- **3 · 审核点**：把 F（用户反馈）、W（走查）、R（调研）汇成一张表写进 `01-points.md`；**先复核再判定**，判定只有「直接改 / 存疑 → 比稿 / 记录」。
- **4 · 比稿**：存疑的点归并成少数几个题目（一个题目回答一组相关的问题），每个题目 2–3 个有实质差别的方向，一个方向一个子代理；**稿必须能看**，文字线框不算稿。派出稿人之前读完 [references/pitch.md](references/pitch.md)，结论写进 `02-pitch.md`。归纳之后按三种走法之一：走「先看稿」的，**定稿之前不动产品代码、不推生产**。
- **5 · 实施**：先公共后分区；版式与材质两题都要落地时先版式后材质。
- **6 · 验收**：同一套矩阵重拍、和改前并排对照，用户反馈逐条回看，派没参与设计的新子代理独立复审，项目检查照跑，结果写进 `03-verify.md`。
- **7 · 收口**：对照真源需求逐条验收，没达成的回到那一步；写回审核点状态、待办、决定与设计系统常驻文档，总报告交批注报告技能出页发布，最后复盘写回蓝图。报告发出后用户的批注是本轮的**验收期**，不另开一轮。

## 试玩这条线（游戏与动效密集的产品）

截图矩阵看不出手感与掉帧。产品是游戏、界面的价值主要在动效与反馈上，用户的反馈指向交互、特效、卡顿，或上架前要一次真的有人玩过的验收时，七步之外加走这条线，产物进同一个运行目录；点名 `fx`、`motion`、`perf` 的也走，只走对应的维度；只点 `style` 的不走，只点 `ui` 的在产品本来就该走时走维度 U。第 0 步定下要走就读 [references/playtest.md](references/playtest.md)：§1 写了它在七步的哪几处加什么，完整规程、记录格式与 [scripts/play.mjs](scripts/play.mjs) 的用法都在那里。
派代理时用的提示词模板：[prompts/research.md](prompts/research.md)（调研）、[prompts/compare.md](prompts/compare.md)（比稿）、[prompts/playtester.md](prompts/playtester.md)（盲测）。

## 多轮

用户要多轮时，每轮都是完整的七步，从上一轮**改完之后的现状**出发；新一轮开工前读 round.md §8。

## 额度与断点

整轮是长任务，额度用尽时会话直接停。续接所需的一切随做随存：

- 每个子步骤完成或受阻，立刻更新本轮日志的「续接」与「进度」；子代理的结论落到文件才算数，派出前把它的产出路径写进断点。
- 派子代理、跑比稿、做实测前查一次用量；任一窗口到 90%，或撑不到下一个可交付单元，先写断点再停。
- **主线程自己也很贵**（上下文越长，每一步越贵）：它只做归纳、决定、看图与核对；读长文件、写代码、跑整套矩阵都交出去；等子代理时不轮询。
- 派子代理或用外部模型之前，以及要停下、续跑、接手别人中断的运行之前，先读 round.md §9（分批派、外部模型的额度另算、自动续跑与接手的规矩）。

## 经验摘录

症状 → 结论 → 细节在哪。

- 方向连着几轮被用户说「还是不对」→ 多半把一句定性评价读偏了：翻成可检查的属性，第一次交付就请用户确认 → round.md §0 第 2 项
- 方案在当前背景上好看，换个场景、外观或机位就散 → 布局与取色绑在了会换的东西上：第 0 步问清稳定项，brief 写进硬约束，评审必答「换了还成立吗」→ round.md §0 第 4 项、pitch.md §3、§6
- 改版没看稿就上了生产、用户要返工 → 改动面大或会上生产的走「先看稿」：能点的稿进批注页，定了再实装 → round.md §4、pitch.md §8
- 审图说某列太窄、某处留白太多 → 先查定宽依据与已定决定，样板数据的分布可能和真实数据不同 → round.md §3「先复核再判定」
- 生图把既有样式或样板数据改了 → brief 逐项列「必须保持原样」，交稿逐格核对，走样不计分 → pitch.md §3、§4
- 截图都对，用户还是说「不跟手」「卡」→ 静态矩阵量不到：出逐帧胶片、在真实试玩里采帧间隔 → playtest.md §5、zone-perf.md §5
- 预热或缓存类的优化测出来像没效果 → 试玩场景直接派发动作绕开了真实入口；首次与之后也要分开报 → zone-perf.md §5
- 比稿定了案，不带参数的构建跑的还是旧方案 → 定案那一刻就把开关的缺省值改成胜者 → playtest.md §7
