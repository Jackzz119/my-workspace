# 记录格式

建运行目录、写审核点、收口时按需查。文件名按项目已有的命名风格调整一次，之后保持稳定。

目录：1 运行编号与目录 · 2 `00-log.md` · 3 `01-points.md` · 4 `03-verify.md` · 5 根目录三份 · 6 证据的去留 · 7 总报告 · 8 工作包与决定项 · 9 交接档

## 1. 运行编号与目录

`run-id` 用日期加序号（`2026-11-11-01`），同一天的第二轮序号加一。每轮一个目录，上一轮的文件不改写（冻结），新发现写新一轮。

```text
AUDIT_DIR/
├── INDEX.md  STEPS.md  FINDINGS.md
├── scripts/            场景表（scenarios.json）与项目专用脚本
└── runs/<run-id>/
    ├── 00-log.md  01-points.md  02-pitch.md  03-verify.md  99-report.md
    └── evidence/
        ├── research-*.md          调研证据（入库）
        ├── before.json  after.json   截图矩阵的 manifest：计时、尺寸、对比度（入库）
        ├── before/  after/         整套截图（不入库，按提交重拍）
        └── img/                   报告里用到的精选图（入库，JPEG，单张尽量小）
```

未开始的阶段不建空文件。

## 2. `00-log.md`

```markdown
# 运行 <run-id> · <主题>
## 一、用户原话（原样）= 真源需求        整段原话；下面一张「真源需求拆条」表（编号 / 需求 / 我的读法（可检查的属性）/ 用户确认 / 归属）
## 二、范围、授权与任务拆解            范围、授权、数据边界；稳定项与会换项；档位（轻量 / 完整）与走法（直接实现 / 先看稿 / 只交付建议）；子步骤表（ID / 目标 / 方法 / 产出与验收 / 状态）
## 三、续接                          覆盖式更新，只留最新：断点 / 已落盘 / 未落盘 / 下一步第一件事 / 环境 / 额度
## 四、进度                          时间 · 子步骤 · 事件，一行一条
## 五、收口验收                       真源需求逐条：达成（证据）/ 回到哪一步
## 六、复盘                          发现问题的、重复低效的、漏掉的；写回蓝图的改动
## 七、验收                          报告发出后用户的批注：逐条处理与回复；本期不做的去向（交接档 / 待办）；交接档的路径
```

「我的读法」只给定性的评价填（「不够 X 的级别」「没质感」）：几条能在截图与实测里检查的属性。「用户确认」写「待确认 / 已确认（日期）/ 用户改成……」；用户改了读法，这一行改写，受影响的审核点与题目跟着重定。

子步骤 ID 用步骤前缀加序号：`P`（准备）、`E`（采证）、`R`（调研）、`A`（审核点）、`C`（比稿）、`I`（实施）、`V`（验收）、`K`（技能与蓝图）。状态：待执行 / 进行中 / 已完成 / 受阻 / 已取消，后两种写原因。

## 3. `01-points.md`

三节（量法改过的那一轮多一节）：

1. **用户反馈**：原话拆条，一句一行，编号 `F-01…`，右栏写对应的审核点。原话不改写；拆的时候不丢句子、不合并两件事。第 2 轮起每轮都原样再记一遍，中间加一栏「上一轮之后（本轮基线）」：这一轮重新拍、重新量出来的现状，不照抄上一轮的结论。
2. **审核点**：一行一条。

    ```text
    ID | 来源（F / W / R）| 位置 | 现状与证据（截图名、数值）| 对照的规则（规则库编号或调研条目）| 判定
    ```

    编号 `VA-001…` 跨轮稳定，复查沿用旧号；判定只有「直接改 / 存疑 → 比稿 <题目> / 记录」。「记录」写明是哪一种：与已定决定冲突（决定编号）、新功能、超出授权、视觉偏好、要用户定。复核时核不上的条目不进表，在表下一句话列出（条目 · 为什么不成立）。
3. **比稿题目**：题目、覆盖的审核点、方向、出稿人。
4. **量法修正**（改过量法才写）：项 | 上一轮的量法 | 本轮的量法 | 影响（同一份代码新旧各量到多少）。放在审核点之后、比稿题目之前。

外部模型对现状的冷读单列一小节：全文存进 `evidence/`，这里只写它的总判断、和主线程走查重合的条目（不重复列）以及它多看出来的（另起编号）。

## 4. `03-verify.md`

```markdown
## 改了什么            按界面分节：做法一句话 + 文件路径（代码细节看提交）
## 前后对照            表：指标 | 改前 | 改后 | 目标 | 达标；没达标的原因紧跟在数字旁
## 用户反馈逐条回看     F 编号 | 现在是什么样 | 图
## 独立复审            复审人（模型）、发现、处理；到哪一轮收敛
## 项目检查            类型 / lint / 构建 / 回归脚本的结果，原有失败与新回归分开
## 待验与未完成         真机、真实账号、其它浏览器、没做完的审核点
```

## 5. `FINDINGS.md`、`INDEX.md`、`STEPS.md`

`FINDINGS.md` 一行一条，只留编号、一句话、状态、最近一轮、待办或提交的指向：

```text
VA-001 | 聊天打开慢 | 已修（<run-id>，<提交>）| 待真机验
```

状态：待处理 / 比稿中 / 已定待做 / 已修 / 已验 / 记录（等用户定）/ 不做（原因）。

`INDEX.md`：现在在哪一轮（一段）、如何续接（三步以内）、边界、历史轮次表（轮 · 运行目录 · 范围 · 报告）。

`STEPS.md`（跨轮，只留仍有效的）：

```markdown
## 标准子步骤 · 蓝图 vK（上次校准：<run-id>）   每步一张表：ID / 子步骤 / 方法与验收
## 子代理配置                                领域 → 模型与 effort（谁哪天定的）
## 跨轮经验                                  每条一句：做法 + 依据（哪一轮发现的什么问题）
## 可复用工具                                脚本、调用方式、适用范围、最近验证
```

## 6. 证据的去留

- 调研文件、数值、精选图长期留；整套截图、比稿的原始批次、外部模型的日志不入库。各组截图的数值用 `scripts/collect.mjs` 并成一个文件（`evidence/before.json`、`after.json`）入库；外部模型的报告全文去掉内嵌图后存进 `evidence/`（原始批次不入库，报告才是证据）。
- 报告精选图：能说明一个审核点的前后一对就够，优先裁到部件；整屏图压到宽 1440 以内的 JPEG。
- 收尾时清掉临时脚本与调试输出；保留的每类证据在报告里写一句「留它做什么」。
- 不入库的原型与图（比稿区之外的临时位置）在 `00-log.md` 的「续接」里写绝对路径，换会话、换工作区还找得到。

## 7. 总报告 `99-report.md`

写给要批注的人：先结论（这一轮改了什么、用户的每条反馈现在怎样），再前后对照图，再比稿的结论与要用户定的事（每项推荐 + 默认），再未完成与待验，最后技能与蓝图的迭代。每节有稳定标题方便批注引用；按宿主协议的报告规范写（要求逐文件贴改动时照贴）。

走「先看稿」时，这份报告就是用户体验稿的地方，比稿那节放在结论后面、最显眼：每题现状 → 各方向的能点的稿（内嵌或链接 + 操作提示，截图辅助）→ 评分与共识分歧 → 推荐 → 要用户定的事。这时报告里没有「前后对照」，结论写成「还没改产品，等你定」。只交付建议时，比稿之后接工作包与决定项（§8）。

## 8. 工作包与决定项

没有实施授权、走轻量档，或用户定了但本期不做时，交这两样。

- **工作包**：每个能单独派给一个 agent。写范围、依据（审核点编号、规范节、决定编号）、具体改法、验收（外观 × 语言 × 宽度矩阵、要跑通的用户任务、要补的测试、要回到的数值）、别踩的线（铁律、必须保持原样的东西、不能碰的文件）。依赖用户决定的标「待定」并指向决定项。
- **决定项**：一项一个问题，给选项、推荐、理由与不回答时的默认。

## 9. 交接档

用户说「本期收尾、交给下一个 agent」时写，放在宿主交接规程指定的位置（如会话存档目录），写法照那个规程，内容至少有：

- 用户原话（本轮的反馈与验收批注，原样）与「我的读法」的确认结果
- 已定的事（决定编号）与已落地的改动（提交）
- 被否的方案与原因，免得下一轮重比
- 下一轮的题目、硬约束（含稳定项与会换项）、本期不做的工作包
- 可复用的工具（场景表、脚本、底图）与踩过的坑

证据留在运行目录，交接档链过去、不复制；`INDEX.md` 的「现在在哪」写明交接档的位置。
