# 专区：渲染性能（perf）

点名 `perf`，或完整一轮开审前读。看的是用户感受到的实时渲染表现：掉不掉帧、打开慢不慢、长时间玩会不会越来越卡。七步的细则在 round.md，试玩规程与脚本用法在 playtest.md，这里只写本专区自己的。

## 1. 审什么

- 高动效段逐帧看掉帧、真实试玩时的帧间隔分布 / 长任务 / 内存曲线、CPU 降速下的表现、原生壳上的测量（测法见 §5）。
- 打开慢不慢：用 round.md §1 的打开计时判。
- 和工程审核技能的界线见 SKILL.md「和别的技能怎么分」。

## 2. 规则库取哪几节

只跑本专区时按下面取；完整一轮照 rules.md 用法第 1 条挑，下面只当本专区的重点提示。

`rules.md` 的 T（T-01–T-08 为主）；有聊天的加 C-10；K 扫一遍。帧率、内存这类目标值照 playtest.md §2 从当轮资料与项目文档推出来，写清来源与适用前提。

## 3. 各步里做什么

- **点名本专区就走试玩这条线**，只走维度 P：一个循环是调研 → 性能 → 双代理验收（playtest.md §1、§4、§9）。完整一轮里走了这条线的，本专区放每个循环的最后；没走的，只做 round.md §1 的打开计时。
- **准备**：交互点清单里 `dimension` 含 P 的行，加上高动效段与最重的画面，列成测量场景；试玩适配照 playtest.md §3，测量构建照 §5 第一条。
- **调研**：标了每轮的两条照做（research.md §1）；测量工具与帧节拍的写法照 playtest.md §2 当场查，brief 用 `prompts/research.md`。
- **采证**：单跑本专区时不拍整套截图矩阵，只拍报告要用的现状图；先读实现列出假设，再在真实试玩时测；首次与之后分开、同机同条件、每组写明跑了几遍。
- **走查**：每条写证据等级（实测 / 静态 / 假设，playtest.md §4 第 4 步）；静态线索没实测到的不当结论报。
- **比稿**：一般不走 pitch.md；几种优化手段都说得通时做成真实变体、同条件测了再选（playtest.md §7）。

## 4. 验收口径

在 round.md §6 之上加看；完整一轮按本轮范围取，不强制逐条（双代理盲测那条除外，照 playtest.md §9）。

- 改前改后两份同样的测量构建、同一份场景、同机同条件，各跑至少两遍，首次与之后分开报；没达标的写在数字旁边。
- 改完同条件重拍胶片并排看（playtest.md §4 第 6 步）：优化没有换来看得见的退化。
- 没有真机或工具链的写清缺口与补测步骤，不拿桌面数字冒充真机结论；双代理盲测里偏老手那一位的性能数字并进对照。
- 双代理盲测：两位都认为（就本专区而言）可以上架，且本专区没有未处理的高优先级发现（playtest.md §9；条件不省，只对本专区下判断）。

## 5. 测法

最后做，先读实现列出假设，再**真实试玩时测**（`sampleStart / sampleStop` 采帧间隔、长任务、长动画帧与堆；`traceStart / traceStop`
录 DevTools trace，`scripts/trace-summary.mjs` 统计呈现 / 丢弃的帧与主线程长任务；`cpu` 步骤模拟降速）。
Web 与原生壳的测量工具、帧节拍与限帧写法都要按 playtest.md §2 当场调研；本机没有真机或工具链时写清缺口与补测步骤，不能拿桌面数字冒充真机结论。
优化前后同条件对照，证据进 `evidence/`。几条测法上的坑：

- **在接近上线的构建上测**：开发构建按需编译模块、代码未压缩，首次进入类的数字会被放大。项目的试玩钩子只在开发构建开时，
  加一个「性能测量构建模式」的门控（构建模式名作条件，普通生产构建里被静态删掉），在压缩代码上用同一套场景驱动。
- **首次与之后分开报**：同一会话里同一路径走两次。首次的冻结（模块、量字、贴图首传、着色器编译）是每会话一次，
  之后每次都有的才是常驻开销，两者的优化手段不同。
- **原生调用要追调用者**：采样里最贵的常是画布填充、纹理上传、量字这类原生函数，用 `scripts/cpuprofile-callers.mjs` 按调用链归到具体代码。
- **预热 / 缓存类优化用真实入口验证**：直接派发动作或写死参数会绕开「预先备好的那一份」，测出来像没效果。
- **原生热点要落到具体参数上**：调用链只能说明「是哪段代码在量字 / 传贴图」，说不出是哪几个字、哪张图。用 `scripts/native-timing.js`
  给原生量字与贴图上传接口挂计时、按参数汇总（字体 + 文字、贴图尺寸）；一次性的大头常常落在个别参数上，先看清再定方案，
  不要凭「总量大」就上最重的改法。
- **前后对照要同机同条件**：把改前的版本另建一份同样的测量构建，和当前构建同时起服务，同一份场景各跑至少两遍、不开 CPU 采样
  （采样器自己会拖慢）。隔了时间、机器负载不同的两组数字只能看方向，不能比大小；报告里写明每组跑了几遍。
