# 比稿规程

第 4 步执行前读。比稿解决「有两个以上说得通的做法」的设计点；规则与证据已经清楚的点直接改，不比。

目录：1 题目与方向 · 2 派谁 · 3 共同 brief · 4 稿要什么样 · 5 外部模型的参与 · 6 评审 · 7 归纳与决定 · 8 先看稿 · 9 常见的坑

## 1. 题目与方向

- **归并题目**：一个题目回答一组必须一起定的问题（比如「面板用什么载体」和「面板里怎么排」分不开，就是一个题目）。一轮通常 2–3 个题目，多了主线程看不过来。
- **每题 2–3 个方向**，要有实质差别（结构不同、立场不同），不是同一个方案换颜色。方向从调研的分歧、用户反馈的两种读法、设计系统里互相拉扯的原则里来。至少有一个方向是「最贴用户原话的读法」。
- 每个方向写清：一句话立场、必须自己解决的难点（这个方向天生的弱点）、不许回避的用户原话。
- **已经定了直接改的，写成各方向共同的前提**（「列宽放到多少」「窄的时候收起什么」），免得几份稿都在争不用争的事。
- **题目之间划清边界**：一题比版式、另一题比材质时，各自的任务里写明「另一样照现状画、不计分」；评审时再核两题的结论合不合（比如一边定了圆角气泡，另一边把气泡画成方角纸条）。

## 2. 派谁

| 题目的领域 | 模型与 effort |
| --- | --- |
| 界面结构、交互流程、信息布局 | 用户为「UI/UX」指定的模型，最高 effort |
| 概念、材质、光与渲染、角色与场景 | 用户为「概念 / 渲染」指定的模型，最高 effort |
| 评审、复审、实现 | 比出稿低一档即可；评审与复审用**没出过稿的新子代理**；材质与光的实现仍用「概念 / 渲染」那个模型 |
| 调研、提炼、拼对照板 | 主力模型常规 effort |

对应关系记在项目蓝图（`STEPS.md` 的「子代理配置」）里，用户改口就改蓝图。用户没指定时跟主线程同一个模型，报告里写明每个子代理实际用的模型与 effort。同一轮里出稿人互不通气；**下一轮换新的子代理**。

## 3. 共同 brief

所有出稿人读同一份，放在比稿区的主题文件夹里。固定七节：

1. 产品（两三句）与铁律。
2. 用户这次的反馈，原话；带定性评价的，附第 0 步翻好的可检查属性（「我把这句话读成了……」），用户确认过的写明。
3. 现状：截图清单（路径 + 每张是什么）、干净的背景图、实测数值。
4. 调研结论与分歧（指向证据文件，让出稿人按需读）。
5. 硬约束：平台与视口、材质与性能限制、字号与对比下限、目标尺寸、动效规矩、不能少的功能、可用的现成素材、不依赖新美术图；已定决定摘原文带编号。另有两条每轮都写：
    - **会换的东西只当风格参考**：第 0 步列出的会换项（场景与背景、镜头、主体的位置与朝向、色调、内容量）不能当布局与取色的依据——方案要在换一张背景、换一个机位、换一种外观后仍成立；出稿人至少交一张换了底图或外观的验证图。
    - **必须保持原样的清单**：既有的特殊样式、样板数据、文案逐项列出。只写「不得出现 X」不够，生图会把相近的既有样式一起改掉。
6. 交付物：原型放哪、怎么截图、外部模型的第二意见怎么拿、设计说明的固定结构、不许做的事（不改源码、不碰别人的文件、不做版本控制操作、不动主线程的浏览器）。走「先看稿」时原型就是给用户亲手体验的那一份，按 §8 的要求做。
7. 评判标准：五六个维度，每项 10 分。常用：回应反馈、产品气质（按第 0 步翻好的属性逐条打，比如「游戏化」拆成质感、层次、视觉冲击、反馈丰富度）、可用性、视觉质感、通用性（换背景 / 换机位还成立吗）、与现有系统的统一、可实现性。

每个出稿人的单独提示只加：编号、方向说明与难点、必须交的画面清单、回复格式。

## 4. 稿要什么样

- **可运行的原型**（网页产品是单文件 HTML，游戏是引擎里的样板场景或可交互图稿）叠在真实背景上，同一视口、同一份内容；用查询参数或开关切状态。
- **截图**由出稿人自己拍、自己看，改到满意；主图一张，状态图若干，命名带编号。
- **设计说明**固定结构：一句话概念 → 布局与尺寸表 → 各状态 → 动效（起止、时长、低动效）→ 其它外观 / 主题怎么取值 → 落到现有代码要改哪里、难点 → 外部模型的意见与采纳 → 自审评分与最弱的一点 → 要图清单。
- 必须交的画面要覆盖：默认状态、用户点名的那个部件打开时（如表情面板）、更窄与更宽的视口、同一套语法下的其它面板、换了底图或外观的那一张（§3 第 5 节）。
- **原型要能点**：关键交互（打开、切换、关闭、展开）真的能操作，状态能切，内容用真实长度；文字线框不算稿。没有出图工具不影响出原型；连原型也做不出的方向，用标注截图说明并写明不是稿。
- **交稿逐格核对**：生图或改图的稿，主线程逐格对照现状与「必须保持原样」清单——错字、改了样板数据、改了既有样式都算走样，走样不计入方案分，记下来退回。

## 5. 外部模型的参与

有出图 / 审图工具技能时（如 `codex-visual`），每个设计点都让它参与，分两处：

1. **出稿阶段**：每个出稿人把主图交给它审一次（审图模式，带背景图做参考，brief 里写清产品、要解决的反馈、硬约束、评判维度），读报告、改一轮，把意见与采纳写进说明。
2. **归纳阶段**：主线程把各方向的主图一起交给它比一次（比稿模式，一次不超过它允许的图数），拿它的排名与理由，和互评并列。

需要概念图或材质气氛图时再用它的出图模式。先看额度：不足时按那个技能的规矩处理，不绕过；外部模型的结论是一票，不是裁决。

- **开工时先让它冷读一遍现状**（第 1 步采证之后）：把改之前的关键截图交给它审，只给产品、用户原话与硬约束，不给主线程的判断。它的发现和主线程的走查并列进审核点；两边重合的是硬问题，它多看出来的另起编号。
- **它的额度是另一本账**：有自己的用量窗口，和主线程的窗口不对齐，一轮里可能撞好几次。它的步骤单独排：出稿期每人一次、归纳期每题一次，撞到上限就欠着、写进断点、恢复后由主线程补跑（出稿人已经结束也没关系，主线程拿它的主图去审）。
- **一次调用能附的图有上限**（含参考图），超了包装脚本直接拒绝：brief 里写明张数。截图多于上限时，把次要的屏拼成一张并加标签条，brief 里写明标签条不是界面。

## 6. 评审：独立评审人，或互评

全部交稿后要有人把几份稿放在一起比。两种做法，按情况选：

**独立评审人（默认）**：每题派一位**没出过稿**的新子代理，给它共同 brief、每份稿的说明与全套截图、改之前的现状、调研与外部模型的意见，要它交一份评审文件：

1. 评分表：每份稿 × 每个维度，每格一句依据并指到图；另一题管的东西（如材质）不加减分。
2. 把题目拆成子问题逐个比：每个子问题谁的做法最好、为什么、另外几家差在哪。
3. **事实核查**：去代码和决定清单里核——稿里出现的东西是不是真数据、真功能；有没有违反硬约束与铁律；和哪条已有决定冲突（列编号）。出稿人既会画出不存在的数据，也会把真数据当成造假删掉，两种都要查。
4. **可行性**：每份稿的关键做法落到现有代码改什么、难点、对速度与逐帧开销的影响；稿里没写到的实装坑。
5. **通用性（必答）**：换一张背景、换一个机位、换一种外观，这份稿还成立吗——看出稿人交的验证图，没交就自己把原型换底图看一次；哪部分是绑在当前画面上的（取色、留白、位置），逐条写出。
6. **用户原话里的量**：做一张数值对照表（面积、条数、毫秒……），改版前 / 现在 / 每份稿。经常会发现几份稿在这个量上其实一样，真正的差别在别处——那才是该比的。
7. 推荐：选一份或给混合方案（按子问题写清用谁的、统一规则是什么）；实施前必须先验证的几件事；要用户定的事（推荐与默认）。

**互评**：把别人的主图、状态图与说明发给每个出稿人（它还在就接着发，结束了就起一个带原方向说明的新子代理），只评别人：按共同标准逐项打分；最强的一点、最要命的问题；自己的方向能从它那里借什么。互评的好处是每个人最懂这个问题，坏处是没人去查事实、而且要把每个出稿人再叫起来一次。方向只有两个、或想看出稿人之间怎么互相借鉴时用它。

## 7. 归纳与决定

主线程自己打开每一张主图看，不只读说明。产出写进本轮的 `02-pitch.md`：

```markdown
## <题目>
| 方向 | 出稿人（模型·effort） | 主图 | 体验稿（原型路径 · 报告里的位置或页面地址） | 自评 | 评审（或互评均分） | 外部模型 | 主线程 |
共识的优点 / 共识的问题 / 分歧在哪
结论：采用哪个，或怎么混合（从谁那里拿什么）、放弃了什么、为什么
要用户定的事：每项给推荐与不回答时的默认
用户批注（走「先看稿」时）：定了哪个方向、改了什么、还要再出一版的地方
被取代的旧决定：编号与新说法
```

- 评审与互评里引用的规范条文，主线程逐条打开原文核对，核不上的不采信。
- 推荐要回到用户原话逐句对一遍：哪句话由方案的哪一部分回答；原话里带量的（大小、快慢）用数值对，别只看观感。
- 互不通气的出稿人走到同一个结构，是比分数更硬的证据；外部模型的排序和互评不一致时两边都记下，先按证据更足的一边做，把分歧留成下一轮的题目。
- 混合方案要说清骨架来自谁、部件来自谁，避免拼出两套语言：先写「统一规则」（几种材料、凭什么是一家、哪条规则管所有部件），再写逐件用谁的。**混合方案没有任何一份原型长那样**——实施出来的第一版就是它的第一张稿，主线程与复审要把它当稿再审一遍。
- 分数很接近时（三份只差一两分），别按最高分选：找出那一个真正的分歧（「亮还是暗」「多出来的地方给谁」），围绕它做决定，并把另一种做法留作要用户定的事。
- 之后按第 0 步定的走法：直接实现就按推荐做，决定清单随报告给用户批注，批注改了决定就按批注再改；先看稿就按 §8 把稿交给用户体验；只交付建议就出工作包与决定项。
- 比稿材料（brief、原型、图、说明）在定案前留在比稿区的主题文件夹；定案后由设计技能把最终规范与选定展示写进设计系统的常驻文档，再按它的「比稿定案」规则把这一轮清出设计系统（落选稿的 log 移档，其余删除）。审核里不提前改定稿。

## 8. 先看稿：把能点的稿交给用户体验

改动面大、会上生产，或用户说要先看稿时走这条。目的是让用户**亲手用过**再定方向，免得没看过的改动推上生产再返工。

- **交什么**：每个方向一份原型，推荐的混合方案也单做一份（混合方案没有任何一份原型长那样，不做就等于让用户凭想象定）。原型照 §4：能点、能切状态、真实长度的内容；同一视口、同一份内容，方向之间只差在要比的地方。
- **怎么放进报告**：原型随批注报告页一起发布（作报告的附属页面，或各自发成页面），按批注报告技能的做法挂批注层，让用户能在稿上直接批注。报告里每题一节：现状截图 → 每个方向一块（一句立场、内嵌框或「打开体验」链接、一行操作提示：点哪里、看哪几个状态）→ 评分与共识分歧 → 推荐 → 要用户定的事（推荐 + 不回答时的默认）。截图放在内嵌框旁边当辅助，不替代原型；内嵌框在窄屏上放不下的，给链接。
- **原型放哪**：比稿区的主题文件夹，不放产品源码目录；`02-pitch.md` 的表里写原型路径和它在报告里的位置。
- **定稿之前**：不动产品代码、不合并、不推生产；第 5 步的实施子代理也不派。用户没回的题不按推荐先做。
- **用户批注之后**：定了的方向写进 `02-pitch.md` 的「用户批注」与项目的决定清单，再进第 5 步；没定或要改的，按批注再出一版稿、再发一次，不另开一轮。实施出来的第一版仍当稿再审一遍。

## 9. 常见的坑

- 方向只差在皮上：互评会一致指出「其实是一个方案」。派之前自查每个方向的结构差别。
- 稿子好看但内容是假的：要求用真实文案长度、真实状态（空、长文本、错误、未读）。
- 出稿人各自把背景截了不同的时刻：背景图由主线程先备好，统一路径；发出去之前自己打开看一遍（隐藏界面的样式没盖全，底图里会带着旧界面）。
- 只评主图：窄视口与部件打开的状态才是出问题的地方，评审要看全套。
- 稿里的数据没人核：出稿人不读后端，画出来的「对方在线」「有一条新消息」可能不成立，反过来也会把真功能当假的删掉。评审任务里写明去代码里核。
- 自评都偏高（普遍比评审高 5 分左右）：自评只用来看出稿人认为自己最弱的是哪一点。
- 外部模型打分普遍偏高或偏低：只看它的排序与指出的具体问题，不直接比绝对分。
- 稿是照着当前那张背景调出来的：取色、留白、位置都贴着这张画，换场景就散。brief 写明会换的东西，评审必答「换了还成立吗」。
- 只交了截图就让用户定：用户没法体验交互与节奏，定下来的方向上线后常要返工。走「先看稿」时交能点的原型。
