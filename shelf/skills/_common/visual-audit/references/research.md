# 调研：通用规则与目标产品的定制调研

第 2 步执行前读。调研的产物是证据文件，不是印象；主线程只读每份的结论节。

## 1. 几条线

每轮都重新定线，下面是常用的五条，按本轮反馈集中的地方增删。一条线一个子代理、一个文件，同时派出。

| 线 | 回答什么 | 什么时候必做 |
| --- | --- | --- |
| 通用规则复核 | [rules.md](rules.md) 里本轮要用的关键条目现在还成立吗、有没有新版本（指南改版、标准更新） | 每轮；规则库已有时只核关键条目与缺口，不重做全表 |
| 领域心理与质感 | 这类产品的用户要什么感受、什么让它显得有质感 / 廉价（游戏感、cozy、陪伴、专业工具感……按产品类型） | 产品类型第一次审，或上一轮超过半年 |
| 界面类型专项 | 用户反馈集中的那类界面（聊天、播放器、设置、商店、HUD……）成熟产品怎么做：呈现模式、布局数值、状态 | 每轮按反馈定 |
| 材质与组件专项 | 本轮要重做的视觉部件（浮层材质、阴影层级、卡片、小组件）的做法与可直接用的数值 | 反馈里有「丑、没质感、单调」时 |
| 同类产品横向 + 纵向 | 同类产品此刻的界面与口碑；相对本产品上一轮调研的变化；本产品该向哪一类靠 | 每轮必做 |

## 2. 给调研子代理的 brief

每份 brief 写清七件事，缺一件子代理就会按通用口味发挥：

1. **角色与任务**：一句话说它是哪方面的研究员、要产出什么。
2. **产出文件**：项目内的确切路径，只写这一个文件；不改代码、不做版本控制操作。
3. **产品背景**：两三句讲清产品是什么、目标平台；纵向线要给上一轮调研的路径让它先读。
4. **用户的反馈**：和这条线相关的原话，原样给。
5. **现状细节**：这条线要用到的尺寸、布局、截图路径（让它知道在评什么）。
6. **必须覆盖的清单与要回答的问题**：具体到产品名、指南名、问题编号。
7. **方法要求**：打开原文核验；只凭搜索摘要或记忆的标 UNVERIFIED；量不到的数值写「未取得」，不编；评论与原文只转述；区分有来源的规则与自己的推断；给出文件结构；回复只要路径、UNVERIFIED 数量和最重要的几条。

调研用主力模型的常规 effort 即可，不必用最高档；一条线的范围控制在一个子代理半小时内能查完。

## 3. 证据文件的写法

```markdown
# <主题>（检索日期）
## 说明          方法、样本限制、UNVERIFIED 数量
## 对比表 / 规则表   一行一条：结论 | 怎么检查或适用前提 | 来源标题 + 直接 URL | 对本产品的转译
## 要回答的问题    逐个作答，带数值与来源
## 对本产品的结论   推荐的方向（2–3 个及取舍）、按影响排序的建议
## UNVERIFIED 与缺口
```

- 链接直指原文，不指搜索结果页；官方站点抓不到正文时找它的数据源或官方仓库文档，并写明。
- 「对本产品的转译」要具体到界面与数值，但标明是推断。
- 用户评论、评测只转述主题并附直达链接；样本小要写明。

## 4. 主线程怎么用

- 读每份的「结论」与「建议」，把建议逐条挂到审核点上（哪条规则支持哪个判定）。
- **两份调研结论相反 = 一个比稿题目**。把分歧原样写进比稿的共同 brief，让出稿人各自去证明。
- 调研建议不是决定：和产品铁律、用户最新的话冲突的建议，记下来、不采纳、写原因。
- 这一轮查到的、跨项目成立的新规则，收尾时续编号加进 [rules.md](rules.md)（改技能本体按技能的修改规矩）；项目特有的结论留在运行目录。

## 5. 共用浏览器的注意

子代理如果能用到主线程的浏览器面板，会把主线程开着的页面导航走。brief 里写明：调研只用搜索与抓取工具，不动浏览器面板；确实要截图就用无头浏览器自己开。
