## 1. 什么时候走这条线

截图矩阵回答「看起来到不到位」，回答不了「点下去第几帧有反馈」「连点会不会吞」「庆祝那一下掉不掉帧」。出现下面任一情况就加走这条线，和 SKILL.md 的七步并行，产物进同一个运行目录：

- 产品是游戏，或界面的价值主要在动效、反馈与手感上；
- 用户的反馈指向交互、特效、动效、卡顿、掉帧；
- 上架前要一次「真的有人玩过」的验收；
- 点名了 `fx`、`motion`、`perf` 专区（只走对应的维度）。

它插在七步的这些位置：第 0 步加交互点清单与试玩适配（§3）；第 1 步除截图矩阵外做摸底试玩与逐帧取证（§5）；第 3 步的审核点按维度推进（§4），试玩与胶片的发现并进走查来源；第 4 步代码驱动的方案做成真实变体再比（§7）；第 6 步加双代理盲测验收（§9）；性能放在每个循环的最后（§6，测法在 `zone-perf.md`）。

玩法规则、存档结构、经济数值不在范围内，碰到了只记待办。用户要求「优化」只授权非破坏性改动：不违背功能文档、不改玩法行为、贴近现有设计系统；破坏性改动（违背功能文档、改变玩法或数据、推翻用户记录过的决定、删除用户可见功能）只出方案，写进总报告等用户看过再做。

## 2. 知识当场查

「该多快、该多弹、该多大、同类产品怎么做、哪个工具怎么用」这类知识，每一轮都当场上网查：官方文档与工具、最新论文、同类产品，打开原文核对后记进本轮运行目录，带链接与检索日期（brief 模板 [../prompts/research.md](../prompts/research.md)）。上一轮查过的只能当线索。从资料里推出**本项目适用的检查问题与目标**，写清来源与适用前提，不照抄数值。项目自己的设计系统、功能文档与用户决定是项目数据，以它们为准。

## 3. 准备：交互点清单与试玩适配

1. **交互点清单**（运行目录里的 `touchpoints.csv`）：从入口代码遍历每个画面 × 每个可交互元素 × 每个反馈事件（按下、抬起、选中、输入、错误、完成、转场、弹层、加载、空态、长内容、低动效）。这是全盘覆盖的分母。

```text
id,screen,element,trigger,feedback,dimension,code,film_before,film_after,status,finding,note
```

- `trigger`：按下 / 抬起 / 点按 / 长按 / 拖动 / 输入正确 / 输入错误 / 完成单元 / 通关 / 失败 / 进场 / 离场 / 弹层开 / 关 / 切后台 / 低动效 等
- `feedback`：现有反馈的一句描述（视觉 / 声音 / 触觉分开写）
- `dimension`：U / V / I / P，可多选用 `|` 分隔
- `code`：实现位置（文件:行）；`film_*`：胶片证据路径
- `status`：待查 / 已查无问题 / 有发现 / 已改 / 不适用（写原因）
- 覆盖率 = 已查行 / 全部适用行；分母来自遍历入口代码，不是凭印象列

2. **试玩适配**（项目的 `AUDIT_DIR/scripts/`）：怎么启动、怎么到达每个画面、调试钩子、在节点树里找元素的探针、试玩场景 JSON（`scenarios/`）、存档预设。写完用 `scripts/play.mjs` 跑通一次冒烟。
3. **摸底试玩**：像第一次打开的玩家一样把主流程走一遍并截图，记第一眼观感（只是候选，不直接当结论）。

## 4. 按维度推进

一个循环 = **调研 → 界面 → 特效视觉 → 交互手感 → 性能 → 双代理验收**。验收发现新问题就开下一个循环，直到两位验收代理都认为可以上架、且没有未处理的高优先级发现，或用户给的额度与时间用完（如实写明停在哪）。

每个维度同时用两种审查方式，可以混合：

- **读实现**：样式与布局代码、主题 token、游戏物体的变换与补间、粒子与特效节点、着色器与滤镜、帧循环与渲染开关。
- **真实试玩**：模拟真人（犹豫、误触、连点、快速连填、中途退出、切后台、长时间游玩），在每个交互点上逐帧取证。

每个维度的步骤：

1. 刷新基线：拉集成分支看有没有别人的大改；记本维度的覆盖面（交互点清单里归它的行）。
2. 当场调研（§2），记进 `evidence/research-*.md`。
3. 读实现 + 试玩取证：逐个交互点过一遍，静态与动态证据对上；要看动效的一律出逐帧胶片（§5）。
4. 记发现：进审核点与 `FINDINGS.md`，写位置、证据等级（实测 / 静态 / 假设）、对玩家的影响、对照的设计系统条款、验收条件（可复跑的场景 + 看什么）。
5. 比稿定方案（§7），每条决策一张卡（§8）。
6. 实施：非破坏性的直接做；破坏性的只写决策卡标「待用户 review」。改完同条件重拍胶片做前后对照。
7. 回归：跑项目自己登记的类型检查 / lint / 测试命令（包管理脚本、CI 里那一条），不自拼编译器参数——用项目引用组织的仓库里，对根配置直接跑可能一个文件都不查、照样「通过」。动了共享层级就把弹层清单全跑一遍；低动效模式各跑一次。
8. 独立复审：派子代理（只给代码与胶片，不给结论）找遗漏和失真，修到一轮没有新的可改项。
9. 提交：本维度的改动与报告一个可独立验收的提交，更新本轮日志的进度与续接。

各维度的关注面写在专区文件里（问题从调研里来，那里只列面）：U 界面 → `zone-ui.md` §1，V 特效视觉 → `zone-fx.md` §1，I 交互手感 → `zone-motion.md` §1，P 性能（最后做）→ `zone-perf.md` §1。

只跑部分专区时，一个循环里只走对应的维度，其余照旧：调研、双代理验收与循环收口的条件都不省，收口条件只对本轮专区下判断。

## 5. 逐帧取证

`scripts/play.mjs` 的 `film` 步骤：注入的虚拟时钟（`vt-shim.js`）冻结页面时间，在指定帧做真实触控，
每推进一帧截一张，拼成带帧号 / 毫秒 / 「与上一帧的变化量」的胶片图。看胶片时逐帧回答（具体阈值来自本轮调研）：

- 按下后第几帧开始有反馈？有没有「死帧」（应该在动却没变化）或「跳帧」（一帧内变化突然很大）？
- 曲线的起势、峰值、回落与稳住各在第几帧？峰值是否被遮挡、裁切？终态有没有残留或闪烁？
- 连续触发、中途打断、低动效模式下分别长什么样？

覆盖要求：交互点清单里每个带动效的行至少一张胶片（改前 + 改后）；做不到的写原因。用法与场景 JSON 写法见 §10。

## 6. 性能

最后做。测法与踩过的坑在 `zone-perf.md` §5：先读实现列出假设，再真实试玩时测，优化前后同条件对照，证据进 `evidence/`。

## 7. 方案先做成真实变体再比

- 一个可优化点至少两个方案（含「保持现状」），交出图工具技能出图或审图对比；模板 `prompts/compare.md` 写明要附上的截图 / 胶片、
  设计系统条款与评判维度。
- **方案先做成真实变体再比**：代码驱动的界面与特效，在开发构建里加比稿开关（URL 参数切换），同条件逐帧拍每个变体，
  拿真实胶片去比，比纯效果图更贴近玩家看到的东西。**开关的缺省值必须是当前采用的方案**：定案那一刻就把缺省值改成胜者，
  旧方案只留在显式参数后面；否则不带参数的构建（含生产）跑的还是旧版。比稿补跑完、确定不再回头后删掉落选分支。
- 选择理由必须落到证据与条款上；每条决策一张卡（§8），总报告逐卡呈现。

模板 [../prompts/compare.md](../prompts/compare.md)。出图额度耗尽或调用失败时不中断审查：先用占位（几何占位、现有素材调色或程序绘制），把需求记进本轮 `evidence/image-requests.md`（用途、尺寸、风格约束、占位方案、优先级），总报告里集中向用户申请额度。

## 8. 记录格式：决策卡、试玩记录、子步骤编号

**决策卡**（每个可优化点一张，总报告逐卡呈现）：

```text
决策 D<循环>-<序号> · <交互点 / 画面>
问题与证据：发现 ID，改前胶片 / 截图
候选方案：A 保持现状 / B … / C …（每个一句话 + 比稿图路径）
比稿：出图工具技能的任务与结论摘要（或额度不足时的替代评审）
选择：<方案> —— 理由落到：证据里的问题是否解决、设计系统条款、性能与实现代价
设计系统：对照的条款；偏离时写为什么
功能文档：是否触及；破坏性？是 → 只出方案，标「待用户 review」
实施：提交 / 文件；改后胶片与前后对照
验证：类型检查 / 测试 / 弹层清单 / 低动效 / 性能
```

**试玩记录**：

每次试玩一段记录：

```text
场次 / 人设（新手首玩、老手速通、误触型、中断型 …）/ 场景文件 / 构建与提交 / 视口与输入
做了什么（步骤）/ 卡住或犹豫在哪 / 惊喜与失望 / 发现 ID / 证据路径
```

人设与任务从产品的真实玩家里来（功能文档、用户说过的目标玩家）；每个循环至少一次「不看代码、只看画面」的纯玩家视角试玩。

**子步骤编号**用 `C<循环>-<维度><序号>`：维度字母 R 调研 · U 界面 · V 特效 · I 交互 · P 性能 · A 验收（如 `C1-V03`）。发现的稳定编号按维度分前缀时沿用同一组字母（`XU`、`XV`、`XI`、`XP`）；项目已有编号体系就沿用它。本轮日志比 [records.md](records.md) §2 的骨架多一节「循环记录」（每循环一节：子步骤表、改了什么、验收代理结论、下一循环要做的）。

## 9. 双代理盲测验收

每个循环结束，派**两个互不通气**的试玩代理（模板 `prompts/playtester.md`），各自从玩家视角完整试玩（一个偏新手首次体验，
一个偏老手高频操作 + 性能监控），只给运行方法与试玩适配说明，不给本轮的结论。第二轮起提示词不变（照样盲测），
只多一步：自己的问题清单写完之后，再对照上一轮报告逐条标「已解决 / 还在 / 变了样」，回归和新问题都不漏。
只跑部分专区时照样盲测：「必须覆盖」写成这些专区会出现的流程，不说审的是哪个专区（说了代理只往那里看）；汇总时别的专区的问题只记一句，不进下一循环。
验收期间不改被测构建的源码（热更新会把正在玩的页面刷掉），文档与技能可以照常写。汇总两份报告：新问题进下一循环，
双方都认为可上架、且本轮没有未处理的高优先级发现时，才进入收口。

模板 [../prompts/playtester.md](../prompts/playtester.md)。派子代理时给它摘录、路径与产出文件位置，写明它能改哪些文件（多数只读）；产出写进运行目录才算完成，结论由主线程核对后才进报告。

## 10. `scripts/play.mjs` 用法

```bash
node <技能目录>/scripts/play.mjs <场景.json> <输出目录> [--url <地址>] [--chrome <exe>] [--headful] [--keep]
```

场景 JSON 写在项目 `AUDIT_DIR/scripts/scenarios/`，步骤清单见脚本头部注释。要点：

- 坐标是视口 CSS 像素；`viewport` 缺省 390×844 @3x 手机触控。画面布局随视口变的项目，坐标按场景里的视口量。
- `film`：`frames` × `dt`（缺省 1000/60）；`do: [{at: 1, tap: [x, y], hold: 80}]` 在第 1 帧点按；`clip` 只截局部、`scale` 控制每格大小；
  输出 `<名>.png` 与 summary 里每帧的变化量（变化像素 %）。变化量序列能快速看出死帧（连续 0）与跳变（单帧尖峰）。
- `probe: '表达式'` 每帧推进后求值，按帧记进 summary：缩放、位移、透明度这类动画曲线直接读数，比看图准、也省（胶片图很大时配 `noShots: true` 只记数）。
  用它能看出「按下后第几帧才动」「打断时速度是否连续」这类看图看不清的问题。
- 坐标与截图区域可以写成页面里求值的表达式（`tapAt` / `downAt` / `clipAt`），配项目场景目录里的探针（在节点树里找格子、按键、文字），排版变了也不会点偏。
- 冻结只管 `performance.now` / `Date.now` / rAF / 定时器；CSS 动画、Web Audio 时钟、Worker 不受控，胶片里出现时要注明。
- 宿主自带的浏览器面板在手机视口模拟下，截图坐标可能与视口不一致（截图更宽、点击会偏）；系统性试玩与取证用本脚本，面板只留给用户旁观。
- 实时采样：`{sampleStart: {counter: '<累计渲染帧数的表达式>'}}` … `{sampleStop: '名'}`，按需渲染的引擎一定要给 counter，否则只量到 rAF 节奏。
  给了 counter 时结果里有 `renderDeltaMs` 与 `gapsByVsync`（每次真渲染隔了几个 vsync 的计数）：「该连续动的时段里出现 3 个以上 vsync 的间隔」就是吞帧或节拍不均。
  浏览器 trace 的掉帧判定未必覆盖「应用自己跳过没画」的帧（每轮按当前浏览器版本调研核实），所以按需渲染的项目要在应用里量。
- trace：`{traceStart: true}` … `{traceStop: '名'}`，再用 `scripts/trace-summary.mjs <名>.trace.json` 出统计；trace 也能拖进 DevTools Performance 面板看。
- CPU 采样：`{profileStart: true}` … `{profileStop: '名', top: 12}`，summary 里是自耗时最高的函数；要知道原生调用（画布填充、纹理上传、量字）是谁调的：
  `node <技能目录>/scripts/cpuprofile-callers.mjs <名>.cpuprofile <函数名> [向上层数] [--top N]`。
- 原生调用按参数归因：场景的 `inject` 里加上 `<技能目录>/scripts/native-timing.js`，在要测的动作前 `{eval: "__nativeTiming.start()"}`、
  之后 `{eval: "__nativeTiming.dump(20)", as: "名"}`；结果按「字体 | 文字」列出量字耗时、按「宽×高」列出贴图上传耗时与总像素数。
  它和 CPU 采样互补：采样给调用链，这个给参数。配合 `{cpu: 倍数}` 用，数字随降速放大。
- 切场景一类测量：每次切换前 `sampleStart` + `profileStart`、等稳定后 `sampleStop` + `profileStop` 各自成段，同一路径排两次区分首次与之后。
- 原始证据（截图、胶片、trace、cpuprofile、堆快照）只留本机，按扩展名写进项目 `AUDIT_DIR/.gitignore`；summary / sample JSON 入库。
- 每次运行是全新的浏览器配置（无存档）；需要存档预设时在 `inject` 里写「只在首次加载时写入 localStorage」的代码，或用项目的调试钩子推进。
- 测性能用 `--headful` 或确认无头模式走的是真 GPU（场景里求值 `WEBGL_debug_renderer_info`），并把渲染器写进证据。
