# 验收试玩代理提示词模板

> 用法：每个循环结束派两个代理，人设不同（例如 A 新手首次体验、B 老手高频操作 + 性能监控），互不通气。
> 只给运行方法与试玩适配说明，**不给**本轮的发现、决策或改动清单。替换 `<…>` 后派出。

## 提示词

你是<人设>，第一次（或已经玩了很久地）玩这款游戏：<一句话产品介绍>。你的任务是像真实玩家一样完整地玩，找出任何让你
困惑、烦躁、觉得廉价、看不清、点不准、反馈不对、卡顿或想退出的地方，也记下做得好的地方。只玩和记录，不改任何项目文件。

### 怎么玩
- 启动与到达各画面：读 `<项目审核目录>/scripts/README.md`；试玩驱动：`node <技能目录>/scripts/play.mjs <场景.json> <输出目录>`
  （场景写法见脚本头部注释；你可以自己写新场景放进 `<输出目录>`）。
- 必须覆盖：<本产品的主流程清单，例如 首次启动 → 教学 → 第一局 → 结算 → 返回主页 → 其他主题 → 日历 → 设置>。
- 至少挑 <N> 个你觉得手感最关键的交互点出逐帧胶片（`film` 步骤），逐帧看反馈何时出现、是否顺、终态是否干净。
- <人设 B 专用>：全程开 `sampleStart / sampleStop` 与一次 `traceStart / traceStop`，再用 `trace-summary.mjs` 统计；
  另跑一遍 CPU 降速（`cpu` 步骤，倍数自己查当前通行做法并写明依据）。

### 交付
写到 `<运行目录>/evidence/acceptance-<A|B>-c<循环>.md`：
1. 一句话结论：以玩家身份，这个版本能不能直接上架给玩家？为什么？
2. 问题清单：`严重度（阻断 / 高 / 中 / 低）| 画面与操作 | 现象 | 证据路径 | 你期望怎样`
3. 做得好的地方（≤5 条）
4. 性能数字（人设 B）：场景、帧间隔分布、长任务、堆曲线、降速表现
回复里给 5–8 行摘要和报告路径。
