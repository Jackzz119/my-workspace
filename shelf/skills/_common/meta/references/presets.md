# 预设工作流

> 什么时候读：选了默认以外的一套，或用户问「这个任务用哪套」。只读用到的那一节。
> 每一套都沿用 SKILL.md 的常设规矩、阶段一的方案批准、阶段四的轮数上限和阶段五的收尾，下面只写差别。

## 0. 怎么选、能不能叠

先问五句，第一个答「是」的就是起点：

1. 要交一个大成品，用户打算一轮一轮看成品、在报告上批注改到满意？→「分区迭代」（里面每区的活仍按默认或并行开发的规矩做）。
2. 不知道该做成什么样、或者不知道哪里坏了？→ 做什么不清楚用「先调研」，几种做法要挑用「比稿」，毛病根因不明用「排查」。
3. 同一种改动要做很多处？→「铺开」。
4. 拆得成互不碰文件的几块，而且接口现在就能定？→「并行开发」。
5. 一两个文件、一两句话说得清验收？→「小任务」。

都不是 → 默认。另外两个是**加在别的上面**的：错一点代价大（金额、权限、安全、数据迁移）叠「先写测试」；用户不在、要跨额度窗口叠「长跑」。已经有一批改动要把关的直接用「评审修复」。

可以首尾相接（先调研 → 默认；排查 → 默认；比稿 → 并行开发），每段之间都有一个用户点头的节点，下一段的会话在那一轮里开。不要三套以上叠在一起。

给用户推荐时说三句：推荐哪套、为什么不是默认、预计开几个会话；另给一个备选。

## 1. 小任务

- **适合**：改动集中、上下文主会话已经有了、验收一两句说得清。
- **不适合**：要读很多代码才能动手的；你已经试过两次没做对的（换默认，让干净的会话做）。
- **怎么走**：要求和验收用一两句复述，没有歧义就当场开工，不再等第二次点头 → 同一轮开好测试会话待命 → 主会话自己写、自己提交 → 测试会话按验收黑盒验 → 打回就自己改。不约额度唤醒。
- **差别**：没有开发会话；测试会话仍然不看你的说法。改完再小，也不由自己放行。
- **会话**：1 个。

## 2. 并行开发

- **适合**：2–4 块，文件不重叠，接口、类型、共享约定能先定下来。
- **不适合**：强耦合；都要改同一份迁移、锁文件、路由表、词典的；后一块要看前一块结果的。
- **怎么走**：
  1. 主会话列每块的文件清单，两两比；有交集的归到一块。接口写进方案当合同。
  2. 公共骨架先由一个会话做完、验过、合进主会话分支；其余的从这个提交切。
  3. 各块并行，各有自己的验收；各块测试可以共用一个测试会话按块先后验，块大的才各开一个。
  4. 一块一块并进主会话分支（串行，由主会话或集成会话做，不让几个开发会话互相合）。冲突的语义拿不准，问造成冲突的两边各一句，由主会话定。
  5. 合在一起整体验一遍：字段名、权限、错误形状、加载顺序这些拼接处优先。
- **差别**：多了「先公共」和「整体验收」两步；设计问题只有主会话一个决定者。
- **会话**：开发 2–4 + 测试 1–2 + 可选集成 1，同时在跑的不超过 5 个。

## 3. 先调研

- **适合**：规格不清、陌生的代码或外部系统、要比较几条路再定。
- **不适合**：规格已经给全（瓶颈在实现，直接默认）；一个子代理半小时能查完的。
- **怎么走**：把问题拆成 2–4 个互不重叠的问题，各开一个只读会话（或者用户不需要看见的，用子代理）→ 交回结论、出处、否掉的路 → 主会话合并、核对互相矛盾的说法、亲自打开最关键的几处出处 → 出方案给用户定 → 接默认或别的。
- **差别**：前面多一段；调研结论要你直接读的，可以让调研会话出页、链接收进方案页；调研会话不改代码，可以共用检出、effort 可以低一些；结论写进台账和报告，实现阶段的说明只带结论。
- **停**：每个问题写明「答到什么程度算完」，到了就停，不为查全而查。

## 4. 评审修复

- **适合**：已经有一批改动或一个 PR；接手别人的代码；合并前把关。
- **不适合**：想靠多找几个评审当保险（同样的评审叠加没用，要叠就叠不同的视角：正确性、安全、性能、用起来）。
- **怎么走**：评审会话看 diff 和要求，假定里面有错，每条发现给具体的错误输入与结果 → 主会话筛一遍（成立 / 不成立 / 不归这次）→ **一个**会话一次改完成立的 → 同一个评审会话只复核上一轮的发现和新改动。
- **差别**：评审代替测试当第一道；改了行为的，后面仍接一次独立测试。
- **停**：没有「挡住」级的就停；最多三轮；复核轮不再翻首轮就在的老代码。

## 5. 比稿

- **适合**：做法差别大、好坏要看到东西才知道：设计、交互、架构、性能方案。
- **不适合**：验收已经能机械判定、做法差不多的（直接默认）。
- **怎么走**：先和用户定评判标准（写成几条能看、能量的）→ 2–3 个会话拿一样的要求、**不一样的出发点**各出一版（原型、截图或最小实现），各自写明代价 → 主会话把同一组检查跑在每一版上、并排放进报告（每一版要你点开细看的，可以让那个会话自己出页，链接收进总报告）→ **用户挑**，或挑一版再借别版的某一点 → 选中的那版接默认做完，没选的分支按收尾清单清掉。
- **差别**：不由 agent 当裁判选优胜；能跑的检查（测试、量测）只用来淘汰。
- **会话**：2–3 个，看完就停，没选中的不再往下做。

## 6. 排查

- **适合**：根因不明、单个会话已经卡住、说法好几种。
- **不适合**：能直接复现、一眼看得出来的；一串相关的失败（先合起来看是不是同一个因）。
- **怎么走**：主会话先要到稳定的复现（复现不了先补观测）→ 列 3–5 个互斥的假设，每个会话领一个，任务是**推翻**它，交回支持与反对的证据 → 没被推翻的那个，由**没参与的**会话或主会话独立复现一遍 → 定位成立才进默认去修，复现步骤就是验收第一条。
- **差别**：调研阶段禁止改代码；单个会话找到一个像样的解释就会停，所以要让别的会话来反驳。
- **停**：全被推翻就把证据摆给用户，别硬选一个最像的去修。

## 7. 铺开

- **适合**：同构、能机械判定对错、量大：迁移、批量替换、全站改同一种写法、全量盘点。
- **不适合**：每一处都要判断的；没有对照（旧实现、基线输出、类型或测试）的。
- **怎么走**：主会话先亲自或派一个会话**试跑 1–3 处**，把规则、例外、自查命令写成一页 → 用户看过 → 按目录或模块分片，每片一个会话、一条分支，说明只带那一页规则和文件清单 → 每片按规则自查，测试会话抽样验加全量跑机械检查 → 例外进清单由主会话统一定。
- **差别**：先试跑再放开；错误清单当队列用；盘点类的覆盖以「实际读过、改过的文件清单」核，不以自报为准。
- **会话**：先 1 个，跑顺了再放 2–4 个；几十片以上、不需要中途拍板的，改用宿主的批量脚本能力（有的话），那不归本技能。

## 8. 长跑（叠加）

- **适合**：用户不在、要跨额度窗口、能分段落地的大活。
- **不适合**：要求含糊；会碰外部系统、花钱、动线上数据的。
- **开工前五问**，答不上就不跑：什么叫做完；怎么自查；能碰什么；什么情况停下来；结果给谁看、谁签字。
- **怎么走**：切成里程碑，每个里程碑一条校验命令，不过就先修、不往下走；每段做完提交、更新台账与进度行；给预算（轮数、会话数、额度百分比）和停止条件。
- **差别**：里程碑之间只开新会话不续老会话（续一个放了很久的大会话更贵）；同一步失败两三次就停下来交用户，不无限重试；宿主不让自动轮开会话的，把后面里程碑的会话在批准那一轮开好待命。
- **卡住时换脑**：保留文件、开一个全新的会话从台账和代码接着做，常比在老会话里硬磨有用。

## 9. 先写测试（叠加）

- **适合**：这块的核心逻辑就是金额、权限、安全、状态机、数据迁移，或者 bug 复现。只是顺带碰到（加一条审计、复用一个权限）的不算，用默认加一条验收就够。
- **不适合**：界面打磨；规则自己还没想清楚的（写错的测试会挡死对的实现）。
- **怎么走**：测试会话按要求写会失败的测试、确认它们现在真的失败并且失败得对 → 主会话核一遍测试对不对得上要求 → **冻结**（说明里写明开发不能改这些文件）→ 开发会话只改实现直到通过 → 另留几条没给开发看过的验收，由测试会话最后验。
- **差别**：测试在前；开发认为测试写错了，带证据交回，由主会话裁，不自己改。
- **别只靠一句「按 TDD 做」**：把会受影响的测试点名写进说明。

## 10. 分区迭代

- **适合**：一个大成品能按功能分成几个长期负责区，用户要一轮一轮看能用的版本、在报告上批注、提修改，直到满意：演示版、整站改版、大功能的多轮打磨。
- **不适合**：一轮就能验收完的（用默认或并行开发）；几区都要改同一批文件、拆不开的（先合区）；用户不打算多轮看的。
- **开工前多定三样**，写进方案和台账：
  1. **成果分支**：这一期的成果并进哪条分支；它和项目集成分支、部署环境的关系（要不要隔离、最后回不回灌、怎么回灌）。
  2. **分区表**：每区一个负责会话，写目标、文件范围、对外接口（共享数据、类型、路由、端口）。区与区之间的接口由主会话定、写进台账当合同；公共底座（数据、环境、公共类型）单独成一区，先做或先把接口定死。
  3. **一轮怎么算完**：各区交回 → 测试会话真实操作验（真点、截图）→ 主会话串行并进成果分支、整体走一遍最长路径、自己抽验 → 出本轮报告页。
- **怎么走**：
  1. 第一轮按用户的全部要求开干，力求第一版就齐；各区并行，同时写代码的不超过 4 个，用户要照看的总数不超过 5 个。区比这多：先开底座和最大的几区，其余合区或排到下一批，在方案里写明。
  2. 测试会话常驻，按区先后验；说明照默认，不看开发的交回。
  3. 报告不必等所有区：有区验过就可以先出一版进度报告，后面的区陆续补进下一版。每轮报告写清每区做了什么、截图、已知问题、要用户定的。
  4. 用户批注进来：逐条记进台账（原话、编号）→ 按区拆成跟进消息，派回**原负责会话**；跨区的先由主会话定接口，再分别发。
  5. 循环，直到用户说满意。
- **换人与细分**：同区同一问题纠两次还错、上下文长到每轮明显变慢变贵、一区要拆成两区 → 开新会话接手，台账写交接（分支、做到哪、未决），老会话收尾。只有用户说话的那一轮能开新会话，换人、细分放在用户批注的那一轮做。
- **差别**：会话跨多轮长期持有，测试会话常驻；每轮都出报告页（中间的自动轮只在会话里说几句）；「三轮没过就停」只管同一条验收的打回，用户的迭代轮不设上限。
- **收尾**：用户说满意才收。成果分支要不要整条并进项目集成分支，由用户定；只回灌一部分的，主会话列出可回灌的改动清单让用户挑，挑中的按项目合并规矩另开分支、另开 PR，不把成果分支整条合过去。
- **会话**：区负责 2–4 个 + 测试 1 个（区大可多开），同时在跑的不超过 5 个。
