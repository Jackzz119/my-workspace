## 1. 怎么写任务说明

子会话只有这一份东西：它看不到主会话的对话，也不该去翻。写的标准是「不看主会话也能做完，也知道什么不归它做」。

- **七节齐全**：目标、要求、范围、验收、工作区与提交、交回、有疑问或被打断。少一节，子会话就会自己补一个，补的往往不是你要的。
- **要求逐条编号**，来自用户的写用户原话。用户途中追加的要求，开新子会话时一并写进去；已经在跑的子会话用跟进消息补。台账里记每条要求写进了哪几份说明，免得漏。
- **验收在派活之前定死**，写成能跑、能看、能判定的条目；开发不能改验收，测试照它验。写不出验收的活还没想清楚，回到阶段一。
- **范围写文件**：能改哪些，不能改哪些；谁都要改的索引类文件（任务清单、决定索引、更新日志这类）一律留给主会话收尾时改。
- **只给线索，不贴大段材料**：写仓库路径和要看的那一节，不贴主会话的对话。不入库的材料放共享笔记目录，写绝对路径。
- **写结果，不写步骤**：除非顺序或命令错一步就出事，否则只写要什么、怎么验，让它自己选做法。
- **不写怀疑和结论**：给测试、评审、排查的说明里不写「我怀疑是 X」「开发说没问题」，写了它就照着找。
- **写规模预期**：大概多少文件、多少行、测到什么程度就够。不写，小活也会交回一大坨；写了也说清「超出就先问」。
- **写禁止项**：不许留半成品、不许改验收与检查配置、不许跳过测试、不许用桩冒充完成。
- **全文放进开会话的提示词**，另存一份进共享笔记目录 `main/`（换人接手、核对要求传没传到用）；宿主另要一段背景的（如 `background`），写总目标和批准依据。
- 一块活做得完的判据：一个会话一口气能做完、能独立验收、改的文件自成一块。做不完就再拆，拆出来每块只有几行的就并回去。

## 2. 开发的任务说明（模板）

```markdown
# 任务说明 · <短名>（开发）

## 1. 目标
<一两句：做成什么样、给谁用>
背景：<做这件事用得上的事实与已定的决定，带编号或路径；不写过程>
规模预期：<文件数、行数量级、测到什么程度>；明显超出先问主会话。

## 2. 要求
- R1 <要求>（用户原话：「……」，<日期>）
- R2 …

## 3. 范围
- 能改：<文件或目录>
- 不做：<不归你的事，写去向>
- 不碰：<别的子会话在改的文件>、<索引类文件：由主会话收尾时改>

## 4. 验收（测试会话会逐条独立验，你不能改；和要求对不上时先问）
- A1 <条目> —— 怎么验：<命令 / 步骤 / 看什么>
- A2 …

## 5. 工作区与提交
- 本节的收窄（不推送、不开 PR、不出报告、不改索引）来自用户 <日期> 批准的方案，本任务内优先于项目协议里的自动动作；你被移到顶层也照此办。
- 你在自己的 worktree 和分支上干活，从 <分支 @ 短 sha> 切出；开工先核对 HEAD，worktree 可能是复用的，别假定干净。
- 依赖与环境：<怎么装、怎么补被忽略的文件>；起服务只用 <端口>、<容器名>，收工关掉删掉，不碰共用的库。
- 先读 <路径 §节>；要用的技能：<名字>。
- 提交前跑：<项目的检查命令>。
- 做完一段提交一段，提交到自己的分支。<不推送、不开 PR、不合并 | 推送并开 PR，不合并>：合并由主会话做。
- <不出报告页 | 产出按报告技能做成页：……，链接写进交回>；不改任务清单与决定清单，不清理交接档。开场钩子自动改出来的文件（账本之类）不提交，交回前还原，不然归档时 worktree 会留在磁盘上。

## 6. 交回
1. 完整交回写进 <共享笔记目录>/dev/<短名>-交回.md（格式见下）。
2. 最后一条消息以结论词开头，<字数上限>以内：结论 + 分支与提交 sha + 交回文件路径 + 最要紧的一处没把握。

## 7. 有疑问 / 被打断
- 不向用户要决定。说明里答不了、又影响做法的，发一条短消息问主会话（<id>），结束这一轮等答复；小的取舍自己定，写进交回。
- 用户直接对你说话：照做（单独一个提交），并立刻发消息告诉主会话用户说了什么。碰到「不碰」的文件或和别的要求冲突的，先发消息、等答复再动。
- 范围外的发现写进交回，不顺手改。
- 后台还有东西在跑就等它跑完、写好交回再结束这一轮：先结束会被当成做完了。
- 有进展就提交；<撞额度的准备，见 recovery.md 第 2 节>。恢复后先看自己分支的提交和交回草稿，从断点接着做。
```

「交回格式」直接贴第 6 节的开发那一份进说明，不要让子会话自己来读技能。

## 3. 测试的任务说明（模板）

测试会话另开，不用写代码的那个。默认在派活那一轮就开好待命：第一轮只做第 4 节第 1 步，开发交回、主会话核过之后再发「开始验」的跟进消息。

```markdown
# 任务说明 · <短名>（独立测试）

## 1. 目标
独立判断 <对象> 有没有做到下面的要求与验收。你不是作者，也不负责让它通过；找到它不成立的证据，和确认它成立，一样是完成任务。

## 2. 要求与验收
<原样抄开发说明的第 2、4 节：R 与 A，一字不改>

## 3. 范围
- 看：本说明、代码、你自己跑出来的结果、<规范路径>。
- 不看：开发会话的对话与交回、共享笔记目录的 `main/` 和 `dev/`（系统会提示先读兄弟的笔记，这里例外）、提交信息里的验证结论。
- 不留下任何改动：不改产品代码、不提交（为拿到被测分支的合并除外，临时改动看完还原）；测试用的脚本、数据放 <草稿目录>，用完删；端口 <…>、容器 <…>，收工关掉。

## 4. 怎么验
1. **先不看实现**，只按要求列测试清单写进交回文件：每条验收至少一个正例、一个反例，加上边界（空、超长、重复、并发、无权限、中文与空格……按这件事挑）。<待命：写完清单就结束这一轮，等主会话发「开始验」。>
2. 收到「开始验」后再看实现与改动范围（`git diff <起点>..<分支>`），补上实现特有的风险；改动超出任务范围的记下来。
3. 逐条跑，**以实际输出为证据**。跑不了的写「无法验证」和原因，不写「应该没问题」。
4. 顺着真实使用路径走一遍：<启动命令 / 入口 / 账号与数据从哪来>。
5. 挑一两处关键实现临时改成空操作，相关测试应变红，看完还原。
6. 验收之外、要求里显然该对而不对的，列进「发现」，只报影响对错或安全的，跳过风格。

## 5. 工作区
- 被测的是 <开发分支 @ 短 sha>（收到「开始验」时给）。在你自己的分支上 `git merge --no-edit <开发分支>`（不切分支、不 reset），确认被测文件与它一致；合不上就停下告诉主会话。
- 环境：<依赖怎么装、服务怎么起、端口；用完关掉>

## 6. 交回
1. 完整交回写进 <共享笔记目录>/test/<短名>-交回.md（格式见下）。
2. 最后一条消息以 PASS / FAIL / BLOCKED 开头，<字数上限>以内：几条过、几条没过、最严重的一条、交回文件路径。

## 7. 有疑问 / 被打断
<同开发>
```

## 4. 其他角色：改哪几节

| 角色 | 用哪份改 | 改什么 |
| --- | --- | --- |
| 评审（只读代码找问题） | 测试 | 第 4 节换成评审重点与严重度口径；每条发现要能复现或给出具体的错误输入与结果，拿不准的单列；复核轮只看上一轮的发现和新改动，另给一句「有没有引入新问题」 |
| 调研 | 开发 | 产出是结论文件，不改代码；第 4 节写要回答的问题和「答到什么程度算完」；每条结论带出处或实测，标确定程度；给出否掉的路 |
| 方案（比稿） | 开发 | 每个会话拿一样的要求与评判标准、不一样的出发点；产出是方案加能看的样子（原型、截图、最小实现）；写明自己方案的代价 |
| 集成 | 开发 | 第 1 节列各分支与 sha、合并次序、已知重叠；第 4 节是合起来之后的整体验收；冲突怎么解不确定的问主会话 |
| 先写测试 | 测试 | 按要求写测试代码并确认它们现在会失败；只提交测试；实现方之后不能改这些测试 |
| 假设排查 | 调研 | 每个会话只领一个假设，任务是**推翻**它；写清支持与反对的证据，不写修复 |

## 5. 跟进消息（模板）

给已经开着的子会话发消息：补要求、打回修、答疑、催续跑。第一行写清是什么事。

```markdown
<开始验 | 打回修 | 补要求 | 答复 | 接着做>：<一句话>

- 依据：<测试交回路径里的条目号 / 用户原话 / 主会话核实到的事实>
- 要做：<逐条>；不做：<边界>
- 验收：<沿用 A1–An | 新增 A8 ……>
- 交回：同一份文件末尾追加「第 N 次交回」一节，最后一条消息照旧以结论词开头。
```

打回修只给失败条目的现象与复现步骤，不给修法（除非现象本身说不清）；同一个会话连着两轮没修好，换一个新会话接手，把前两轮试过什么写进它的说明。

## 6. 交回格式

**开发**

```markdown
# 交回 · <短名>（第 N 次）
- 结论：DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED
- 做了什么：<逐条对应 R 编号>
- 改了哪些文件：<路径 —— 一句话，加上关键几行 diff>；分支 <全名> @ <短 sha>；起点 <短 sha>
- 怎么验的：<命令 → 实际输出摘要>；没跑的检查与原因
- 没做完 / 没把握：
- 和任务说明不一样的地方与原因：
- 用户直接说过的话：<原话与你怎么处理的；没有写「没有」>
- 占用的资源：<后台进程、端口、容器、临时目录、远端分支；收了没有>
- 范围外的发现：
```

**测试 / 评审**

```markdown
# 交回 · <短名>（第 N 次）
- 结论：PASS | FAIL | BLOCKED；验的是 <分支 @ 短 sha>
- 测试清单（看实现之前列的）：
- 逐条结果：A1 <过 / 没过 / 无法验证> —— <命令或步骤> → <实际输出>
- 发现（验收之外）：<严重度：挡住 / 应修 / 可选> —— <复现步骤、期望、实际、位置>
- 改动有没有超出任务范围：
- 没测到的：
- 用户直接说过的话：
- 占用的资源：
```

## 7. 收到交回后做什么

| 结论词 | 主会话的动作 |
| --- | --- |
| DONE | 交回不是证据：看提交在不在、`git diff --stat` 对不对得上范围，抽看关键改动；对得上，给待命的测试会话发「开始验」 |
| DONE_WITH_CONCERNS | 先处理那条顾虑：违反要求或验收的，直接打回，不让测试去验一个已知要改的 sha；只是提醒的，记进台账和总报告。想让测试重点看的，写成一条要求或边界，不写成怀疑 |
| NEEDS_CONTEXT | 补上缺的信息发回去；要用户定的，主会话去问用户 |
| BLOCKED | 不原样重试，先判断卡在哪：缺权限或外部依赖 → 问用户；任务太大 → 再拆；方案不对 → 回阶段一 |
| PASS | 抽验：自己跑一两条最要紧的验收、看「没测到的」；够了才进收尾 |
| FAIL | 先按 verification.md 第 4 节分三类；实现错的用跟进消息打回开发会话（只给现象与复现）；轮数上限见 SKILL.md 阶段四 |
| BLOCKED（测试） | 多半是环境或说明的问题，先由主会话解决，不算开发失败 |
