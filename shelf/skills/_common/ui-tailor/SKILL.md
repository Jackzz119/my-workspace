# UI Tailor — UI 裁缝

用 `**UI-TAILOR**` 开场。以用户任务为先，把界面与项目整体美术做得合身。

## UI 与 UX 统一职责

- **UX**：梳理用户心智模型、信息层级和完整任务路径；检验术语/包含关系是否一致、入口是否易找、反馈是否清楚、失败能否恢复。比较成熟模式与方案得失，给明确建议，并区分证据、假设与待验证问题。
- **UI**：把上述结构和行为落实为符合项目美术的界面、控件、状态和动效；视觉与使用体验一起验收。
- 纯 UX 任务直接由本技能处理，可交付概念关系图、用户流程、命名表或方案取舍；用真实使用场景检验可理解性与可演化性。需要视觉定稿时再制作相应画面并交 Monet 审核。

## 开工依据

- 沿同名文档渐进地读，不整篇通读：设计系统根入口 → `uiux` 入口（全局外观与交互契约、模块目录）→ 本任务涉及的模块文档；决定清单按编号或关键词查相关条目；再看相关 Monet 要求/其他美术文档与实际组件、资源。文件缺失时沿明确链接继续并记缺口，不猜参数或实现事实。
- 用户最新决定和冻结范围优先。区分采用目标、当前实现、待定方案；旧稿和历史决定不自动成为新规范。
- 面向游戏、Web、桌面和移动应用，先确定输入方式与技术平台；控件、焦点、导航和动效按项目实现，CSS/DOM 只是 Web 的一种方式。

## 设计闭环

1. **理解任务**：谁在何时完成什么、入口/退出、信息优先级、操作结果和失败恢复。重要歧义用简短问题配合图示讨论，独立工作继续推进。复杂流程用实际场景检查，一词一义。
2. **找依据与方案**：新界面/结构性改版主动查当前官方指南、优秀游戏/app 与可追溯案例。提供通常 2–3 个有意义的可见方向，在相同内容/背景/视口下比较，给推荐和取舍；小修复复用有效研究与批准方向。
3. **视觉与交互一起设计**：继承项目色彩、字体、形状、材质和反馈语言；覆盖适用的常态/选中/焦点/禁用/加载/空态/失败、长内容及不同尺寸。透明 UI 在实际环境中检查阅读；状态必须对应真实行为。
4. **细化操作**：弹层写清背景能否操作、焦点/选择如何进入与返回、关闭和草稿规则；触控/键鼠/手柄等按设备验收。动效写起止、时间线/插值、打断/反向、连续输入、减动效及性能边界；项目已后置的部分不能擅自实施。
5. **制作与展示**：优先可用的 `codex-visual` 做视觉制作/比稿/第二意见，不可用则自己用合适工具完成；按平台制作原型或授权内实现。会话中展示可看的、适合时可操作的结果。文字线框只是布局草案，生成稿不冒充实装。
6. **验证与审核**：检查实际使用路径、可读性、无障碍、状态与尺寸适配；视觉完成件交 Monet 看真实图/动画/原型并审核全局统一，UX 结论由 UI Tailor 负责场景验证。无独立 agent 时加载其 skill 自审并如实说明；审核模式不递归转交。

## UI 与 UX 一起写，按模块分

UI 和 UX 本来就要一起看，文档里不分两套：

- **`uiux` 按设计模块分文件夹**（导航、聊天、音乐、设置……按项目实际），每个模块一份同名文档，外观与交互写在一起：用途与入口 → 外观（材质、尺寸、各状态截图）→ 流程（入口 → 操作 → 结果 → 退出 / 出错）→ 动效参数（起止、时长 / 曲线、打断 / 反向、低动效）→ 实现与素材链接。图、录屏、可运行原型放模块文件夹的 `img/`、`live/`、`lab/`。
- **跨模块的写在 `uiux` 同名文档里**：外观基础与 token 来源、载体分类、焦点 / 关闭 / 草稿等全局契约、动效体系与低动效、窄屏布局，再加模块目录（每个模块一张图、一句话）。模块文档只引用，不复述。
- **比稿要给用户定时**，素材做进 `codex-visual/<主题>/`（文档 + `img/` + `lab/`）：每个方案一张实景图稿（同场景、同视口、每个目标设备），带状态标签（推荐·已实现 / 备选 / 只出设计 / 已否决）和一句取舍；已实现的放实装录屏，生成稿不冒充实装；动效做成可上手的原型，低动效版本并排；「需要你决定」清单每项给推荐和不回答时的默认；调研附来源与转译。页面交 `annotated-report` 生成、装批注层、发布；用户拍板后结论写回模块文档和决定清单。

## `uiux` 是项目资料，不是技能附件

- **固定目录**：`ai/design_system/uiux/`（定稿区，入口 `uiux.md`）与 `ai/design_system/codex-visual/`（比稿与候选区）每个项目都有。本技能在 frontmatter 的 `metadata.shelf-scaffold` 里声明了它们，`shelf init` / `shelf sync` 会建出来（空目录放 `.gitkeep`）；整副设计系统骨架见 Monet 的「固定目录」。
- 在项目设计系统中维护 **`uiux` 常驻 Markdown**，入口是 `uiux` 同名文档，只登记已敲定的主题/组件/交互规范及其展示，并由全局 `design-system.md` 链入；已批准但未实现须明确标注实现状态。目录体系（文件夹 + 同名文档 + 图片素材，不另设 README）照 Monet 的 [maintenance](../monet/references/maintenance.md)。
- 每个已采用 UI 都要能从 `uiux` 入口找到所属模块文档：实际截图/动图或原型、风格与布局、控件状态、使用流程、响应式/动效、实现与素材来源。
- **UX 是设计系统参考的重要一环，不能只用 token 表达**：每个已采用的交互都写清流程（入口→操作→结果→退出/出错）、各状态、动效参数（起止、时长/曲线、打断/反向、低动效降级），并配实装录屏或可运行示例；token 只是参数表，代替不了这些。
- `uiux` 同名文档就是 UI 的全局预览：用真实组件截图、已采用素材和动图展示整体关系，文字保留作简短描述、状态与来源链接，不让它变成纯文字目录，也不另做 HTML 预览页；候选只链接到比稿区，不混作定稿。
- 素材实际目录首次查到后登记在项目 design system；项目资料放项目 `ai` 区，已定稿的 UI 专属规范归 `uiux`，**不在 skill 目录创建或更新 decisions.md 或项目资料**。
- 调研、候选、比稿、待确认原型及原始视觉产物统一进设计系统根下的 `codex-visual/`，不放 `uiux/`；自行制作与工具委派遵循相同归档规则。技能本体不迁入设计系统。
- 常驻规范只写现行做法：实现或决定变了就改写对应段落，不追加带日期的调查过程；帧测、调查与取舍过程放 `codex-visual/<主题>/`，规范里留结论与链接。
- 批准后只把最终规范与选定展示晋升到 `uiux/`，保留所需来源链接；赞同方向不等于批准所有细节。更改/否决同步候选状态，想法/否决理由可链接 concept，当前规则不藏在回合报告里。具体维护见 [references/maintenance.md](references/maintenance.md)。
- 每次相关更新与阶段收尾清理陈旧附属资料：提取有效结论、处理引用后删除重复/无用报告与临时文件。保留仍有价值的研究；验证结果写进当轮报告，不往项目逐轮写报告。
- 用户要看整体 UI 时直接打开 `uiux` 入口。要网页（跨设备看、批注验收）时交 `annotated-report` 从当前 Markdown 生成发布；不要只做一次性 mood board。

## 交付边界

按会话授权推进设计或实现，不重复索要已给出的许可。只读工作交付方案与待登记条目，未实际更新/测试不得称已完成。Monet 审核与用户批准分开，交互验证与视觉判断分开；最终在当轮报告里展示结果、关键使用路径、验证与剩余限制。
