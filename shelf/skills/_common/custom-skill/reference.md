## 1. Frontmatter

```yaml
---
name: skill-name                    # 必需：与目录名相同
description: 做什么。什么时候用。     # 必需：≤ 1024 字符
metadata:                           # 可选：字符串到字符串的映射
  shelf-scaffold: "features, design_system/uiux"
---
```

**开放标准字段**（Agent Skills 规范的六个字段，Claude Code 与 Codex 都能解析；上传 claude.ai、走 Skills API 时只允许这六个，多一个就报错）：

| 字段 | 必需 | 约束与用法 |
| --- | --- | --- |
| `name` | 是 | ≤ 64 字符；只用小写字母、数字、连字符；不以连字符开头或结尾，不连写 `--`；与所在目录名相同；不含 `anthropic`、`claude`（Claude API 的保留词） |
| `description` | 是 | 1–1024 字符；写法见第 2 节 |
| `license` | 否 | 许可证名或附带的许可文件名；第三方移植或要外发的技能才写 |
| `compatibility` | 否 | ≤ 500 字符；只在有特殊环境要求时写，如「需要 git、jq 与网络」。多数技能不需要 |
| `metadata` | 否 | 字符串到字符串的映射，键名取得独特些以免撞名；Claude Code 不解读；Codex 读 `metadata.short-description` 作界面短描述 |
| `allowed-tools` | 否 | 预批准工具；开放标准里是实验字段，写法是空格分隔；Codex 不认。见第 4 节 |

**Claude Code 扩展字段**（只有 Claude Code 认；Codex 忽略，claude.ai 上传会报错）。自建技能默认不写，确有需要再加，并在正文写明 Codex 侧怎么办：

| 字段 | 作用 | 口径 |
| --- | --- | --- |
| `when_to_use` | 接在 description 后的触发说明，两者合计在技能清单里截到 1536 字符 | 不用；触发条件写进 description，两边都认 |
| `argument-hint`、`arguments` | 补全提示；命名参数 | 接参数的技能可加 `argument-hint` |
| `disable-model-invocation` | `true`：只能用户 `/名字` 触发，description 也不进上下文 | 见第 3 节 |
| `user-invocable` | `false`：不进 `/` 菜单，只由模型加载 | 只给不能当命令用的背景知识类技能 |
| `disallowed-tools` | 技能生效期间把工具从可用池里拿掉——真正的限制 | 需要硬限制时用 |
| `model`、`effort` | 本轮剩余部分换模型 / 推理强度 | `model` 自建技能不写（用户 2026-10-16 定，理由见下）；`effort` 按同样理由默认不写（本规范建议） |
| `context: fork` + `agent` | 在子代理里跑，子代理看不到对话历史 | 只给有明确任务、指令自成一体的技能；只有规范没有任务的技能 fork 出去会空手而回 |
| `hooks`、`paths`、`shell` | 技能生效后注册钩子；只在读写匹配文件时自动激活；注入命令用的 shell | 按需 |

**`model`：自建技能不写**（用户 2026-10-16 定），不写就跟会话模型。它只在技能生效的那一轮换模型，写死的型号会过时、换了新模型也不跟着升级；确实要某一步换模型（比如只做格式转换、要省钱）时才写，并在说明里写清为什么。

**`metadata.shelf-scaffold`：技能的固定目录**（用户 2026-10-19 定）。技能要在项目的 ai 区用固定的文件夹（如 `features/`、`design_system/uiux/`、`project-audit/runs/`）时，两处一起写：

- frontmatter 声明：逗号分隔、相对 ai 区（.NET 项目是 `AI/`），只写目录；绝对路径和带 `..` 的会被丢掉。装了这个技能的项目，`shelf init` / `shelf sync` 会把缺的目录建出来，空目录放 `.gitkeep`（只放在最深一层）。
- SKILL.md 正文写一节「固定目录」：每个目录放什么、入口文档叫什么、第一次什么时候写。只写跨项目都成立的目录；项目特有的目录登记在项目文档里。目录只建空架子，不预建空文档。

两处说法要一致；改目录名时同时改声明、正文和所有引用它的地方。

**YAML 陷阱**：

- 写坏的 YAML 在 Claude Code 里技能照样加载，但字段全空——description 不生效，只能靠 `/名字` 调用；Codex 遇到缺 frontmatter 或 description 为空的直接不加载。`claude --debug` 能看到解析错误。
- description 里的半角「冒号加空格」会让解析失败；「空格加 #」后面会被当注释**静默截掉**；以 `[`、`{` 开头也会失败。改用全角「：」，或把整句放进双引号。
- Claude Code 把 description 里的尖括号显示成 `&lt;`、`&gt;`，占位写成 `[名字]`。

## 2. name 与 description

**name**：小写加连字符，说清这个技能干什么（`pdf-processing`、`shelf-ops`）；避免 `helper`、`utils`、`tools` 这种空名字；一套技能里命名方式统一。带「人设」的技能（`intj`、`monet`）沿用本项目已有的叫法。

**description 是触发的唯一依据**：会话开始时只有各技能的名字和描述在上下文里，模型拿用户的请求去和描述比，决定读不读正文。写法：

- **两件事都写**：做什么（能力、产物）+ 什么时候用（触发条件、用户会说的话、涉及的文件或工具名）。
- **关键用途放最前**：技能多了清单会超预算——Claude Code 先丢最少用的技能的描述，单条（连同 `when_to_use`）截到 1536 字符；Codex 先缩短描述再省略技能。
- **人称**：第三人称陈述，或「……时使用」；不写「我能帮你……」「你可以用它……」。描述是拼进系统提示里的，人称不一致会影响匹配。
- **宽窄**：模型倾向于少用技能，所以触发条件要列全，包括用户没点名这个领域、但其实需要它的说法；但别写成包罗万象的能力清单——太宽会抢走别的技能的触发。和相邻技能容易混淆时，加一句边界（「不用于……，那归 X」）。
- **不在描述里概述流程**：描述写「什么时候用」，步骤写正文。描述里写了流程摘要，模型可能照着摘要做、不去读正文。
- **长度**：硬上限 1024 字符；几句话到一小段即可。
- **人设称呼**（本项目口径）：有人设的技能可以在开头留一个短称呼（「Skill 主管：」「任务主管——」），后面紧跟用途；称呼不替代用途。
- 只需一步、模型自己就能做的请求（「读一下这个 PDF」），描述再贴切也可能不触发——测试触发时要用有分量的真实任务。

例：

```yaml
# 太虚：不知道什么时候用
description: Skill 主管——管理所有 skills，主动监督并按策略触发各 skill
# 做什么 + 什么时候用，关键用途在前，带用户会说的词
description: Skill 主管：技能的创建规范与审查清单。创建、修改、审查、登记技能时使用，包括写 description、frontmatter、allowed-tools；读写 ai/jaSkills/ 下任何文件之前先用它。
```

## 3. 谁能触发

| 想要的效果 | Claude Code | Codex |
| --- | --- | --- |
| 用户和模型都能触发（默认） | 不写 | 不写 |
| 只能用户显式调用 | `disable-model-invocation: true`（描述也不进上下文） | `agents/openai.yaml` 里 `policy: allow_implicit_invocation: false`，只认 `$名字` |
| 只给模型用、不进菜单 | `user-invocable: false` | 无对应字段 |

两个字段同时设（`disable-model-invocation: true` + `user-invocable: false`）技能就谁也调不到了。

**官方两种看法**：Claude Code 文档建议有副作用、要控制时机的工作流（提交、部署、发消息）设 `disable-model-invocation: true`；Codex 的 skill-creator 则建议不要因为操作敏感就改成只许显式调用，而是保持可被发现、在真正动手改东西之前要授权。

**本项目口径**：触发策略分「自动 / 询问后 / 点名时」三档，登记在协议「通用技能与触发」表和 `ai/JASKILL.md`——它们在触发前就在上下文里。技能正文里那句「触发策略：……」要等加载后才看得到，不能单靠它。「询问后」= 保持可被发现、动手前先问，和 Codex 的建议一致，不改成 `disable-model-invocation`（那样模型看不到描述，也就无从「先问」）。要不要给某个技能收紧成只许显式调用，先问用户。

## 4. allowed-tools：只是免确认，按最小授权写

**它是什么**：

- 列出的工具在**调用这个技能的那一轮**免确认执行；用户发下一条消息就失效（技能正文还留在上下文里，授权不跟着留）。
- **不是限制**：没列的工具照样能调用，走用户自己的权限设置。要真限制，用 `disallowed-tools`（Claude Code）或 settings 里的 deny 规则。
- settings 里的 deny、ask 规则优先于它。
- 工作区信任不拦它：仓库里的技能可以给自己宽授权。装别人的技能，先看这一行。
- Codex 不认这个字段，按自己的审批与沙箱模式走。

**收窄原则**：

1. **默认不写**。`Read`、`Grep`、`Glob` 和内置只读命令（`ls`、`cat`、`head`、`tail`、`grep`、`find`、`wc`、`diff`、`stat`、只读的 `git status` / `diff` / `log` 等）在工作目录内本来就不弹确认，列进来是空操作。不填 = 全按用户自己的权限设置走。
2. 只有「每次必跑、会弹确认、只读或后果可控」的命令才写，而且写到具体子命令：`Bash(shelf status *)`，不写 `Bash(shelf *)`。
3. **不写裸 `Bash`**：等于这一轮放行所有命令，包括写操作——「Bash 只用于只读命令」要靠收窄保证，写在说明里拦不住。
4. **解释器和运行器等于任意代码**：`Bash(node *)`、`Bash(python3 *)`、`Bash(bash *)`、`Bash(npx *)`、`Bash(devbox run *)` 会执行后面跟着的任何东西；两头都带通配的 `Bash(node *x.mjs*)` 也能被 `node -e '…' x.mjs` 匹配。要放行技能自带的脚本，写到脚本路径：`Bash(node ${CLAUDE_SKILL_DIR}/scripts/check.mjs *)`（Claude Code 会替换 allowed-tools 里的技能目录占位符）；正文里的命令怎么写（路径带不带引号），规则就怎么写，写完实际调用一次，确认真的免确认了。
5. 参数级收窄很脆：`Bash(curl https://example.com/ *)` 挡不住换选项顺序、换协议、变量、重定向。要放行网络访问，优先用 WebFetch 的 `domain:` 规则。
6. **`Write`、`Edit` 不加入**（本项目口径）——文件修改必须每次经用户确认。官方示例给只能手动调用的提交类技能预批准 `git add` / `git commit`，本项目不这样做。
7. 写法：`Bash(git diff *)` 与 `Bash(git diff:*)` 等价，`:*` 只在末尾有效；`Bash(ls *)` 不匹配 `lsof`，`Bash(ls*)` 匹配。多个工具 Claude Code 接受空格分隔、逗号分隔或 YAML 列表，开放标准写空格分隔。
8. 有注入命令的技能：渲染时不弹确认，非 auto 模式下没被放行的注入命令会中止整个调用。内置只读命令通常直接放行（以实际调用一次为准），其余写到具体命令。

> **原因**：`allowed-tools` 绕过的是用户确认这一层。「自动触发 skill」≠「自动执行写操作」，两者是不同层级的控制；规则写在正文里只能影响模型想做什么，权限层才是边界。

**已批准的例外**：用户明确批准的宽授权，按记录保留，审查时不报违规，但要核对批准记录还在。批准记录写在**项目自己**的决定清单与技能登记表（如 `ai/JASKILL.md` 那个技能的条目），不写进本技能——本技能随货架进所有项目，不装某个项目的例外。预批准只省掉执行命令时的确认，不是写操作的许可：写操作能不能做、什么时候做，以那个技能自己的权限边界与项目的授权记录为准。

## 5. 动态特性：注入命令、调用参数、技能目录

三者都是 **Claude Code 的语法**。Codex 不执行、不替换，本项目 `AGENTS.md`「调用方式（Codex 侧）」表让 Codex 自己代入。技能离了它们也要能用。

### `` !`命令` `` — 运行时注入

```markdown
当前 git 状态：
!`git status --short`
```

- 命令必须包在反引号里，`!` 放在行首或紧跟空白；写成 `!git status` 不会执行，只会原样显示；`!` 紧贴别的字符（如 `` KEY=!`cmd` ``）也不执行。多行命令用围栏代码块，开头写三个反引号紧跟 `!`。
- 命令在技能**渲染时**、发给模型之前执行一次，输出替换占位符、直接进上下文，不会再被扫描一遍；适合注入「当前状态」类信息。
- 在会话当前目录里跑（模型 `cd` 过就跟着变）；路径要固定的用技能目录或项目目录占位符。stderr 并进输出；超时同 Bash 工具（默认 2 分钟）。
- 命令失败（非零退出；搜索、比较类命令的退出码 1 不算）会**中止整个技能调用**，模型连技能内容都看不到——预期会非零退出的命令以 `|| true` 收尾。
- 权限：见第 4 节第 8 条。auto 模式下没被放行的命令不中止，技能照常加载，并附一句让模型先自己跑这条命令。
- 用户或组织可以用 `disableSkillShellExecution` 关掉注入（命令被换成一句「已被策略禁用」）；从 claude.ai 同步来的技能从不执行注入。
- 反过来，说明文字里别让 `!` 紧跟空白再接反引号——那也会被当成命令执行。

### 调用参数

```markdown
目标功能：$ARGUMENTS
```

- `$ARGUMENTS`：调用时的全部参数。用户调用 `/custom-skill create bigwin` 时，`$ARGUMENTS` = `create bigwin`。
- `$ARGUMENTS[0]` 或 `$0`：按位置取（从 0 开始，带引号的算一个）；在 frontmatter 的 `arguments` 里声明名字后可写 `$名字`。
- 正文里没有任何参数占位符时，Claude Code 把参数以 `ARGUMENTS: …` 追加在技能内容末尾。

### `${CLAUDE_SKILL_DIR}` 等目录变量

- `${CLAUDE_SKILL_DIR}`：本技能 SKILL.md 所在目录；`${CLAUDE_PROJECT_DIR}`：项目根。另有 `${CLAUDE_SESSION_ID}`、`${CLAUDE_EFFORT}`。
- 在 SKILL.md 正文和 `allowed-tools` 的 Bash 规则里都会被替换。

**用哪种路径**：读支持文件用相对链接 `[reference.md](reference.md)`——两个 agent 都按技能目录解析，Codex 不用翻译；要**执行**的命令里用 `"${CLAUDE_SKILL_DIR}/scripts/x.mjs"`——Claude Code 的命令在项目目录里跑，相对路径找不到脚本。

### 占位符写进 SKILL.md 就会被替换

调用时整份 SKILL.md 都做替换，反引号里的也一样：说明文字里提到的 `$ARGUMENTS`、`${CLAUDE_SKILL_DIR}` 会被换成调用参数和绝对路径，句子随之错乱。

- 讲到它们时换个说法（「调用参数」「技能目录」），哪个 agent 读着都对。
- 非写字面量不可：`$ARGUMENTS`、`$1` 前加反斜杠（`\$ARGUMENTS`）；只有紧贴的单个反斜杠才算转义；`${CLAUDE_*}` 变量加反斜杠也挡不住。
- 语法讲解放 reference.md 这类按需 Read 的文件——Read 读到的是原文，不做替换。

## 6. 正文写法

- **只写模型不知道的**：项目约定、非显而易见的坑、具体工具与命令。不解释 PDF 是什么、HTTP 怎么工作。逐段问「没有这句它会做错吗」，不会就删。
- **给默认做法，不给菜单**：一个默认 + 一句例外（「用 A；扫描件改用 B」），不并列五种做法。
- **教方法，不写某一次的答案**：写处理这一类问题的步骤；输出模板、硬约束、具体命令照样可以写。
- **自由度随脆弱度**：多种做法都对的，描述目标和判断标准；易错、要一致、顺序固定的，给确切命令（「照这条跑，不要加参数」）。
- **用词一致**：一个概念始终用一个词。
- **不写会过期的条件**：「某月之前用旧接口」这类写进「旧做法」一节或删掉。用户决定的日期标注（「用户 2026-10-16 定」）是本项目的溯源口径，保留。
- **规则给一句理由，不靠音量**：一句「为什么」比全大写的 MUST 更能让模型在边界情况下判断对；少用 🔴、「必须」「绝不」的叠加强调——新模型更字面地执行，叠加的强调会让它在不该用的地方也照做。事故经过、过程叙事放进 commit 或 references。
- **贯穿整个任务的规则写成常设指令**：「每次改完都跑测试」，而不是「跑测试」。Claude Code 不会在后续轮次重读技能文件，正文是作为一条消息留在对话里的。
- **最重要的规则放前面**：上下文压缩后，Claude Code 给每个技能只保留最近一次调用的前 5000 token（所有技能合计 25000 token）。
- **必须每次都成立、不能靠模型记住的规则用钩子**（技能的 `hooks` 字段或 settings 里的 hooks），正文只能影响模型、拦不住操作。
- **严格的输出格式给模板**；多步流程给可勾选的清单，质量要紧的加「校验 → 修 → 再校验」回路；批量或破坏性操作先产出计划文件、校验计划、再执行。
- MCP 工具写带服务器名的全名（Claude Code 里形如 `mcp__服务器__工具`），多个服务器时才不会找错。
- 路径一律用正斜杠。

## 7. 文件结构与渐进披露

**三层加载**：

| 层 | 什么时候进上下文 | 预算 | 放什么 |
| --- | --- | --- | --- |
| 名字 + 描述 | 会话开始就在 | 每个技能约 100 token，所有技能共用清单预算 | 触发依据 |
| SKILL.md 正文 | 触发时读入 | ≤ 500 行、约 5000 token（建议值，不是目标） | 每次都要的规则、流程、坑 |
| 支持文件 | 用到才读 | 不读不占 | 参考、示例、模板；脚本执行时只有输出进上下文 |

正文一旦加载就一直留在上下文里，每一行都是之后每一轮的成本。中文按字算 token 比英文重，行数没到 500 也可能超过 5000 token。

### 什么时候拆出支持文件

- SKILL.md 超过约 200 行，或接近上面的预算
- 有大量示例代码、详细的规范表格或参数说明
- 内容不是每次都需要，可以按需加载
- 有几种互斥的模式或领域（按模式各一份，只读用到的那份）

### 怎么拆

- **只下一层**：所有支持文件都从 SKILL.md 直接链接，别在支持文件里再链到第三份——模型读二级引用时可能只预览开头，拿到的信息不全。
- **写清什么时候读**：「接口返回非 200 时读 references/api-errors.md」比「详见 references/」有用。
- 超过 100 行的支持文件开头放目录，模型只预览开头时也能看到全貌。
- 文件名说明内容（`form_validation_rules.md`，不是 `doc2.md`），按领域分（`references/finance.md`）。
- 同一条信息只放一处，不在入口和支持文件里各写一遍。
- 不加用不上的辅助文档（README、安装指南、更新日志、重复的速查）；第三方移植件要保留的许可与来源文件（LICENSE、NOTICE）除外。

### 经验摘录：细节在 references，主技能留一行

技能用起来解决了一个实际问题（踩坑、修法、调好的参数），细节写进 references 对应的那一节，**同时在 SKILL.md 的
「经验摘录」里加一行**：认出这个情形的症状 → 结论 → 细节在哪一节。主技能每次都会读，references 按需才读；
不留摘录，下次遇到相似的情形想不到去翻，经验就等于没积累下来。（开放标准的最佳实践也把「坑」放在 SKILL.md：模型要在遇到之前就看到。）

- 一条一行到三行：先写看得到的症状（用户怎么描述、画面上什么样），再写结论，最后写去哪读（文件 + 节名）
- 摘录不重复 references 的正文，只够让人认出「就是这种情况」、知道去哪读
- 同一个症状换了更好的修法，改写那一条，不追加第二条

### 什么时候需要 examples.md？

- skill 有多种调用方式
- 有复杂的输出格式示例
- 用户经常问"这种情况怎么用"

## 8. 技能里的脚本

**什么时候写脚本**：同一段逻辑每次都要重写一遍，或确定性执行能明显提高可靠性（校验、格式转换、批量修改）时。正文写清是「运行」（多数情况）还是「当参考读」。脚本执行时代码不进上下文，只有输出进。

**为 agent 设计接口**：

- **不交互**：agent 没法回应终端提示，等输入的脚本会一直挂着。参数走命令行、环境变量或 stdin；缺参数就报错并给出用法。
- `--help` 写清用途、参数和例子，保持简短（它会进上下文）。
- 报错说清错在哪、期望什么、怎么改（「字段 signature_date 不存在，可用字段：…」）。
- 结构化数据（JSON 等）写 stdout，进度与诊断写 stderr；输出量可预期，默认给摘要，大输出支持分页或写文件——工具输出超过阈值会被截断。
- 能重试：「没有才建」比「重复就失败」安全；破坏性或有状态的操作给 `--dry-run`，危险动作要求显式 `--confirm` 之类的参数。
- 退出码区分失败类型，并写进 `--help`。
- 自己处理能预见的错误，不甩给模型；常量写明为什么是这个值。
- 写明前置条件（「需要 Node 20+」），或用 `compatibility` 字段；需要包时只在本地装，不全局安装；版本钉住。

**经链接执行时比较真实路径**：技能目录里的脚本（`scripts/`、`assets/` 下的 `.mjs` 等）由 agent 按技能目录的路径执行，而技能目录在项目里通常是一条链接（如 `.claude/skills` 指向真源），脚本拿到的就是**链接路径**；仓库本身放在链接目录下时也一样（macOS 的 `/tmp` 其实是 `/private/tmp`）。凡是拿「自己的路径」去比较的写法，都要先解析成真实路径。

**判断自己是被直接执行还是被 import**（脚本既当命令行工具、又给别的代码 import 时才需要）：

```js
import fs from 'node:fs';
import { fileURLToPath } from 'node:url';

// 经链接执行时，argv[1] 保留链接路径，import.meta.url 却是真实路径：两边都先解析成真实路径再比
function isMain() {
    try {
        return fs.realpathSync(process.argv[1]) === fs.realpathSync(fileURLToPath(import.meta.url));
    } catch {
        return false;
    }
}

if (isMain()) main();
```

- 不要写 `import.meta.url === pathToFileURL(process.argv[1]).href`，也不要先 `path.resolve(process.argv[1])` 再比：`path.resolve` 不顺着链接找真实路径，经链接执行时两边永远不等，脚本**静默不跑、也不报错**，退出码还是 0，是最难发现的一种失败。
- `import.meta.main` 只在确认所有会跑这个脚本的机器上 Node 都支持时才用：不支持的版本上它是 `undefined`，同样静默不跑。
- 最好让入口文件只当入口（只调用 `main()`），要给别人 import 的函数放进另一个文件，这样根本用不着这道判断。
- 改完经技能目录的链接路径实际跑一次，确认主体真的执行了，不能只看退出码。

## 9. 两个 agent 的差异（Claude Code / Codex）

本项目同一份技能给两个 agent 用（`.claude/skills`、`.agents/skills` 都链到 `ai/jaSkills/`）。

| 项目 | Claude Code | Codex |
| --- | --- | --- |
| 发现位置 | `.claude/skills/`（项目，含子目录）、`~/.claude/skills/`（个人）等；不读 `.agents/skills` | `.agents/skills/`（当前目录、上级目录、仓库根）、`~/.agents/skills` 等；不读 `.claude/skills` |
| 链接 | 技能条目可以是 symlink，读目标 | 支持 symlink，扫描时跟到目标 |
| frontmatter | 认开放标准字段 + 扩展字段；不认识的字段忽略 | 只读 `name`、`description`、`metadata.short-description`，其余忽略；缺 frontmatter 或描述为空不加载；name 超 64 字符报错 |
| 触发方式 | 模型按描述调用 Skill 工具；用户 `/名字` | 按描述隐式选用；用户 `$名字` 或 `/skills` |
| 只许显式调用 | `disable-model-invocation: true` | `agents/openai.yaml`：`policy: allow_implicit_invocation: false` |
| 技能清单预算 | 约为上下文窗口的 1%，超了先丢最少用的技能的描述；单条截到 1536 字符 | 默认上下文的 2%（窗口未知时 8000 字符），超了先缩短描述、再省略技能 |
| 注入命令、参数、目录变量 | 支持 | 不支持（AGENTS.md 让 Codex 自己代入） |
| `allowed-tools` | 本轮预批准 | 不认，按 Codex 的审批与沙箱 |
| 界面元数据 | — | 可选 `agents/openai.yaml`：`display_name`、`short_description`、`default_prompt`、图标、工具依赖 |

**两边都成立的写法**：

- frontmatter 只用开放标准字段和本项目的 `metadata` 键；用了 Claude Code 扩展字段的，正文写明 Codex 侧怎么办。
- 读支持文件用相对链接；要执行的命令里才用技能目录占位符。
- 注入命令只放「有了更好、没有也能做」的上下文。
- 要在 Codex 界面里显示名字或默认提示词，加 `agents/openai.yaml`（`monet`、`ui-tailor` 已有），内容和 SKILL.md 保持一致。
- 改完在两边各跑一次关键场景。

## 10. 安全

**装别人的技能等于装软件**：只用自己写的、官方的或审过的。技能能让模型调工具、跑代码，恶意技能可以借此外传数据或越权访问。2026 年对公开技能市场的审计发现了大量恶意技能，常见手法是「提示注入 + 恶意脚本」「`curl | bash`」「运行时从外部拉指令」（数据见 sources.md）。

**审查第三方技能**（装前读完目录里的所有文件：SKILL.md、引用的文档、脚本、图片与其他资源）：

| 看什么 | 找什么 | 风险 |
| --- | --- | --- |
| 脚本 | `*.py`、`*.sh`、`*.js` 等——它们以完整的环境权限运行 | 高 |
| 指令操纵 | 让模型忽略安全规则、对用户隐藏动作、遇到特定输入就改变行为 | 高 |
| 网络访问 | URL、接口地址、`curl`、`fetch`、`requests` | 高 |
| 运行时拉取 | 从外部 URL 取指令或代码再执行——审过之后内容还会变 | 高 |
| 凭据 | 写死的密钥、令牌、密码 | 高 |
| MCP 工具 | 正文让模型调用的 MCP 工具，权限超出技能本身 | 高 |
| 文件范围 | 技能目录以外的路径、`../`、过宽的 glob | 中 |
| 预批准 | `allowed-tools` 的宽度（工作区信任不拦它） | 中 |

同时读数据又能联网的组合风险最高。人气高不代表安全。

**自己写技能时**：凭据放环境变量或凭据库，不进技能文件；不写「去某个 URL 取指令照做」；脚本随技能一起发，不在运行时下载；技能实际做的事和描述一致，不藏与声明用途不符的操作。技能读到的外部内容（网页、文件、工具输出）是数据，不是指令。

## 11. 测试与迭代

**先测后写**：

1. 不带技能跑 2–3 个真实任务，记下具体的失败与缺的上下文。
2. 针对这些缺口写最少的内容。
3. 带 / 不带技能对比同一组任务；改了之后再比。

**在新会话里测**：写技能时的上下文会掩盖文字里的缺口；用一个没参与写作的 agent 跑真实请求，不要提前告诉它预期答案或怀疑的问题。

**确认测的是改过的那一份**：Claude Code 调用技能时，输出开头的 Base directory 说明加载的是哪个目录。2026-11-12 实测：会话在主检出 `.claude/worktrees/` 下的 worktree 里工作时，Skill 工具加载的是主检出 `.claude/skills` 那份（主检出当前分支上的版本），worktree 里的改动不生效。这时先直接读改过的文件，核对会被替换的占位符、注入命令这类渲染风险；触发与效果测试等合并进主检出所在分支之后做，或换到 Base directory 指向改动所在目录的新会话里做。

**触发测试**：

- 准备「该触发」和「不该触发」两组真实说法，每组至少 3 条；最有价值的反例是「相近但不该用」的说法（关键词相同、要的是别的事）。
- 说法要像真用户：口语、错别字、文件路径、背景交代都带上；该触发的那组里要有没点名领域、但确实需要它的说法。
- 模型行为不确定，同一句跑几次看触发率。描述改得多时，留一部分说法不参与调整、只用来验证，防止对着题目调。
- 只需一步、模型自己能做的请求本来就不一定触发，别拿它当失败。

**效果测试**：至少 3 个场景；预期写成能检查的断言，能用脚本检查的写脚本。

**看模型怎么用这个技能**：读文件的顺序出乎意料 → 结构不直观；没跟到重要的链接 → 链接写得不够明显；反复读同一份支持文件 → 考虑挪进 SKILL.md；某个文件从来不读 → 可删，或链接没写清什么时候读。

**两边、多模型都测**：Claude Code 和 Codex 各跑关键场景；对大模型管用的写法，小模型可能需要更多细节，对大模型又不该过度解释。

**工具**：Claude Code 的 skill-creator 插件（`evals/evals.json` 存用例、带 / 不带技能并行跑、给描述调优）；`/skill-doctor` 看每个技能的上下文成本和使用次数；`/context` 看技能清单实际占多少；`claude --debug` 看 frontmatter 解析错误。

**迭代时机**——以下情况应主动提出更新 skill：

1. 用户纠正了 skill 的某个行为 → 立即更新规范
2. 发现 skill 缺少某个常用场景的覆盖 → 补充
3. 该触发时没触发、或抢了别的技能的触发 → 改 description，重跑触发测试
4. SKILL.md 超出篇幅预算 → 拆分到支持文件
5. 某条注入命令在当前环境报错 → 修复命令
6. 用技能解决了一个实际问题 → 细节进 references，主技能的「经验摘录」加一行（见第 7 节）
7. 用户添加了新的全局约束（如新的代码风格规范）→ 检查是否需要更新相关 skill
8. 换了模型或 agent 版本 → 重跑关键场景

## 12. 通用 vs 项目特定、通用性规范

两类都放在 `ai/jaSkills/`，区别只在登记处：通用技能登记在 `CLAUDE.md` / `AGENTS.md`，项目专属技能登记在 `ai/JASKILL.md`。
判据见 SKILL.md「落地三步」③；通用技能经货架跨项目复用（见 `shelf-ops`）。

通用 skill 必须能跨项目复用，以下三条是常见的通用性失误：

### 1. 命名不要绑定技术域

类名、工具名不能反映特定技术栈。

| ❌ 错误 | ✅ 正确 | 原因 |
| --- | --- | --- |
| `GameLogger` | `Logman` / `AppLogger` | 用户不一定在做游戏 |
| `UnityEventBus` | `EventBus` | 不一定用 Unity |
| `ReactPage` | `Page` | 不一定用 React |

### 2. 可变槽位不要硬编码

有些值在不同项目里不同，应描述为「由项目自定义」，而不是写死。

常见可变槽位示例：

| 槽位 | ❌ 硬编码 | ✅ 通用写法 |
| --- | --- | --- |
| 运行时环境标签 | `[Unity]` | `[运行时环境]`，由项目自定义（如 `Unity`、`React`、`Node`） |
| Pro 环境标识 | `#if !PRODUCTION` | 由项目自定义（Unity Define Symbols / NODE_ENV / REACT_APP_ENV 等） |
| 日志级别枚举 | `LogLevel.Debug` | 由项目实现决定 |

### 3. 项目特定数据不写进 skill

以下内容属于**项目数据**，不属于**通用规范**，应存放在 `PROJECT.md` 或项目文档中：

- 标签池（功能域标签列表）
- 具体的枚举值、配置项名称
- 项目内的文件路径、模块名

Skill 只写「原则」，不写「清单」。

## 13. 常见反模式

**不要这样做：**

- description 写得太宽泛（如「帮助开发」）→ 写做什么 + 什么时候用，具体到场景
- description 里概述流程步骤 → 步骤写正文，描述只写触发条件
- description 写成包罗万象的能力清单 → 只写真实能力和适用场景，必要时加边界
- 一个 skill 做多件不相关的事 → 拆分成多个 skill
- SKILL.md 里写大量示例代码 → 放 examples.md 或 references
- 每次加载都注入大量静态文本 → 静态规范放支持文件按需读取
- 支持文件层层链接（A 链 B、B 链 C）→ 都从 SKILL.md 直接链接
- 并列给出一堆做法 → 给一个默认，另一种情况一句话带过
- 叠加全大写、🔴、「必须」来强调 → 给一句理由；必须每次成立的用钩子
- 正文里写事故经过 → 结论进正文，经过进 commit 或 references
- 写会过期的日期条件 → 写现行做法，旧做法单列或删除
- `allowed-tools` 写裸 `Bash`、`Write`、`Edit` 或解释器通配 → 默认不写，要写就写到具体命令
- 让模型从外部 URL 取指令照做、运行时下载脚本 → 脚本随技能发，外部内容当数据
- 把项目路径硬编码进通用 skill → 用调用参数或动态查找
- 类名/工具名绑定技术域（如 `GameLogger`）→ 用通用名
- 可变槽位硬编码（如运行时标签写死为 `Unity`）→ 描述为「由项目自定义」
- 把项目标签池、枚举值写进 skill → 留在 PROJECT.md
- Windows 风格的反斜杠路径 → 一律正斜杠
