# 第四步：性能审核与反复复查

只在第四步、相关性能拓展或性能修改复验时加载。它规定证据口径，不替代当前版本的真实调研。

## 1. 基线与子步骤

先确认实际目标：设备/平台、并发或实体规模、数据量、帧率/延迟/内存目标、冷启动或热运行、
网络与存储条件、构建模式和已有性能预算。没有目标就记录现状与瓶颈，不臆造通用合格线。
将本步拆成项目适配的静态检查、测量、问题归因、建议和复验子步骤，记录到 `STEPS.md`。

执行顺序固定：先全项目代码与资源分析，形成性能假设和场景清单；再通过真实 computer use 启动/连接项目、
操作功能与场景，使用适合当前技术栈的性能工具录制并分析 runtime。最后把实测与静态假设逐项对账。

| 运行环境 | 实际观测方式 |
| --- | --- |
| Chrome/Web | 操作真实页面/流程，录制 DevTools Performance trace，按需结合 Memory、网络瀑布或更适合的 profiler |
| Unity | 运行真实场景，连接 Unity Profiler，按问题检查 CPU、Rendering、Memory 和目标设备数据 |
| Godot | 运行真实场景，使用当前版本 Profiler、Visual Profiler/Monitors 等适用工具观察帧时与资源 |
| 其他软件/引擎 | 真实操作应用，并使用该运行时或目标平台的对应 profiler；检索当前版本的官方操作方法 |

computer use 负责真实交互；可用专用工具/API 导出 profile，保留录制文件、场景输入、操作步骤和时间标识，
统一进入本轮 `evidence/`。截图可辅助说明，但不能替代 profile 数据；日志、单测或只打开应用同样不能替代。
环境、账号或观测工具不可用时先完成代码分析，准确列出缺口与补测步骤，本步保持受限，不能以静态报告结案。

从入口列出全部路由、任务/服务、场景/关卡、插件、后台工作、资源管线及共享模块。
静态审核覆盖全部自有代码与资源元数据；动态场景按核心链路、最重负载与生命周期风险选择并说明覆盖限制。
至少考虑启动、首用、连续使用、往返切换、并发/大数据、失败/取消/重试和退出回收，具体组合按项目确定。

每个场景记录：

```text
场景 ID / 对应模块 / 受审提交与本地改动
设备、OS、引擎或浏览器/运行时版本 / 构建与测量模式
输入数据、并发或实体数 / 缓存冷热状态 / 网络条件
操作步骤、预热、测量时长与重复次数
工具及参数 / 原始证据 / 结果与波动 / 未覆盖条件
```

不混用 dev 与生产构建、编辑器与导出运行、不同设备或不同数据规模的数值。
明确 profiler 自身开销；持续压力、真实账号或付费服务操作按本次用户授权执行。

## 2. 全域检查矩阵

每项映射实际模块和子步骤。不存在的领域记不适用；存在但不能运行的记待验证。

| 领域 | 检查什么 | 适合的证据 |
| --- | --- | --- |
| CPU/主线程 | 热循环、重复计算、同步 I/O、大对象解析/序列化、算法复杂度、锁竞争、事件循环阻塞 | profile、火焰图、耗时分布、队列等待 |
| 内存与所有权 | 监听/订阅、计时器、闭包保留、全局缓存、集合无界增长、池化生命周期、连接/句柄释放 | 时间曲线、分配分析、堆快照/保留路径、资源计数 |
| 渲染/更新 | 无效重渲染、布局抖动、大列表、过度绘制、draw calls、材质/批次、纹理/GPU 内存、每帧分配 | 组件/渲染 profile、CPU/GPU 帧时、慢帧分布、draw calls |
| 网络/数据库/存储 | N+1、无限查询、分页、重复请求、瀑布、缓存范围/失效、索引、连接池、导出/流式处理、背压 | 查询计划、请求瀑布、吞吐、延迟分布、池/队列长度 |
| 异步与并发 | 并发上限、超时、取消传播、竞态、重试退避、幂等、卸载后回写、工作线程收尾 | 时序、错误/取消测试、在途任务数、队列上界 |
| 加载与卸载 | 预加载、懒加载、分块、解码/实例化/上传、缓存失效、资源引用释放、场景/页面往返 | 首用/切换延迟、阶段耗时、回收后存活对象与资源数 |
| 素材与产物 | 重复资源、多余格式/分辨率、压缩、依赖重复、首包/分包、导出规则、未使用资源 | 文件清单、构建分析、包组成、下载量与运行内存 |

不要仅因为代码出现 memo、cache、对象池或异步 API 就判为优化完成。
每个优化同时评估内存、CPU、延迟、带宽与复杂度的交换；缓存与池化必须有边界和失效/回收策略。
GPU、原生资源、托管堆、进程 RSS 和外部缓冲区分开计量；磁盘压缩后的素材大小不代表解码内存。

## 3. 泄漏结论的门槛

分别判断：内存泄漏、工作集过大、瞬时峰值、频繁 GC/分配抖动及有意保留的有界缓存。

1. 固定负载反复执行同一生命周期，例如打开/关闭页面、加载/卸载场景、启动/取消任务。
2. 比较可比的稳定状态，结合运行时允许的方法观察 GC 后存活对象、资源数量或原生/GPU 释放情况。
3. 查保留引用/资源所有权和释放链；增长趋势与具体对象关联，而不是只看一张截图或 RSS 没回落。
4. 排除预热、分配器保留、缓存、调试器和 profiler 干扰。手动 GC 仅作为诊断条件并明确记录。
5. 对修复重复同一实验，报告趋势与剩余限制。无法运行时只报静态嫌疑和复现方案。

允许的结论：“此场景复现持续存活对象增长，保留链是……”“静态发现未解绑路径，运行待验证”。
禁止据静态扫描宣称“整个项目无内存泄漏”。没有发现也必须附场景范围、测量时长和未覆盖项。

## 4. 加载与素材体积

沿“发起 → 排队/请求 → 等待完成 → 解码 → 实例化/上传 → 使用 → 释放”逐段核对。
后台下载完成不表示主线程不会卡顿；取消后请求、解码、实例化或回写仍可能继续执行。
检查懒加载是否被静态 import/预取提前拉入、失败重试是否无限、并发是否有界、重复请求是否适当合并。

体积表至少按资源/模块列：

```text
路径/资源 ID | 源文件 bytes | 构建或导出 bytes | 传输压缩 bytes（如适用）
首用/按需/全部打包 | 解码后内存（实测/估计/未知） | 重复关系 | 预算 | 比基线变化
```

首次建立可比较基线，后续审核报告绝对量与变化比例。下载包、安装体积、源素材和运行内存不能相加混算。
若建议持续监控，写清构建清单、资源预算、差异阈值和 CI 检查方案；没有预算先收集基线。
用户授权落地时接入现有构建检查；否则交付监控建议，不凭“审核”创建后台定时任务。

## 5. 最详尽的阶段报告

除通用报告骨架外，第四步必须有：

1. 全项目静态覆盖表、动态场景覆盖表和环境限制。
2. 基线指标：CPU/GPU 帧时或响应延迟分布、内存峰值与稳定值、分配/GC、请求/查询/资源量、包体积；
   只报告实际适用和有证据的指标，小样本不得包装成可靠的 p95/p99。
3. 逐条问题：位置、触发条件、影响随规模如何变化、实测/静态/假设等级、证据与根因。
4. 优化建议：建议改法、收益依据、成本/风险、优先级、实施依赖、可操作的复验步骤和验收预算。
5. 已修改项的同条件前后对照；尚未实施的收益写预计/定性，不编造提速百分比。
6. 已确认问题、静态风险、待验证项、监控建议和下一轮重点分别列清。

不因前三步花得太久而压缩本步成结论摘要。环境缺失时完整交付静态结果及补测清单，标本步受限。

## 6. 复查

每轮保留新运行标识、项目版本、场景输入与原始证据；旧发现 ID 保持稳定，标新增/仍在/已修/失效。
用户要求全量复查时重新覆盖整个项目，旧问题复验和新的全域扫描都要做；不能只重跑旧问题。
仅要求验收某个修复时可限该场景，但明确这是局部复验。
报告相对上一轮和初始基线的差异、回归、无法比较原因，并更新 `STEPS.md` 中有证据支持的检查改进。
