# 内置拓展：UI/UX 与概念设计审核

有用户界面的项目（网页、桌面、移动应用、游戏）可启用。只在用户点名、`EXTRA-STEPS.md` 启用或准备阶段问过且用户同意时运行。
启用后排在拓展的第一个（编号照常 `X01`……），紧接第四步，复用它的走查与截图；真实操作的纪律见 [live.md](live.md)。
和其他拓展一样：范围是全部用户界面；先调研（当前版本的官方设计与无障碍指南、所用组件库的文档、同类产品的成熟做法，记法同阶段报告的调研表）；
子步骤写进本轮日志；默认只交付建议、工作包与决定项，用户授权的小修除外。
审核在现有设计系统里找问题，不以换风格为目标；要换风格是单独的设计任务。

## 1. 分工与调用顺序

| 角色 | 在本拓展里做什么 |
| --- | --- |
| 审核主线程（本技能） | 实例化子步骤、写共同 brief、分流、核对评审引用、归纳推荐、出工作包与决定项、写日志、控成本 |
| `ui-tailor` | UX 与界面：概念模型、术语一词一义、信息架构、任务流程、状态与反馈、失败恢复、可用性；复核审图里的 UX 类条目，判断比稿方向的使用路径 |
| `monet` | 视觉与设计系统：整体风格、设计系统与实现的对账、对比度与层级、全局一致；游戏还管角色、场景、效果与概念文档；推荐方向的视觉审核 |
| 出图 / 审图工具（如 `codex-visual`） | 审图的第二意见、方向稿出图；额度、附图上限、比稿子线程的模型与推理档按它的规定 |
| 批注报告工具（如 `annotated-report`） | 总报告与验收回复页 |

顺序：主线程编排 → `monet` 与 `ui-tailor` 定约束 → 工具出审图 → 设计技能复核、主线程分流 → 工具出方向稿 → 互评 → 设计技能复核产物 → 主线程归纳交付。
设计判断不由工具或主线程替代；没有这些技能时主线程按同一顺序做，复核写明是同一 agent 自审，不虚构第二意见。
没有出图工具时，比稿用标注截图或线框说明方向，不冒充设计稿。

## 2. 标准子步骤（实例化进本轮日志，按项目增删）

1. **启用与范围**：界面清单（应用、屏、场景）、设计系统入口与决定清单、授权（能否小修、能否用外部额度）、
   工具与额度（宿主、出图工具，有无付费兜底）、档位（轻量：不比稿；完整：含比稿）与成本预估。
2. **设计系统与已定决定对账**（概念审核）：按设计技能的读法读设计系统根入口 → UI/UX 入口 → 相关模块文档；
   列出硬约束与已定决定（带编号、摘原文），后面所有 brief 与复核都以它为准。核对规范与实现的偏差（token、组件、状态、文案）、
   过时或重复的设计文档、只有 token 没有流程 / 状态 / 动效的 UX 描述；游戏还核对角色、场景、效果与当期概念文档。
3. **实测与截图矩阵**：用第四步的走查与截图矩阵（[live.md](live.md) §4）；单独运行本拓展时按 live.md 自己走一遍。
   补 UX 观察：命名是否一词一义、入口好不好找、反馈与失败恢复、焦点与键盘、对比度。
4. **审图**：第二意见交出图 / 审图工具的审图模式，brief 摘入第 2 项的硬约束原文；截图多于工具的附图上限时，
   把次要的屏拼成一张并加标签条（brief 写明标签条不是界面）。工具不可用时由设计技能自审并写明。
5. **复核与分流**：逐条回到代码、规范原文、已定决定与真实数据分布核对。模拟数据的长度与分布可能和真实数据不同，
   截图里的列宽、留白、截断先查定宽依据再判。每条判一类，写进去向表：
   - 属实且小、有小修授权 → 直接修并复测，记进本拓展的改动表；
   - 属实、做法清楚 → 工作包；
   - 属实、存在真正的方向之争 → 比稿题候选；
   - 与已定决定冲突 → 不改，写明决定编号；确实值得重议的转决定项；
   - 合规或纯属视觉偏好 → 不动，或列为可选工作包。
6. **选题与比稿**（完整档）：比稿题只从「属实且有方向之争」里选，按用户影响排序，默认至多 2 个题、每题 2 个方向。
   每个方向一个子线程，出稿按出图工具的比稿规则（没有时：与主线程同模型，方向稿用最高推理档）。
   共同 brief 由主线程写：产品与用户、视口与设备、硬约束原文、评分标准与权重，以及**必须保持原样的特殊样式与模拟数据清单**
   ——只写「不得出现 X」，生图可能把相近的既有样式一起改掉。每个子线程把图、设计说明与自评写进自己的交稿文件。
7. **互评与归纳**：互评按出图工具的规则（不评自己的稿）；有两个以上题时，同题对手稿细评，别题的稿从外部视角评。
   主线程逐条核对评审引用的规范条文原文，核不上的不采信；生图走样（错字、改了模拟数据、改了既有样式）逐格核对，不计入方案分。
   归纳成：得分表（自评 / 对手评 / 外部评 / 平均，写明谁评的）、两稿共识（选哪个都照做的）、分歧在哪、
   推荐（以哪个为底、吸收另一个的哪几点、为什么）；推荐方向再过一次 `monet` 视角的视觉审核。
8. **工作包与决定项**：每个工作包能单独派给一个 agent：范围、依据（审图条目、规范节、决定编号）、具体改法、
   验收（主题 × 语言 × 宽度矩阵、要跑通的用户任务、要补的测试）、别踩的线；依赖用户决定的标「待定」并指向决定项。
   每个决定项给推荐与不回答时的默认。
9. **交接**（验收期）：用户定下、本期不做的工作包转成交接档（见 [acceptance.md](acceptance.md) §3），正文就是工作包；
   用户批准的设计结论由 `ui-tailor` / `monet` 晋升进设计系统的定稿区，审核里不提前改定稿。

## 3. 报告与素材

- 总报告单列本拓展一节（用户点名时并进点名的那一节）：实测覆盖与修复、审图条目与去向表、每个比稿题的
  现状 → 方向 → 得分表 → 共识与分歧 → 推荐、工作包、决定项。要用户看的图（现状截图、方向稿、改前改后）嵌进报告页。
- 素材按设计技能的归档规则放（候选与比稿区），不进定稿区，也不进审核目录；不入库的，在本轮日志「续接」写明位置。
- 阶段报告 `x0n-uiux.md` 照阶段报告骨架写，比稿细节链到素材目录，不复制设计说明全文。

## 4. 成本与额度

- 开审时就查出图工具的额度与有无付费兜底；不够就把审图与比稿排到重置之后、先做别的步骤，排期写进「续接」。
  每批方向子线程派出前再查一次：几个子线程同时出图，消耗成倍。
- 子线程只读自己方向需要的规范节；交稿说明与互评都落文件，主线程读文件归纳，不在会话里来回转述。
- 额度或授权不够比稿时走轻量档（第 1–5 与第 8 项），把「要不要比稿、比哪几个题」列成决定项。
