# 公共规则：覆盖、证据、报告、目录与续跑

每个模块共用的记录与证据口径，只此一份。首次准备时读 §1 与 §7；出方案、删文件、写报告、派子代理、续跑时按目录查对应的节。节号稳定，不重排。

1. 覆盖规则（含并行分工与分区深读）
2. 研究与方案
3. 删除与精简证据
4. 问题与阶段交付
5. 拓展模块约定
6. 研究起点

11. 审核脚本复用

## 1. 覆盖规则

`run-id` 采用项目已有运行编号习惯，否则使用日期加序号。记录根目录、分支/提交（无 Git 则文件摘要）、
工作区变更、技术栈版本、目标平台、时间、本轮跑哪些模块和授权范围。Git 状态只读，不切换用户工作台。

先建立文件总体：逐文件区分自有文本、自有二进制、第三方依赖、生成物、外部链接和受保护范围。
忽略规则不等于无用；也不因为某个文件未跟踪就允许删除。不可枚举范围只记录根级边界，数量写未知。
目录符号链接不递归跟出项目；同一真实文件去重并保留别名，避免循环遍历和重复计算。
大型依赖目录可按来源/锁文件/体积汇总，二进制查元数据和资源/包关系，不能声称已逐行审核。

`coverage.csv` 的最小字段：

```text
path,kind,module,revision,step,substep_id,status,method,evidence,reason
```

- `step`：模块代号（`files`、`prompt`、`tests`、`code`、`perf`）或拓展编号 `X01`……；每个模块均从完整清单确定适用面。
  一次深读兼做几个模块时写多个（如 `code;perf`）。字段名沿用 `step`，旧数据里的 `01`–`05` 按 §10 对照读。
- `substep_id`：关联本轮 `00-log.md` 子步骤表的稳定 ID；同一文件可分多行关联不同子步骤，覆盖数量按文件去重。
- `status`：待检查、已检查、待验证、不适用、受限。已删除文件保留删除前记录与实施结果。
- `method`：全文分批阅读、语义分析、引用核验、引擎资源检查、运行测量等；只列目录不算已检查。
- `evidence`：报告中的发现 ID、实际检查记录或受审版本；“没有发现”也记录检查方法。
- `reason`：不适用/受限的具体理由，不能空填，也不能用“文件太多”当排除理由。

报告每个模块的总体数量、适用数量、已检查数、未检查数、待验证数、受限数与排除清单。
覆盖率 = 已检查适用项 / 可枚举的适用项；受限与未知另列，不能把分母缩小后宣称全仓 100%。
文本按文件/模块统计，二进制按资源统计，运行按场景统计，不能混成一个虚假的百分比。
只完成静态 review 时说“静态范围已审”，动态验收缺失仍为待验证。

并行按互斥模块或检查维度分工，共享画像、规范和同一基线；协调者复核跨模块发现与覆盖并去重。
给每个子代理写明它负责改哪些文件、哪些文件别人在改不能碰（需要改的列进它的报告）；子代理不做改变 Git 状态的操作，
由协调者统一核对、验证和提交。子代理的报告是给协调者的，结论经协调者核过再进阶段报告。
复审员新开，不续接做第一遍的那个；宿主有不止一种模型可选时换一种。读量、额度消耗与怎么搭配，校准后记进项目蓝图。
变化导致旧结论失效时，标明失效项并重审相关依赖；用户要求全量复查则重新覆盖全部适用项。

**分区深读**（代码模块的各部分、测试模块与性能模块的静态线索共用一次全量阅读时）：

- 一份简报发给所有分区：共同的画像、规范入口与基线，加按模块分开的清单（如结构 / 复用 / 注释、协议 / 后端 / 前端、
  测试成本、静态性能线索），发现按清单分别编号。每个模块照常单独调研、汇总与交付。
- 分区按「一个子代理一轮能全文读完」来切，按行数估，文件数只作参考。先派一个分区试出这档模型的实际读量，再定其余分区；校准值记进项目蓝图。
- 读法按文件类型在简报里先定，要够得上这个模块要查的东西（例：源码与配置全文读；测试读用例清单与关键断言；
  迁移读头注释、按风险模式扫描、高风险的通读；词典与契约按结构与用法核验），写进 `method`。
  不是全文读的，报告的覆盖数字旁边写明读法分档，不写成「全文读完」。
- 子代理交回先核覆盖口径（全文读了多少、哪些只抽读、为什么），不达标的当场派补读，不留到汇总才发现。
- 分区多时汇总也交一个子代理：读各分区证据文件、去重、对上已有编号、分配新编号；协调者逐条核 P1 与跨分区的调用链，再定严重度。

## 2. 研究与方案

每个阶段报告单独记录以下表格，网址直接指向原文而非搜索结果页：

```text
查询 | 检索日期 | 来源标题和 URL | 来源版本 | 可核验的结论 | 适用前提 | 本项目证据 | 采纳/不采纳及理由
```

官方文档描述的是框架契约还是建议要分开；开源项目布局是案例，不能冒称行业标准。
先读本地随版本提供的文档，再网上核验适用版本；本地规定与外部建议冲突时明确差异，
不能静默用网上的习惯覆盖项目决策。资料不足就写不足，不编造最佳实践、收益或来源。

每个模块的方案沟通必须具体：

```text
范围/文件：
当前问题与证据：
建议改动（文件路径、职责变化或目录前后图）：
为什么适合这个项目、参考什么：
预期好处（实测/估计/定性）：
代价、行为与契约影响：
验证和恢复方式：
已有授权；仍需用户决定的具体事项：
```

发现过多时可分批讨论，但最终范围仍是整个项目。获得该批授权后不再按文件重复问同一问题。

## 3. 删除与精简证据

删除每个候选项前确认：

1. 内容是什么、谁使用、是否已被准确替代；比较正文与差异，不能仅根据文件名或时间判断。
2. 文档链接/锚点、import、动态 import/反射/路径拼装、约定入口、配置、CI、打包/导出均已核对。
3. 游戏资源检查场景/预制体/资源图、UID/GUID、导入元数据、动态加载和外部内容管线。
   采用目标引擎当前版本支持的重命名/移动机制，引用和配套元数据一起更新。
4. 不是受保护的协议/手动存档、他人未完成文件、许可证/归属声明、独有产品决策或恢复资料。
   历史迁移、锁文件、导入元数据及看似重复的生成物，先查生成/重建契约，不能凭外形自动删除。
5. 记录恢复依据：已提交的原版本，或统一目录内仅保存该项所需的差异/备份；未知来源内容保留。
   不把“Git 管理”当作未跟踪或未提交内容已备份，不运行广泛清理命令代替逐项删除。

删除清单写明路径、用途判定、引用证据、保留的权威源、恢复依据和验证结果。
精简文档前后逐条核对强制性语气、条件、例外、术语和待决项；删除重复措辞不能删除规则差异。
文件移动后核对文本链接、构建/运行引用和引擎资源引用，不能只验 Markdown 链接。

## 4. 问题与阶段交付

问题 ID 跨复查稳定，例如 `PA-001`；所属模块可以变化，状态和证据保留。每条至少包含：

```text
ID / 优先级 / 状态 / 所属模块
文件与准确位置 / 受审版本
问题、触发条件及具体影响
证据等级：实测确认 / 静态证据 / 待验证假设
证据或复现步骤 / 来源链接
建议、替代方案与代价 / 影响范围与依赖
实施状态 / 验收条件 / 待办链接或 ID
```

优先级按影响、触发概率、规模和修复成本说明理由，不能把所有结构偏好标高危。
待办有既有唯一来源时只关联既有 ID，审核目录存证据和建议；未经授权不向外部任务平台写入。
若用户要求本技能所有新文档集中一处，新建议先保留在 `FINDINGS.md`，不同时复制到其他文档。

一个模块一份阶段报告，文件名是模块代号加 `-report`（`prompt-report.md`、`code-report.md` 等，拓展是 `x01-主题.md`），免得和技能的参考文件同名；篇幅大时按部分分册，文件名仍以模块代号开头。
使用以下骨架，内容为空的可说明无发现，不造空任务：

```markdown
# 模块名（代号）：主题
## 结论与完成状态
## 基线、全项目覆盖与限制
## 本模块调研与适配结论
## 已讨论方案、授权和取舍
## 发现与证据
## 已执行改动（文件路径、改动目的、原因与 commit/PR 定位）
## 验证（命令目的、结果、失败归因与未验证项）
## 建议、待办和下一步
```

验证按实际变更选择：文档清理查链接与语义，模块移动查消费者与构建，行为修改查契约/回归，
性能优化跑可比较场景。扫描器告警须人工复核，现有测试绿也不能证明整个项目没有问题。
数字旁边写清口径；目标没完全达成的，剩余数量与原因紧跟在数字后面，别让读者到别处找原因。

总报告 `99-report.md` 写给要批注的人看：先结论、再各模块摘要、再待决定事项（每项给推荐与默认）、最后问题清单；
用户开审时点名的要求，在结论后单列一节先回应（做到什么、没做到的原因与补做清单、要用户做的事）。
只跑一个模块时，总报告写这个模块的结论、待决定事项与问题清单，不把阶段报告再抄一遍。
每节有稳定锚点，方便批注引用。用批注报告工具生成页面发布，源文留在运行目录。
宿主协议要求逐文件贴改动时，源稿里放占位、由脚本从 `git diff` 展开：代码与仓库一字不差，也不占模型输出；展开脚本存进 `scripts/`。

阶段报告只用路径定位代码和文档，实现及删除原文由对应 commit 提供；不复制源码、逐行 diff 或另存完整 patch。
「不贴源码」只管阶段报告：会话汇报与给用户验收的总报告页按宿主协议的报告规范写（例如要求逐文件贴改动时照贴）；
还没落实的建议改动（受保护文件的建议稿、提示词审核的建议改动）没有提交可指，存进本轮 `proposals/`。
路径很多时按模块分组，仍能定位各变更文件；保留原因、结论、验证和未完成项，不把机器指标全文转贴成人读报告。
所有模块的 review 均保留：文件路径、改了什么、为什么、影响/取舍、验证结果与未完成项；代码细节通过对应 commit 查看。
每个模块提交本任务的改动与报告（宿主协议要求先只暂存时照协议），记录该模块基线及提交主题/PR；提交前可用唯一提交主题或 PR 定位，
交付时给出实际提交 SHA，rebase 后以目标分支 SHA 为准并说明映射，不为给提交写入自身 SHA 反复提交。

## 5. 拓展模块约定

用户可在 `AUDIT_DIR/EXTRA-STEPS.md` 添加条目。每项最少有 ID、启用状态、目标和验收条件；
可附重点、来源线索、限制。朴素的自然语言清单同样可读，不因没遵守模板就忽略真实用户要求。
只含示例、明确禁用或没有真实目标的项不执行。需求歧义先查已有上下文，再问具体缺口。
来源线索仍需实时打开核验；不得因为用户提供链接就省去当前阶段的真实研究。

- 准备时识别拓展文件；轮到拓展模块前重新核对一次，纳入用户期间的修改。
- 每个启用条目按文档顺序、作为独立阶段 `X01`、`X02`……运行，同样全项目覆盖、先真实调研、沟通方案、落实/建议与验证，
  走同一套共用流程并写 `runs/<run-id>/x01-主题.md`。例如超出代码模块注释精简要求的注释契约专项；
  不能因一个例子只检查某个目录。用户明确缩小范围时注明“局部专项”。
- 拓展默认先交付建议；当前用户已授权该项修改时执行。启用一个审核条目本身不等于授权修改其全部对象。
- 文件缺失、没有启用条目或全部完成时，继续收口。不自行编造拓展。
- 拓展改了代码时复验相关行为/性能。
- 拓展不覆盖运行中的用户指令、现有权限或受保护范围，不自动触发外部发布、安装或全量重构。
- 界面、体验与同品类对比的评审不写成拓展，归 `visual-audit` 技能单独跑一轮。

## 7. 目录、审核根文档、本轮日志与蓝图迭代

已有同职能目录时优先复用并记录为 `AUDIT_DIR`，不另建第二套；文件名按项目现有命名风格调整一次，随后保持稳定。

| 层 | 文件 | 内容与加载时机 |
| --- | --- | --- |
| 技能 | `SKILL.md`、`references/` | 通用方法与证据口径；不放任何项目的蓝图、发现、数字与路径 |
| 审核根 | `INDEX.md` | 入口：「当前」一段（哪一轮、跑哪些模块、状态、续接从哪读，覆盖式更新）+ 轮次表（一轮一行）；不是日志；继续时先读 |
| 审核根 | `STEPS.md` | **本项目**的蓝图：各模块的标准子步骤（带版本、就地升版）、跨轮经验、可复用工具登记；开工时实例化，收尾写回 |
| 审核根 | `FINDINGS.md` | 本项目的问题登记簿：稳定 ID 一行一条、只留最新状态、建议与验收条件；有既有待办时引用其 ID，不复制完整任务 |
| 审核根 | `EXTRA-STEPS.md` | 用户维护的拓展审核要求；准备时识别，轮到拓展模块时核对并执行，收口统一收尾 |
| 审核根 | `scripts/` | 反复使用的清单、引用、计量、走查和验证脚本；运行前查找复用，登记在 `STEPS.md` |
| 审核根 | `CONVENTIONS.md` | 确有缺口时才创建的结构与代码规范；标明已采纳或待讨论 |
| 运行目录 | `00-log.md` | 本轮日志：用户原话（原样）、本轮模块、范围与授权、子步骤表、续接断点、进度、收口、复盘、验收；续接先读 |
| 运行目录 | 各模块的阶段报告、`x01-*.md` | 各模块的方案、调研来源、发现、实施和验证；按模块读 |
| 运行目录 | `99-report.md` | 总报告的源文；交给批注报告工具（如 `annotated-report`）生成可批注页面发布 |
| 运行目录 | `coverage.csv`、`metrics/`、`evidence/`、`proposals/` | 覆盖清单、指标明细、复验证据与还没落实的建议稿；按需读，敏感数据不写入，收口时清理无后续价值项 |

没开始的模块不创建空报告。保留比较所需的证据，复查写差异，不复制全套旧报告。
既有项目文档可在授权内原位精简；新拆出的正文也放在 `AUDIT_DIR` 内，原位置只保留必要索引。
既有唯一规范仍是权威源，新增规范引用它、不复述它；规范变化与报告建议不得混写成已实施事实。

审核根的 `INDEX.md`、`STEPS.md`、`FINDINGS.md` 都是本项目一份、跨轮更新，不在技能里；每轮的执行在 `runs/<run-id>/00-log.md`。
问题状态在 `FINDINGS.md`，执行证据在阶段报告，子步骤以链接关联；都不是第二份问题台账。
每份根文档开头一句话写明：它是什么、本项目只此一份（每轮的东西在运行目录）、和另外几份的关系。

`INDEX.md`（入口，不是日志）：

```markdown
# 审核入口（本项目一份；每轮的日志在 runs/<run-id>/00-log.md）
当前：<run-id> · <跑哪些模块、范围一句> · <进行中 / 已交付待验收 / 已验收>；续接先读本轮日志「续接」节（验收期读「七、验收」最新一小节）
| 轮次 | 运行目录 | 模块与范围 | 状态 | 总报告 |
其余入口：STEPS（本项目蓝图）· FINDINGS（问题登记簿）· EXTRA-STEPS · 技能
```

「当前」一段覆盖式更新，旧的「当前」不保留（它在那一轮的日志里）；历史只在轮次表里一轮一行，历史结论绑定当时基线，不覆盖现状。

`STEPS.md`（本项目的蓝图：技能只给通用方法，本项目怎么拆、怎么校准写在这里；只留仍有效的）：

```markdown
# 审核蓝图（本项目一份，逐轮校准升版；通用方法在技能里）
## 准备 · vK
## 模块名（代号）· 蓝图 vK（上次校准：<run-id>；vK-1 → vK：一句原因）
### <子步骤 ID> · 子步骤名称 — 目标 / 方法 / 产出与验收 / 适用条件
跨轮经验：每条一句，做法 + 依据（哪一轮发现的什么问题）
## 其余模块、拓展、收口：同上，按完整一轮的顺序排
## 可复用工具 — 一张表：脚本、用途与调用、适用范围、最近验证
```

升版本就地改写那个模块的节，不在文末追加「增量」节；不写本轮状态、基线和完成情况（那些在本轮日志）；跨轮经验跟着它所属的模块。

`FINDINGS.md`（本项目的问题登记簿）：

```markdown
# 审核发现（本项目一份；任务状态以 <任务来源> 为准）
## 开放 — | ID | 优先级 | 一句话结论 | 状态 | 最近复验 | 详情 | 待办 |
## 已关闭 — | ID | 结论 | 关闭方式与证据 | 关闭于 |
```

一个 ID 一行，按优先级再按编号排；复验时就地改状态与「最近复验」，细节在那一轮的报告里，不按轮分节。
没编 ID 的条目（审图建议、比稿结论等）留在那一轮的报告里，转成要跟踪的问题时才编号。
现有文件不是这个结构的，在文件整理模块或收口时一次改齐：ID 不变，旧链接改到新位置。

`00-log.md`（本轮）：

```markdown
# 运行 <run-id> · <主题>
## 一、用户原话（原样）= 真源需求，收口逐条验收
## 二、本轮模块、范围、授权与任务拆解（子步骤表：ID / 目标与范围 / 依赖与方法 / 产出与验收 / 状态与证据）
## 三、续接（断点，覆盖式更新；模板见 §9）
## 四、进度（时间 · 子步骤 · 事件，一行一条）
## 五、收口验收（真源需求与各模块要求逐条：达成 / 回到哪个模块重做）
## 六、复盘（发现问题的、重复低效的、漏掉边界的；写回蓝图的改动）
## 七、验收（总报告发出后按批注轮次分小节：分组、决定编号、分工、断点、收尾清单；见 acceptance.md）
```

**子步骤**：每项使用稳定 ID——模块代号加序号（如 `prompt-S03`），拓展是 `X01-S01`；已有蓝图里的旧编号（如 `04-S03`）原样沿用，
不为对齐前缀重排（对照见 §10）。写清目标、范围、前置依赖、方法/来源、产出、验收条件与当前状态。
开始时记进行中，完成后立即写证据链接与结果，受阻时写阻塞点及仍可推进的其他子步骤。
允许并行无依赖子步骤；修改、验证和依赖步骤按顺序执行。新发现导致增删/重排时记原因，不静默漏项。
同一模块共用已核验资料；子步骤出现新的技术问题时补做针对性网上研究，不凭旧链接推断。

子步骤状态：待执行 / 进行中 / 已完成 / 受阻 / 已取消；取消或受阻必须写原因。
准备下一个模块时按需实例化它的子步骤，不提前臆造完整项目细节。
覆盖清单关联子步骤 ID，模块验收时核对：适用项均有负责的子步骤，没有孤儿范围或遗漏的依赖。
“子步骤已完成”表示要求的检查和产出完成，不等同所有发现已修；未满足的验收条件不能划为完成。
复查保留稳定 ID 和旧轮证据，当前轮所有需重审项重新记待执行，不把旧轮勾选当成新轮完成。
新一轮先验证版本、模块和历史改进是否仍适用，再调整蓝图。结果有新证据才改流程，避免越审越繁琐。

## 8. 运行材料生命周期与收口清理

收口必须处理审核留下的运行材料，不能只给清理建议而把过程数据原样堆回项目：本轮产生的每轮都清；
历届留下的，在完整一轮或本轮含提示词与文档模块时一并按用途清。保留的逐项说明用途。
先区分可执行复用脚本与它生成的 CSV/JSON/日志；机器格式不等于无用，存在于磁盘也不等于每轮自动消耗 token。
清单、覆盖 CSV、AST/哈希 JSON、原始日志是工具使用的证据数据，支持续接、覆盖复核和前后比较；脚本才是可执行工具。

| 去留 | 判断与动作 |
| --- | --- |
| 长期保留 | 精简的阶段 review、执行范围 / 命令目的 / 验证结果摘要、实际子步骤和迭代经验、未结发现；实现细节以 Git 为准，由 commit 定位 |
| 有条件保留 | 下轮比较基线、未结问题原始证据、不可重建的 profile、复验必需输入、已验证复用脚本；写清用途和版本 |
| 完成用途后删除 | 一次性 inventory、重复清单/AST/哈希快照、被最终结果替代的过程 JSON/CSV、临时日志与改写脚本 |

- 逐组检查后续消费者和重建代价，将必要结论提炼进现有 review、本轮日志或 `STEPS.md` 蓝图；删除前核对报告/脚本引用和恢复依据，
  删除时修正链接与脚本输入引用。
- 保留记录直接写在阶段报告，说明路径/目录、消费者或下次使用场景、版本与何时可删；不为登记去留再制造一套庞大清单，也不把原始数据转抄成长文。
- 旧覆盖表不能替代下一轮重新生成的清单，旧清单仅用于版本明确的比较，不作为当前覆盖证明；
  若仍有待复验问题，保留其最小证据并列为例外，不能让清理破坏验证。
- 不按扩展名批量删除，不读取受保护范围；默认入口只指向当前状态与必要材料，不递归加载 `runs/`，历史证据按问题查询，按需用脚本筛出命中项和摘要。
- 本轮含 `prompt` 模块时，清理后重算库存与加载成本（口径见 references/prompt.md §2）；不含时只记清理了什么。

## 9. 额度与断点续跑

额度用尽时会话直接中断，不给收尾机会；断点只能是「随做随存」的副产品，不能指望最后一刻补写。

断点写在本轮 `00-log.md` 的「三、续接」节，覆盖式更新、只留最新一份：

```markdown
## 三、续接
- 断点：<模块与子步骤 ID、名称>，做到哪、还剩什么
- 已落盘：<运行目录里已写的报告、证据、脚本；已暂存或提交的改动与 SHA>
- 只在本机、不入库：<被忽略的素材、本地兜底环境，写绝对路径与所在 worktree；换 worktree 或换机器要拷或重建；没有写「无」>
- 在途子代理：<名字 · 负责的文件 · 产出路径 · 写到哪>；没有写「无」
- 未落盘：<只存在于会话、续跑时要重做的部分；没有写「无」>
- 下一步第一件事：<一句可直接执行的动作>
- 环境：<分支、worktree、依赖服务、凭据缺口等续跑前要核对的事>
- 额度：<宿主各窗口用到多少、何时重置；外部工具（如出图工具）的额度与有无付费兜底；续跑方式：自动续跑的任务名与时间，或交用户手动>
```

- **查用量**：用宿主给的途径——Claude Code 桌面版的用量工具（各额度窗口的已用百分比与重置时间）、CLI 的用量命令、
  API 账户的 Usage & Cost 接口或自己记的 `usage` 字段；外部工具用它自己的状态命令（如出图工具的额度检查）。查不到就靠「随做随存」兜底，不猜额度。
  宿主能查用量时，在开一个模块、派子代理、做实测这类耗量大的动作前查一次。外部工具的额度（如出图用的订阅窗口）开审时一起查，不够的子步骤排到重置之后、先做别的。
- **何时主动停**：任一窗口到 90%，或按本轮已耗速度估算撑不到下一个可交付单元（一个子步骤、一次实测）。
  先写好断点再停，不硬撑到被截断；停在子步骤边界，不为凑额度把子步骤拆碎。
- **主线程的上下文也是预算**：用得多了（如过半）就只做协调——派活、核对、合并、写日志，读得多的活交子代理、结论落文件。
- **自动续跑**：只在用户授权过时排，授权只管本轮；用宿主的定时机制排在额度重置之后几分钟，没有这类机制就把续接指令交给用户。任务提示写清
  「继续 project-audit 运行 <run-id>：先读 INDEX.md 与 00-log.md 的续接节」，任务名与时间记进「续接」。
  续跑若发现本轮已收口，什么都不做并说明。
- **续跑核对**：先读 `INDEX.md` 与本轮 `00-log.md`（按需看证据，不重读历史报告）。分支与 HEAD、暂存区与未提交改动、运行目录里的产物，
  与断点记录逐项对照；不一致以磁盘与 Git 为准，在进度里记一行差异。再从断点继续，不重做已完成的子步骤。
  中断期间别的会话动过同一批文件的，先停下问。上一会话留下没提交的改动，先按宿主协议处理（如单独提交、写明来源），再开始新改动。
- **子代理**：派一批之前查一次额度——并行的子代理共用宿主额度，消耗按人数成倍，估算撑不到这批交回就少派或先写断点。
  派出前把分工与产出路径写进断点；让它先建好产出文件（标题与要填的节）再边做边写，结论落到运行目录才算完成，
  被截断时留下的是半份结果而不是零。会话被截断时在途的按「未落盘」处理：只读了素材、文件里没有结论的重派。
- **换会话、换 worktree、换账号**：会话临时目录换会话就找不到，要留的脚本进 `scripts/`、素材写进「只在本机」；
  新 worktree 里没有被忽略的文件，按断点里的绝对路径拷过来；续跑换了账号时，上一账号发布的页面改不了、批注清不掉，回复照发新页并说明。

## 11. 审核脚本复用

大量重复使用的扫描、引用检查、指标采集与报告汇总脚本保存到 `AUDIT_DIR/scripts/`，下次先检查并复用，
不在每轮重新生成相同逻辑。用项目已有的运行时写（如 Node 项目就用 Node），不为审核引入新的运行时依赖。
参数化项目根、模块和输出目录，避免写死机器路径；不把凭据或一次性数据写入脚本。
在 `STEPS.md` 记录用途、调用方法、依赖、适用范围和最近验证结果。新建或修改后用实际输入验证，
区分自动扫描结果与人工核验结论；脚本运行成功不代表全项目审核完成。一次性简单命令不必强行存成脚本。
会话临时目录换会话就找不到：要复用的走查、快照与报告展开脚本落进 `scripts/`，不只留在会话临时目录。
