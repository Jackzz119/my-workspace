# 第五步：AI 上下文成本与文档关系

只在第五步、上下文专项或相关精简复验时加载。第五步位于拓展之后，统一收尾全部审核产生的上下文。
本步衡量 agent 做事要读多少，不只统计仓库有多大；可复用计量脚本留在 `AUDIT_DIR/scripts/`。

## 1. 重建实际加载关系

识别当前 agent、模型、上下文窗口/输入上限、自动加载配置和项目必读规则；来源不明时标未知。
网上核验对应版本的加载/技能机制和 tokenizer 说明，本地可读取的实际配置与工具输出提供项目证据。
不要读取凭据值或被禁止的存档；无法取得的内容/开销写未知，不通过枚举受限目录补数。

把全部可审文件分类：根/嵌套协议、项目入口、任务总览、架构/功能/规范、技能入口及参考、
审核记录、代码/测试/配置、资源与生成物。为本阶段适用文本分配计量子步骤，存入 `STEPS.md`。
区分四种成本：

- **库存量**：磁盘上所有可审文本的规模，说明范围；不等于一次调用输入。
- **启动必读**：实际自动注入或明确要求开工读取的内容，并写加载规则的来源。
- **按需成本**：做某一功能才读取的文档、代码、技能与工具输出。
- **重复/运行开销**：重复读取、冗余正文、对话历史、工具 schema/返回包装、多代理重复传递等。
  仅对有日志/元数据的部分量化，无法看到的开销不写成零。

构建带类型的关系图：`A --必读--> B`、`A --任务条件--> B`、`A --参考链接--> B`。
普通 Markdown 链接不能视为自动递归读取；只有明确加载规则才进入启动闭包。
区分文件真实路径和链接别名，检测循环，并记录当次实际读取是否重复，不能一律去重后当作实耗。

## 2. 指标及分词口径

逐文件记录，再汇总文档族和目录；根入口、功能文档、技能、本次审核产物都必须单列。

```text
path,category,bytes,lines,token_count,count_method,model_or_encoding,
load_class,load_reason,frequency_evidence,duplicate_group,canonical_source,proposed_action
```

优先用目标模型官方计数器或可验证匹配的 tokenizer，对实际 UTF-8 文本计数；
记录模型/encoding、工具版本、计量日期和输入范围。文件正文 token 不包含消息包装等隐含输入。
不存在可靠匹配时不得把相近 tokenizer 当成精确结果；可同时提供代理计数并标“参考编码”。

无法真实分词时报告 bytes/行数与估算：抽取本项目中文、英文、代码、表格的分层样本，
在有可靠计数样本时校准区间、说明误差；连校准条件也没有时 token 写未知或粗略区间，不能伪装精确值。
禁止把“字符数 ÷ 4”当跨中文、代码和模型通用的准确算法。
文件级 token 之和是统一口径的近似聚合；实际合并输入的边界与包装计数可能不同，必须注明。

报告必须包含：

| 层级 | 输出 |
| --- | --- |
| 每个文件 | bytes、行数、token/估算口径、必读/按需、权威源、重复和改进建议 |
| 文档族/目录 | 数量、库存 token、启动贡献、按需贡献、重复正文与长文来源 |
| 典型任务 | 必需文档/代码集合、加载关系、去重与重复读取成本、工具输出预留 |
| 整体 | 已知启动成本、未知开销、已知可用预算、是否超标及依据 |

按需使用图展示“入口 → 索引 → 功能正文”与重复权威源，不为简单映射额外生成图文件。

## 3. 判断是否超标

选择项目真实任务场景，例如一般 Bug、单功能开发、跨模块接口修改、某玩法或资源加载问题。
报告每种场景实际会读的集合，不把全仓源码算成每轮启动成本。

```text
任务输入估计 = 启动必读 + 本任务按需正文 + 必要代码/工具输出 + 已知对话/包装开销
有效输入预算 = min(已知输入上限, 上下文窗口 - 预留输出)
项目可用额度 = 有效输入预算 - 其他已知必需输入 - 用户约定的预留空间
```

只在模型限制、预留与输入范围可核验时计算比例；未知项单独列出，并说明当前数字是下限还是估计。
用户未设预算时给当前占比和几种有明确假设的情景，不自行设置“超过 X token 就违规”。
启动上下文成本、一次任务总输入、累计计费 token 是三种指标；缓存输入可能减少费用但仍占上下文。
没有官方用量就不能从文件计数倒推出本次实际消耗；没有实时价格就不报货币成本。

## 4. 精简与关系优化

对每个高成本文件或重复簇提出具体改法，写明当前值、预计值、保留的权威正文、移动/删除段落和加载条件。

- 项目入口保留定位、当前约束与短索引；功能细节在对应正文，只在相关任务读取。
- 把重复规则收敛到唯一源，入口用定位明确的链接；不要让几个文件互相要求全文必读而形成隐性全量加载。
- 长文按稳定职责拆，不按固定 token 数硬切；保留术语、条件、例外、强制规则与待决项。
- 技能的发现描述、执行入口和条件参考分层；可执行工具输出优先提供命中范围/摘要，避免重复打印整文件。
- 新拆文档与计量结果统一进入 `AUDIT_DIR`，沿用已有权威文档时原位精简，不另建同义规范。
- 审核报告、步骤蓝图、证据与历史轮次同样纳入成本；默认入口只链当前报告，不把历史全部设为必读。

关系优化示例：

```text
之前：PROJECT 全文包含 A/B/C 功能细节，并要求每次读取全部功能文档
之后：PROJECT 的定位/约束 + 功能索引
      做功能 A → 只读 A 的正文与依赖规范
      做功能 B → 只读 B 的正文与依赖规范
```

这是有条件的优化：若当前协议仍要求全文读取，单纯增加索引不会降低启动成本。
先报告规则与目标的冲突；协议变更须遵守项目授权，不能为省 token 偷改工作规则。

## 5. 运行材料收尾清理

第五步必须处理本次及历史审核留下的运行材料，不能只给清理建议而把过程数据原样堆回项目。
先区分可执行复用脚本与它生成的 CSV/JSON/日志；机器格式不等于无用，存在于磁盘也不等于每轮自动消耗 token。

| 去留 | 判断与动作 |
| --- | --- |
| 长期保留 | 精简 review、执行范围与验证摘要、实际子步骤和迭代经验、未结发现；实现由 commit 定位 |
| 有条件保留 | 下轮比较基线、未结问题原始证据、不可重建的 profile、复验必需输入、已验证复用脚本；写清用途和版本 |
| 完成用途后删除 | 一次性 inventory、重复清单/AST/哈希快照、被最终结果替代的过程 JSON/CSV、临时日志与改写脚本 |

逐组检查后续消费者和重建代价，将必要结论提炼进现有 review/执行摘要/STEPS；删除时修正链接与脚本输入引用。
保留记录直接写在阶段报告，说明路径、下次使用场景及可删除条件。不要为此新增另一套大型库存或把原始数据转抄成长文。
旧覆盖表不能替代下一轮重新生成的清单；若仍有待复验问题，保留其最小证据并列为例外，不能让清理破坏验证。
清理后重算库存与加载成本；默认入口不递归加载 runs，按需用脚本筛出命中项和摘要。

## 6. 报告与复验

输出加载关系、逐文件指标、分类汇总、任务情景、重复正文证据、逐文档精简建议与预期收益。
区分“内容字数下降”“启动必读下降”“按需读取下降”；预计 token 节省不是实际账单节省。
实施后用同一 tokenizer、加载假设和任务集合重算，核对链接/锚点、规则完整性、必读闭包及检索可达性。
用具体任务走一次入口到正文，确认没因精简丢失关键约束；尚未实施时报告模拟值而非改后实测。
报告自身的计量采用固定快照，注明新增报告文字尚未计入或在写完后补计，不无限递归重算自己的计量段落。
纳入此前拓展、步骤蓝图、复用脚本与报告的最终成本，更新步骤复盘；不重复创建整套报告。
