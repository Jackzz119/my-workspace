# 覆盖、证据与阶段报告

首次准备时读覆盖规则；输出方案、删除文件或生成报告时按需查相应节。

## 1. 覆盖规则

`run-id` 采用项目已有运行编号习惯，否则使用日期加序号。记录根目录、分支/提交（无 Git 则文件摘要）、
工作区变更、技术栈版本、目标平台、时间和授权范围。Git 状态只读，不切换用户工作台。

先建立文件总体：逐文件区分自有文本、自有二进制、第三方依赖、生成物、外部链接和受保护范围。
忽略规则不等于无用；也不因为某个文件未跟踪就允许删除。不可枚举范围只记录根级边界，数量写未知。
目录符号链接不递归跟出项目；同一真实文件去重并保留别名，避免循环遍历和重复计算。
大型依赖目录可按来源/锁文件/体积汇总，二进制查元数据和资源/包关系，不能声称已逐行审核。

`coverage.csv` 的最小字段：

```text
path,kind,module,revision,step,substep_id,status,method,evidence,reason
```

- `step`：01–05 或 X01……；每步均从完整清单确定适用面。
- `substep_id`：关联本轮 `00-log.md` 子步骤表的稳定 ID；同一文件可分多行关联不同子步骤，覆盖数量按文件去重。
- `status`：待检查、已检查、待验证、不适用、受限。已删除文件保留删除前记录与实施结果。
- `method`：全文分批阅读、语义分析、引用核验、引擎资源检查、运行测量等；只列目录不算已检查。
- `evidence`：报告中的发现 ID、实际检查记录或受审版本；“没有发现”也记录检查方法。
- `reason`：不适用/受限的具体理由，不能空填，也不能用“文件太多”当排除理由。

报告每步的总体数量、适用数量、已检查数、未检查数、待验证数、受限数与排除清单。
覆盖率 = 已检查适用项 / 可枚举的适用项；受限与未知另列，不能把分母缩小后宣称全仓 100%。
文本按文件/模块统计，二进制按资源统计，运行按场景统计，不能混成一个虚假的百分比。
只完成静态 review 时说“静态范围已审”，动态验收缺失仍为待验证。

并行按互斥模块或检查维度分工，共享画像、规范和同一基线；协调者复核跨模块发现与覆盖并去重。
给每个子代理写明它负责改哪些文件、哪些文件别人在改不能碰（需要改的列进它的报告）；子代理不做改变 Git 状态的操作，
由协调者统一核对、验证和提交。子代理的报告是给协调者的，结论经协调者核过再进阶段报告。
变化导致旧结论失效时，标明失效项并重审相关依赖；用户要求全量复查则重新覆盖全部适用项。

## 2. 研究与方案

每个阶段报告单独记录以下表格，网址直接指向原文而非搜索结果页：

```text
查询 | 检索日期 | 来源标题和 URL | 来源版本 | 可核验的结论 | 适用前提 | 本项目证据 | 采纳/不采纳及理由
```

官方文档描述的是框架契约还是建议要分开；开源项目布局是案例，不能冒称行业标准。
先读本地随版本提供的文档，再网上核验适用版本；本地规定与外部建议冲突时明确差异，
不能静默用网上的习惯覆盖项目决策。资料不足就写不足，不编造最佳实践、收益或来源。

每步的方案沟通必须具体：

```text
范围/文件：
当前问题与证据：
建议改动（文件路径、职责变化或目录前后图）：
为什么适合这个项目、参考什么：
预期好处（实测/估计/定性）：
代价、行为与契约影响：
验证和恢复方式：
已有授权；仍需用户决定的具体事项：
```

发现过多时可分批讨论，但最终范围仍是整个项目。获得该批授权后不再按文件重复问同一问题。

## 3. 删除与精简证据

删除每个候选项前确认：

1. 内容是什么、谁使用、是否已被准确替代；比较正文与差异，不能仅根据文件名或时间判断。
2. 文档链接/锚点、import、动态 import/反射/路径拼装、约定入口、配置、CI、打包/导出均已核对。
3. 游戏资源检查场景/预制体/资源图、UID/GUID、导入元数据、动态加载和外部内容管线。
   采用目标引擎当前版本支持的重命名/移动机制，引用和配套元数据一起更新。
4. 不是受保护的协议/手动存档、他人未完成文件、许可证/归属声明、独有产品决策或恢复资料。
   历史迁移、锁文件、导入元数据及看似重复的生成物，先查生成/重建契约，不能凭外形自动删除。
5. 记录恢复依据：已提交的原版本，或统一目录内仅保存该项所需的差异/备份；未知来源内容保留。
   不把“Git 管理”当作未跟踪或未提交内容已备份，不运行广泛清理命令代替逐项删除。

删除清单写明路径、用途判定、引用证据、保留的权威源、恢复依据和验证结果。
精简文档前后逐条核对强制性语气、条件、例外、术语和待决项；删除重复措辞不能删除规则差异。
文件移动后核对文本链接、构建/运行引用和引擎资源引用，不能只验 Markdown 链接。

## 4. 问题与阶段交付

问题 ID 跨复查稳定，例如 `PA-001`；所属步骤可以变化，状态和证据保留。每条至少包含：

```text
ID / 优先级 / 状态 / 所属阶段
文件与准确位置 / 受审版本
问题、触发条件及具体影响
证据等级：实测确认 / 静态证据 / 待验证假设
证据或复现步骤 / 来源链接
建议、替代方案与代价 / 影响范围与依赖
实施状态 / 验收条件 / 待办链接或 ID
```

优先级按影响、触发概率、规模和修复成本说明理由，不能把所有结构偏好标高危。
待办有既有唯一来源时只关联既有 ID，审核目录存证据和建议；未经授权不向外部任务平台写入。
若用户要求本技能所有新文档集中一处，新建议先保留在 `FINDINGS.md`，不同时复制到其他文档。

每个阶段报告使用以下骨架，内容为空的可说明无发现，不造空任务：

```markdown
# 第 N 步：主题
## 结论与完成状态
## 基线、全项目覆盖与限制
## 本步骤调研与适配结论
## 已讨论方案、授权和取舍
## 发现与证据
## 已执行改动（文件路径、改动目的、原因与 commit/PR 定位）
## 验证（命令目的、结果、失败归因与未验证项）
## 建议、待办和下一步
```

验证按实际变更选择：文档清理查链接与语义，模块移动查消费者与构建，行为修改查契约/回归，
性能优化跑可比较场景。扫描器告警须人工复核，现有测试绿也不能证明整个项目没有问题。
数字旁边写清口径；目标没完全达成的，剩余数量与原因紧跟在数字后面，别让读者到别处找原因。

总报告 `99-report.md` 写给要批注的人看：先结论、再各步摘要、再待决定事项（每项给推荐与默认）、最后问题清单；
每节有稳定锚点，方便批注引用。用批注报告工具生成页面发布，源文留在运行目录。

阶段报告只用路径定位代码和文档，实现及删除原文由对应 commit 提供；不复制源码、逐行 diff 或另存完整 patch。给用户验收的总报告页按宿主协议的报告规范写。
路径很多时按模块分组，仍能定位各变更文件；保留原因、结论、验证和未完成项，不把机器指标全文转贴成人读报告。
每步提交本任务的改动与报告（宿主协议要求先只暂存时照协议），记录该步基线及提交主题/PR，交付时给出实际提交 SHA；后续 rebase 的映射在交付时说明。

## 5. 拓展步骤约定

用户可在 `AUDIT_DIR/EXTRA-STEPS.md` 添加条目。每项最少有 ID、启用状态、目标和验收条件；
可附重点、来源线索、限制。朴素的自然语言清单同样可读，不因没遵守模板就忽略真实用户要求。
只含示例、明确禁用或没有真实目标的项不执行。需求歧义先查已有上下文，再问具体缺口。
来源线索仍需实时打开核验；不得因为用户提供链接就省去当前阶段的真实研究。

拓展范围默认全项目，每项走同一共用流程并写 `runs/<run-id>/X01-主题.md`。
拓展不覆盖运行中的用户指令、现有权限或受保护范围，不自动触发外部发布、安装或全量重构。

## 6. 研究起点（运行时重新检索，不能代替本轮研究）

以下官方资料用于校准方法，不要求每个项目读取所有技术栈资料：

- [Next.js 项目结构](https://nextjs.org/docs/app/getting-started/project-structure)：区分框架约定与项目组织选择。
- [Godot 项目组织](https://docs.godotengine.org/en/stable/tutorials/best_practices/project_organization.html)：核对场景与资源的关系。
- [Godot 文件系统](https://docs.godotengine.org/en/stable/tutorials/scripting/filesystem.html)：核对资源移动与引用处理。

这些是方法参考；使用时切换到实际项目版本，其他框架/引擎检索对应的一手资料。

## 7. 蓝图、本轮日志与流程迭代

两层分开存：根目录 `STEPS.md` 是跨轮蓝图，`runs/<run-id>/00-log.md` 是这一轮的实际执行。
问题状态在 `FINDINGS.md`，执行证据在阶段报告，子步骤以链接关联。都不是第二份问题台账。

`STEPS.md`（跨轮，只留仍有效的）：

```markdown
## 第 N 步 · 蓝图 vK（上次校准：<run-id>）
### NN-S01 · 子步骤名称 — 目标 / 方法 / 产出与验收 / 适用条件
## 跨轮经验 — 每条一句：做法 + 依据（哪一轮发现的什么问题）
## 可复用工具 — 脚本、调用方式、适用范围、最近验证
```

`00-log.md`（本轮）：

```markdown
# 运行 <run-id> · <主题>
## 一、用户原话（原样）= 真源需求，第五步收口逐条验收
## 二、范围、授权与任务拆解（子步骤表：ID / 目标与范围 / 依赖与方法 / 产出与验收 / 状态与证据）
## 三、续接（中断后先读哪里、环境限制）
## 四、进度（时间 · 子步骤 · 事件，一行一条）
## 五、收口验收（真源需求与各步要求逐条：达成 / 回到哪一步重做）
## 六、复盘（发现问题的、重复低效的、漏掉边界的；写回蓝图的改动）
## 七、验收（总报告发出后用户的批注：逐条处理与回复）
```

子步骤状态：待执行 / 进行中 / 已完成 / 受阻 / 已取消；取消或受阻必须写原因。
准备下一大步骤时按需实例化该阶段，不提前臆造完整项目细节。
阶段覆盖清单关联子步骤 ID，父阶段验收核对：适用项均有负责步骤，没有孤儿范围或遗漏的依赖。
“步骤已完成”表示要求的检查和产出完成，不等同所有发现已修；未满足的验收条件不能划为完成。
复查保留稳定 ID 和旧轮证据，当前轮所有需重审项重新记待执行，不把旧轮勾选当成新轮完成。
新一轮先验证版本、模块和历史改进是否仍适用，再调整蓝图。结果有新证据才改流程，避免越审越繁琐。
`INDEX.md` 的历史表一轮一行（第 N 轮 · 运行目录 · 范围 · 报告链接）；历史结论绑定当时基线，不覆盖现状。

## 8. 运行材料生命周期

- 长期保留精简阶段 review、运行范围/命令目的/验证结果摘要、子步骤及迭代结论、未结问题；实现细节以 Git 为准。
- 清单、覆盖 CSV、AST/哈希 JSON、原始日志是工具使用的证据数据，支持续接、覆盖复核和前后比较；脚本才是可执行工具。
- 第五步按用途清理整个审核目录：一次性过程数据和重复快照完成用途后删除；跨轮基线、复验原始输入或未结问题证据确有用途才留。
- 在阶段报告简记保留路径/目录、消费者或下次使用场景、版本与何时可删；不为登记去留再制造一套庞大清单。
- 删除前提炼摘要、核对报告/脚本引用和恢复依据；下一轮生成当前清单，旧清单仅用于版本明确的比较，不作为当前覆盖证明。
- 不按扩展名批量删除，不读取受保护范围；默认入口只指向当前状态与必要材料，历史证据按问题查询。

## 9. 额度与断点续跑

额度用尽时会话直接中断，不给收尾机会；断点只能是「随做随存」的副产品，不能指望最后一刻补写。

断点写在本轮 `00-log.md` 的「三、续接」节，覆盖式更新、只留最新一份：

```markdown
## 三、续接
- 断点：<子步骤 ID 与名称>，做到哪、还剩什么
- 已落盘：<运行目录里已写的报告、证据、脚本；已暂存或提交的改动与 SHA>
- 未落盘：<只存在于会话、续跑时要重做的部分；没有写「无」>
- 下一步第一件事：<一句可直接执行的动作>
- 环境：<分支、worktree、依赖服务、凭据缺口等续跑前要核对的事>
- 额度：<哪个窗口用到多少、何时重置；续跑方式：自动续跑的任务名与时间，或交用户手动>
```

- **查用量**：用宿主给的途径——Claude Code 桌面版的用量工具（各额度窗口的已用百分比与重置时间）、CLI 的用量命令、
  API 账户的 Usage & Cost 接口或自己记的 `usage` 字段。查不到就靠「随做随存」兜底，不猜额度。
- **何时主动停**：任一窗口到 90%，或按本轮已耗速度估算撑不到下一个可交付单元（一个子步骤、一次实测）。
  停在子步骤边界；不为凑额度把子步骤拆碎。
- **自动续跑**：只在用户授权过时排，授权只管本轮。时间定在重置之后几分钟；任务提示写清
  「继续 project-audit 运行 <run-id>：先读 INDEX.md 与 00-log.md 的续接节」，任务名与时间记进「续接」。
  续跑若发现本轮已收口，什么都不做并说明。
- **续跑核对**：分支与 HEAD、暂存区与未提交改动、运行目录里的产物，与断点记录逐项对照；不一致以磁盘与 Git 为准，
  在进度里记一行差异。中断期间别的会话动过同一批文件的，先停下问。
- **子代理**：派出前把它的产出路径写进断点；结论落到运行目录才算完成，会话被截断时在途的结论按「未落盘」处理。
